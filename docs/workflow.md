# Customizing `workflow.yml`

This guide explains how to adapt Relais's behavior on a repository without reading the code: which Linear or GitHub events trigger what, with which model, which limits and which checks.

## 1. Role of the file and merging with the pack

Relais reads two files and combines them:

- **the pack workflow** `packs/standard/workflow.yml` (shipped with Relais): it defines the default behavior;
- **the project workflow** `.relais/workflow.yml`, at the root of the repository handed to Relais (the `repoPath` path in `~/.relais/config.yaml`). It is optional: without it, the pack applies as is. `relais init` creates a minimal one (see below).

The project file contains **only what you change**. Exact merge rules:

| Part | Rule |
|---|---|
| `tracker`, `states`, `limits`, `workspace` | Deep merge, key by key: `limits: { per_run: { duration: 2h } }` only changes the duration and keeps the pack's `turns`. |
| Lists (`verify`, `setup`, `pickup.checks`…) | **Replaced** entirely, never concatenated. |
| `on` | **Replaced per event type**: if the project declares `on.status.changed`, the pack's whole `status.changed` list is ignored; the pack's other events stay active. |
| `jobs` | Deep merge, job by job: `jobs.review.model: sonnet` only changes the model of the pack's `review` job. A job name absent from the pack creates a new job. |
| A job's `extends` | The job inherits from its parent field by field, **except** `on_start` and `on_success`, which entirely replace the parent's value when present (`on_start: {}` therefore cancels the inherited `move`). |

The order is: pack + project merge, then resolution of `extends`. Practical consequence: `jobs.dev.verify` defined in the project is inherited by `dev-feedback` and `fix-ci`, which extend `dev`.

Merge limitation: you cannot **delete** a key inherited by a job (`null` is rejected). You can only replace it with another value. To neutralize a behavior, act on the `on` rules (section 6).

**When is the file read?** Only once, when `relais up` starts (and on every `relais plan`). It is read from disk, in the `repoPath` working copy, not from `origin`. After a change: restart `relais up`. A validation error prevents startup.

File generated by `relais init` (if `.relais/workflow.yml` does not exist yet):

```yaml
version: 1
extends: standard
tracker:
  kind: linear
  team: REL
workspace:
  setup: ["npm ci"]
jobs:
  dev:
    verify: ["npm run lint", "npm run typecheck", "npm test"]
```

`setup` is `["npm ci"]` if the repository has a `package-lock.json`, otherwise `[]`. `verify` suggests the `lint`, `typecheck` and `test` scripts found in `package.json`; you can edit the list during `init`.

## 2. Key-by-key reference

### `version` (required)
Always `1`. Any other value, or its absence, is rejected.

### `extends`
Accepted for readability (`extends: standard`) but **has no effect**: the pack used is always `packs/standard`.

### `tracker`
| Key | Type | Default | Effect |
|---|---|---|---|
| `kind` | `linear` | `linear` | Only supported tracker. |
| `team` | text | — | Informational. The team actually followed is `linearTeamKey` in `~/.relais/config.yaml`. |
| `pickup.checks` | list among `has_description`, `not_started`, `has_acceptance_criteria` | pack: `[has_description, not_started]` (`[]` if no file defines it) | Checks made before the **first** run of a `pickup: true` job (see `jobs.*.pickup`). |

The checks:
- `has_description`: the ticket description is at least 30 characters long.
- `not_started`: no `relais/<ticket-id>-…` branch already exists on `origin`.
- `has_acceptance_criteria`: the description contains « critères d'acceptation » (or « critère d'acceptation », « criteres… ») or "acceptance criteria", case-insensitively.

If a check fails, the ticket is blocked and Relais replies in the Linear session with the list of problems (« I cannot start this ticket… Fix it, then reply in this thread »). `relais plan` shows, for each delegated ticket, whether it would be picked up or not, and why.

### `states`
Maps Relais's five **logical states** to the exact names of the team's Linear columns (statuses):

| Logical state | Pack |
|---|---|
| `todo` | `Todo` |
| `dev` | `In Progress` |
| `human_review` | `Human Review` |
| `ai_review` | `AI Review` |
| `done` | `Done` |

You can redefine only some of them; after merging, all five must have a name. `ready` ("Ready to Merge") is no longer declared by the pack (ORC-170); a `move` to a state without a name is rejected at load time, with the key's path. No other state name is accepted. During « Connect Linear », Relais creates the missing statuses in the team. A Linear status that is not mapped to any logical state is seen as "unknown": a move to it produces a `status.changed` with an empty `to`, which `from`/`to` rules do not recognize.

### `limits`
| Key | Type | Default | Effect when the limit is reached |
|---|---|---|---|
| `parallel_sessions` | integer > 0 | 3 | Number of simultaneous runs in the `dev` queue, if `factory.yml` does not set `concurrency`. Beyond that, runs wait in a persistent queue. Each run in the `dev` queue also receives `PORT = workspace.ports.base + slot number` (0 to `parallel_sessions - 1`). |
| `question_sessions` | integer > 0 | 2 | Same for the `questions` queue. |
| `per_run.turns` | integer > 0 | 150 | Number of assistant messages in a run, a message counting once even if written over several lines of the stream. Beyond that, the run is interrupted; its result is `limit`. A job with `step` never exceeds its step's turns: `per_run` and its `limits` can only lower them. |
| `per_run.duration` | duration | `90m` | Maximum duration of a run, same `limit` result. |
| `verify_attempts` | integer ≥ 0 | 4 (preset) | Number of verification passes before blocking the ticket (see `jobs.*.verify`). `0` and `1` block on the first failure. By default, the bound from the [`factory/default` preset](preset.md): 3 returns to the run, the 4th failure blocks. |
| `ci_fix_attempts` | integer ≥ 0 | 2 (preset) | Number of runs a red CI (`pr.checks_failed`) or a conflict with the base (`pr.conflicted`, ORC-146) can launch, together, before the next one blocks the ticket (see below). `0` blocks on the first. |
| `review_rounds` | integer > 0 | 2 (preset) | Given to the review skill in its prompt (« Max review rounds: 2 »); only for jobs whose skill ends with `:review`. The skill respects this number; Relais does not count it. By default the preset's `review_ci` bound, the count shared with red CI and rebases (ORC-184, ORC-216, ORC-146). |

The defaults of `verify_attempts` and `ci_fix_attempts` come from the [`factory/default` preset](preset.md) (ORC-187); the pack no longer declares them. These two keys remain a possible override until `workflow.yml` is removed (ORC-177).

`per_run` is the default limit for **all** jobs; each job can replace it field by field with its own `limits`.

What happens when a run hits a limit (`limit`) or fails?
- Job in the `dev` queue: the ticket is **blocked** and Relais says so in the ticket's block comment (« The run <job> reached a limit (turns, duration or budget). », or « … failed. »; an attempt stopped at its token or turn cap says « The run <job> spent its token budget … » or « … its turn budget (max_turns of its step). », kind `budget`, ORC-216). A reply in the ticket relaunches that job, or `dev-feedback` if the block has none (the pack's `session.prompted` rule).
- Job in the `questions` queue: Relais replies « I could not finish (failure or limit reached). ».

What happens when CI stays red (`ci_fix_attempts`)?
- Each `pr.checks_failed` rule that launches a run (`fix-ci` in the pack) counts that run against the ticket. Once `ci_fix_attempts` runs have been launched, the next red CI does not apply the rule: the ticket is **blocked** and Relais says so in the block comment (« CI still failing after 2 attempts of fix-ci. », plus the failing checks). Subsequent red CIs relaunch nothing and do not repeat the message.
- The count resets to zero when CI turns green (`pr.checks_passed`, which also lifts the block caused by this bound), when another PR is detected for the ticket (`pr.opened` with another number), or when a human relaunches the blocked ticket (reply in the ticket, project label, status change or delegation that launches a run). Neither a new push by the agent (that is the loop itself) nor a `debounce` timer armed before the block resets it.
- Unlike `verify_attempts`, which counts passes (including the first run), `ci_fix_attempts` counts relaunches: with `2`, two `fix-ci` runs, then a block on the third red CI. This is the unit of invariant I5 ([`decisions/ORC-138.md`](decisions/ORC-138.md), point 8).
- Provisional bound: the AI review → fix loop is not yet counted by the engine, and so does not share this counter with red CI. The single counter for both loops arrives with ORC-184 and the ORC-187 preset.

Durations: a number (milliseconds) or a `<integer><unit>` text with the unit `ms`, `s`, `m` or `h` (`90m`, `30s`, `2h`). Combinations such as `1h30m` are rejected: write `90m`.

There is no "unlimited" value: see section 8.

There is no budget in dollars (ORC-216): a `usd` key left in `per_run` or a job's `limits` is ignored. Budgets count tokens and turns: `budgets` of `factory.yml` ([`configuration.md`](configuration.md)).

> Queue capacities (`parallel_sessions`, `question_sessions`) are global to the instance: they are read from the workflow of the **first** project in `config.yaml`. The other limits are specific to each project.

### `workspace`
| Key | Type | Default | Effect |
|---|---|---|---|
| `setup` | list of commands | `[]` | Run (via `bash -c`, in order) when a worktree is **created**, not on later runs that reuse it. If one fails, the worktree is deleted and the ticket blocked (« Launch error: The worktree setup failed: <command> »). |
| `ports.base` | integer > 0 | 4200 | First port assigned to runs in the `dev` queue (`PORT` in the run's environment). |

### `on`
The event rules, detailed in section 3.

### `jobs`
A job describes **how** to launch a Claude Code run. Fields:

| Field | Values | Default | Effect |
|---|---|---|---|
| `extends` | name of another job | — | Inherits its fields (see section 1). |
| `step` | agent step of the [preset](preset.md) | — | The step this job runs (ORC-136): it sets its effort (`claude --effort`) and caps its turns. A name that is not an agent step makes loading fail. Without `step`, the job keeps its own limits and has no effort, except `claude.effort.default` from `factory.yml`. |
| `queue` | `dev`, `questions` | **required** | Execution queue (section 5). A `dev` job is only launched on a ticket delegated to Relais. |
| `model` | text | **required** | Passed as is to `claude --model` (alias such as `sonnet`, `opus`, `haiku`, or full identifier). |
| `workspace` | `worktree`, `trunk-readonly`, `knowledge` | **required** | `worktree`: git worktree specific to the ticket, on a `relais/<ticket>-<title>` branch, reused from one run to the next. `trunk-readonly`: up-to-date copy of the main branch, run launched in plan mode (read-only). `knowledge`: worktree of the knowledge repository; the job is ignored if no knowledge repository is configured. |
| `session` | `new`, `resume` | `new` | `resume` resumes the ticket's Claude session if it exists (the development context), otherwise opens a new one. |
| `skill` | text | **required** | The run's prompt starts with `/<skill>` followed by the ticket (identifier, title, URL, branch, PR, description). The pack's job skills are called `relais:dev`, `relais:feedback`, `relais:fix-ci`, `relais:review`, `relais:ask`, `relais:learn`; they load the method skills themselves ([`pack-and-skills.md`](pack-and-skills.md#method-skills)). |
| `input` | `feedback`, `ci_failures`, `thread`, `verify_failures` | — | Section added to the prompt (see below). |
| `verify` | list of commands | `[]` | Run after a successful run (see below). |
| `repo_checks` | boolean | `false` | The run goes through `verify` even without commands: the commands from `.factory/config.yml` read on the base branch, forbidden paths, the freeze. Merging then requires a green `verify` on the reviewed commit. True in the pack for `dev`, what inherits from it, and `review`. **Only such a job publishes** (ORC-125): a job that writes code without it stays in its worktree, the agent having no way to push. |
| `verify_failure` | `block` | — | A failing `verify` blocks the ticket instead of relaunching the job, which did not write the commit: `review`, on a human push. |
| `pickup` | boolean | `false` | If `true`, applies `tracker.pickup.checks` before the ticket's first run (when no Claude session exists yet). `intake` runs them too, as inputs of its guard rather than a block (ORC-206, [preset](preset.md#intake-step-and-the-guard-before-in-progress-orc-206)). Both also read the « blocked by » tickets not done: the ticket waits for them instead of starting (ORC-363, [preset](preset.md#waiting-on-a-blocked-by-ticket-orc-363)). |
| `structured_output` | boolean | absent | **Provisional** (ORC-289, until ORC-191/ORC-192 make every agent call `submit_result`): if `true`, a run in the `dev` queue that ends without valid output is a failure. When absent, it stays a success. In the pack, `true` for `dev` only, the `build` step (ORC-136). |
| `limits` | `{ turns, duration }`, each optional | `limits.per_run` | Replaces the per-run limits for this job. |
| `on_start` | `{ move: <logical state> }` | `{}` | Moves the ticket when the run starts (if it is not already there). |
| `on_success` | `{ move: <logical state>, post: summary \| reply \| synthesis }` | `{}` | After a successful run (and successful checks): moves the ticket and/or posts in the Linear session the message the factory composes from the agent's `submit_result`, never from its last message (ORC-214): `summary` (end of the dev work) posts its summary, why, risks, untested and points to review; `reply` (reply to feedback, to a question) and `synthesis` (review synthesis) post its `summary` alone. A run that returned no result posts a fixed sentence saying so. The text then goes through the `OutputPolicy` ([`linear.md`](linear.md#what-the-factory-publishes-orc-214)). |

The values of `input`:
- `feedback`: the Linear thread messages accumulated since the last run, plus the PR's unresolved review comments (title « Feedback to address »).
- `ci_failures`: « The PR's CI is failing. Run `gh pr checks` for the details. » (title « CI failures »).
- `thread`: the text of the message that triggered the run (mention or command) (title « Message »). Empty if the event is not a message.
- `verify_failures`: used by Relais itself when it relaunches a job after failed checks; no need to configure it.

The checks (`verify`): with sandboxes (`FACTORY_CONTAINER_CLI`), the factory pins the branch's last commit, exports it with `git bundle` to a fresh clone, and runs each command in a fresh container with network `none` (`bash -c`, 15 minutes maximum per command), **all of them** even if one fails. What is not committed is not checked. Without a sandbox, see `FACTORY_ALLOW_HOST_VERIFY` in [`configuration.md`](configuration.md#environment-variables). The same commit already found green is not rechecked. On top of these come, as blocking, `factory/chemins-interdits`, `factory/secrets` (gitleaks, on the commits added to the base branch) and `factory/tests-gelés`.
- All pass: `on_success` applies.
- One fails and attempts remain: Relais relaunches **the same job**, resuming the session, with the output of the failing commands, trimmed to its beginning, its end and its error lines (8,000 characters at most).
- After `limits.verify_attempts` failed passes: the ticket is blocked and Relais posts the list of failing commands in the session.
- The check cannot run (engine down, silent sandbox, failing `setup`, rejected configuration, unreachable forge): `verify.errored`, the ticket is blocked for infrastructure reasons, without sending anything back to the agent or touching the counter.
- Same failure three times in a row (same failing commands, same exit codes, unchanged commit content): the ticket is blocked with the cause « Loop », even if passes remain. The worktree's fingerprint is the git tree of its content, untracked files included, computed without touching its index or its objects (60 s at most). Files written by the checks must be ignored by git (`coverage/`, reports): otherwise the fingerprint changes on every pass and the guard never triggers, without ever blocking wrongly. The count resets to zero on a green check or a human relaunch. Outside a git repository, this guard does not apply. Its bound comes from the preset and is not set in `workflow.yml`.

Pack jobs:

| Job | Queue | Model | Role |
|---|---|---|---|
| `dev` | dev | sonnet | First development; moves the ticket to `dev` at the start, to `human_review` at the end, and posts a summary. |
| `dev-feedback` | dev | sonnet | Extends `dev`: resumes the session to address feedback. |
| `fix-ci` | dev | sonnet | Extends `dev-feedback`: fixes CI. |
| `review` | dev | opus | AI review in a fresh session, then moves back to `human_review`. |
| `ask` | questions | sonnet | Answers questions read-only (30 turns, 5 min, $0.50). |
| `learn` | questions | haiku | After a merge, feeds the knowledge base. |
| `remember` | questions | haiku | Extends `learn`: remembers what it is asked to (`@relais retiens …`). |

## 3. The `on` rules

`on` maps an event type to an **ordered list** of rules. For a given event, Relais goes through the list and applies **the first rule that matches, and only that one**. If none matches, nothing happens, except for a reply in the ticket's dev session, which is always kept (see `session.prompted`).

### Configurable events

| Event | When | Specifics |
|---|---|---|
| `ticket.delegated` | The ticket is delegated to Relais in Linear. | — |
| `ticket.commented` | A workspace user comments on a blocked ticket, outside a session (ORC-196). | A reply to the block comment: checked against the matrix, kept for the run, which launches the blocked step. Absent from versions pinned before it. |
| `status.changed` | The ticket changes status in Linear (by a human). | Filterable with `from` / `to`. Moves made by Relais itself do not generate this event. |
| `session.mentioned` | `@relais …` in a comment, when the first word is not a command. | — |
| `session.prompted` | Reply in a Relais Linear session. | The accepted message always enters `humanInbox`, whether a rule matches or not: without a rule for the ticket's state (`todo`, `ai_review`, `ready`, `done` in the pack), it waits for the next run of the implementing agent. The rule receives an instruction from any session, and any reply in the dev session; a question there also launches `ask`. A question from a thread launches `ask`, without reading the rules ([details](linear.md#human-messages-during-a-run)). |
| `session.stopped` | "Stop" button in Linear, or ticket taken away from the agent. | In a question session, Relais stops the answer in progress, without reading the rules. |
| `label.changed` | A label is added to or removed from the ticket (by a human). | Filterable with `label`. Only an addition matches a rule: a removal enters the inbox and the journal (`change: removed`) but triggers nothing. |
| `push.human` | A human pushes a commit to the ticket's branch. | No rule in the pack. Received through the GitHub `push` webhook (account that is not a bot), marked untrusted ([`github.md`](github.md#github-webhooks)). |
| `command` | `@relais <word> …` when `<word>` is a `say` value from the `command` list. | Filterable with `say`. |
| `pr.checks_passed` | The PR's CI passes. | Before the rules, Relais resets the red-CI relaunch count (`limits.ci_fix_attempts`) and lifts the block caused by this bound. |
| `pr.checks_failed` | The PR's CI fails. | A rule that launches a run is bounded by `limits.ci_fix_attempts`: once the bound is reached, Relais blocks the ticket instead of applying the rule. |
| `pr.conflicted` | The PR conflicts with its base branch (ORC-146). | Only for the ticket's open PR. A rule that launches a run counts on the same bound as red CI (`limits.ci_fix_attempts`): once it is reached, Relais blocks the ticket (cause « conflict ») instead of applying the rule. |
| `pr.merged` | The PR is merged. | Before the rules, Relais records the PR as merged and stops work on the ticket like a `stop`, without blocking it: the running `dev` run is stopped, waiting or queued runs and `debounce` timers are deleted. After that, no job from the `dev` queue starts on the ticket any more, whatever rule, timer or wait requests it (project label, reply, red CI, waiting or queued job): the refusal is only traced, with no message in Linear. The end of the stopped `dev` run and its checks are ignored. The rules apply after the stop: `done`, cleanup and `learn` do not change, and jobs from the `questions` queue (`learn`, `ask`) still run. The ticket becomes active again when a human changes its status to something other than *Done* (also when Relais could not move it to *Done*), delegates it again, or a new PR (another number) is detected for it. GitHub polling no longer looks at a ticket in *Done* whose PR is merged: a new PR is only seen once the ticket has left *Done*. |
| `pr.closed` | The PR is closed without merging. | Before the rules, if it is the ticket's known PR, open, and the ticket is not *Done*, Relais cancels work on the ticket: the running `dev` run is stopped, the waiting job and the expected check are deleted, the ticket is blocked (« PR #n closed without merge ») with a message in the session. A human relaunches as after a `stop` (reply in the ticket); a new PR (another number) is followed like any PR, and the same PR reopened becomes open again (`pr.opened`). |

The pack uses neither `pr.checks_passed` nor `pr.closed`: you can add your own rules there.

### Lifecycle events (not configurable)

These types are accepted by the loader, but Relais handles them in hard-coded fashion: a rule placed under them **never triggers**.

| Event | Fixed behavior |
|---|---|
| `run.finished` | Success: checks if the job has any, otherwise `on_success`. Failure or limit: ticket blocked (`dev` queue) or error message (`questions` queue). `dev` queue, depending on the attempt's outcome (ORC-289): agent question (`needs_input`) or disputed ticket (`spec_impossible`), ticket blocked with the question or the justification; infrastructure failure (`errored`: runner or sandbox down, unreadable output; not an error after the run has ended), ticket blocked, without a fix run; an already blocked ticket (the agent called `ask`) keeps its block, without a second message. A `done` returned by a failing run is a failure. Stopped run: nothing. End of a `dev` queue run after the PR is merged: nothing. |
| `verify.passed` / `verify.failed` | `on_success`, or a new attempt, or a block (see `verify`). After the PR is merged: nothing. |
| `timer.fired` | A timer set by a decision expires (event `timer:<key>:<due>` written to the inbox). Kind `debounce`: launches the job whose `debounce` delay just expired (and unblocks the ticket). Kinds `clarify.remind` and `clarify.expire` (ORC-210): at 24 h the open `clarify` questions are asked again, at 72 h the ticket is blocked on `intake`; a round answered or ended since does nothing ([preset](preset.md#clarify-questions-reminder-and-expiry-orc-210)). Kind `usage.reset` without a job: nothing. |
| `pr.opened` | Records the PR and attaches it to the Linear session. |
| `control.pause` / `control.resume` / `control.stop` | Pause / resume of the queue, stop of a ticket (UI, `relais pause`, `relais resume`, `relais stop`). |

**Delegation withdrawn** (`ticket.undelegated`, internal: no rule can name it). The reconciliation writes it when a human takes the ticket back from the agent in Linear, after a `session.stopped` when a run is under way, which stops that run as Linear's Stop does. On a delegated ticket that is not blocked, Relais cancels its work as a cancel of the ticket stops it (ORC-227): the run is stopped, the verdict of a check in progress is ignored, the waiting job and the `debounce` timers are deleted, nothing is published. It writes nothing in Linear and blocks nothing. A blocked ticket keeps its block and its job: its work already ended, by the `session.stopped` when a run was under way. Unlike a cancel, the block and the messages kept in `humanInbox` stay.

Any other name under `on` is rejected (`on.<name>: unknown event type`), except the old names, still accepted as aliases: `ticket.moved` (read as `status.changed`), `label.added` (read as `label.changed`) and `debounce.fired` (read as `timer.fired`). A single file cannot declare an event under both its names: loading is rejected (`on.ticket.moved: same event as on.status.changed`).

Events about a ticket that Relais does not follow yet are ignored, except `ticket.delegated`, `session.mentioned`, `session.prompted` and `command`, which add it to the followed tickets.

**Untrusted events.** Each event carries a trust label (`taint`). An event marked `untrusted` (content from a source the orchestrator does not consider trustworthy) never launches a `workspace: knowledge` job (`learn`, `remember`): the rule applies without that run, and a Linear activity explains the refusal. The other runs the event requests carry a mark of it (`sensitivePaths`, a list kept for the decisions the journals record, of which only the presence is read): the recorded run and the runner request carry it. Linear ingestion marks as `untrusted` whatever Linear does not attribute to a workspace user: reply or comment without a user id, coming through a bot or from outside the workspace, ticket change made by an integration or an OAuth app, delegation or move found by reconciliation without a signed actor ([Linear](linear.md), ORC-160); GitHub ingestion always marks a `push.human` and a `pr.reviewed` as `untrusted` ([GitHub](github.md#github-webhooks), ORC-134). The runner enforces nothing while the run writes: `checkClone`, which `verify` and the publication both run on every commit of the branch since the base, refuses the diff (`factory/chemins-interdits`, ORC-338), and so does `verify` on the host without sandboxes (`hostChecks`), with the same function (`checkBranchPaths`) on the branch read on the factory's repository against the forge's default branch, fetched first: the same verdict as on the clone. As on the clone, what gives no verdict (no worktree, a git read that fails, a config the default branch refuses) is an infrastructure or config failure that blocks the ticket, never sent to the agent, and no command runs on a refused branch. The rules:

- **Every run, trusted or not:** the unconditional forbidden paths: `.github/**` (workflows, actions, `dependabot.yml`…), `CODEOWNERS` at any depth (GitHub reads it at the root, in `.github/` and in `docs/`), `.env`, `.envrc` and every `.env.*` but the templates `.env.example`, `.env.sample` and `.env.template`, which leave this rule only, not the forbidden directories they may sit in (dotenv, Vite and Next.js load `.env`, `.env.local`, `.env.<mode>` and `.env.<mode>.local`, and direnv runs `.envrc`: they hold values or run; an unknown `.env.*` is treated as one of them), `.factory/**`, `.claude/**`, and what runs at checkout or install (git hooks, `.gitattributes`, `.gitmodules`, `.npmrc`, `.yarnrc*`, `.yarn/releases/**`, `.yarn/plugins/**`, `.pnpmfile.cjs`, `setup.py`, `package.json#scripts`, `.husky/**`, `.vscode/**`, `Dockerfile*`, `.devcontainer/**`), plus `claims/**`.
- **Untrusted branch:** when a run that read untrusted content first starts in the ticket's worktree, the ticket records the branch's head at that moment (`untrustedSince`, sticky). From then on, what the agent's commits since that head touch in the repository's [`sensitive_paths`](repository-configuration.md), read on the default branch, is refused, at every later verification and publication of that ticket, whoever runs next: the untrusted run's commits stay on the branch. What a trusted run committed before stays the human reviewer's, as on a trusted branch, and so do the commits a human pushed to the branch (`push.human`: the ticket keeps each push's `before` and `after`, and only the commits between them are the human's, not the agent's they were built on) and the default branch's: a teammate's edit of a sensitive path never wedges the ticket. A push recorded without its `before` leaves out nothing. A merge counts by what it changed beyond the clean merge. A head that was not read, or that is no longer an ancestor of the branch (a rewritten history), reads all the agent's commits since the branch left the default branch, human pushes still left out. A ticket from before this mark is read once in its run records, at its first verification, publication or untrusted launch, and the answer kept on it: its whole branch when an untrusted run of a worktree job worked on it, and a later untrusted run does not narrow that. An entry of `sensitive_paths` that names nothing is left out of the check with a warning (`factory validate`, the daemon's log); an untrusted branch is then refused as a config failure until it is fixed, and trusted branches go on.
- **Trusted branch:** a branch no untrusted run ever worked on may change the repository's `sensitive_paths`. Nothing blocks it; the human review of the draft PR is the control, as for any other file.

 Each pending piece of feedback keeps the label of the event that brought it: a run that reads feedback (`input: feedback`) is untrusted as soon as one of those pieces of feedback is, even if launched later by a trusted event (end of `debounce`, project label, move to `dev`). A run's label is set at its **launch**, based on what it reads then, and not when the decision requests it: a job put on hold behind a run (launched by `settle` at the end of that run) or left in the queue reads the feedback that arrived in the meantime, and becomes untrusted if any of it is. The run also keeps the sensitive paths it was requested with. Unresolved review comments that the forge returns to an `input: feedback` run are always untrusted: anyone who can comment on the PR writes them, and nothing authenticates them as coming from the team (ORC-160). A `knowledge` job that would read untrusted feedback at launch (review comments included) is refused, and the refusal is explained in its Linear session. Feedback recorded before this rule, without a label, counts as trusted, like an event from the first version of the journal: no source marked any event `untrusted` back then. **What a run reads beyond its input takes the label of who wrote it, not of who started the run** (ORC-349): a run that resumes the ticket's Claude session (a `verify` relaunch, a reply) carries the sensitive paths when the ticket's branch carries the mark of an untrusted run (`untrustedSince`, ORC-338), since that session read what that run read; a `knowledge` job (`learn` after a merge, `remember` too, whatever its `input`) can read the ticket and its PR, and is refused, its refusal explained in its Linear session, on such a branch or once the ticket's journal holds an untrusted event that brings content (a delegation, a human message, a `pr.reviewed`, a `push.human`; not a move, a label or CI's facts). Both are read at the launch, outside any decision: a recorded journal replays as it was decided. `learn` after a merge reads nothing of the PR that the factory never ingested, a comment on the PR's conversation (`issue_comment`), or any review when GitHub webhooks are off (the poll reads none) (ORC-361): its prompt gives it the messages and reviews of the ticket's journal, the trusted ones only (an untrusted approval without a word lets it run, and is not given), and of the forge it reads the merged diff alone (`gh pr diff`: code a team member pushed or the factory published, and a human merged), the pack's hook refusing any other `gh` command in a `knowledge` run (`forge-read`). The other runs only take the label of their event.

**Authorizations.** Before the rules, `decide` checks the [authorization matrix](linear.md#authorizations-who-can-do-what) against the event's signed actor and the roles journaled with it (ORC-186): a delegation, a mention or a command requires the right to trigger; a reply in the session, the right to reply (or to relaunch, if the ticket is blocked); a label or a status change, only when the rule that takes it launches a run (`run:`), the right to trigger or, for a blocked ticket, to relaunch. A refusal applies no rule and replies in the ticket. The `on` rules do not change the matrix; the `factory/default` preset will declare it (ORC-187).

### Rule fields

**Conditions** (all must be true):

| Field | Effect |
|---|---|
| `when` | Condition on the ticket's state (section 4). |
| `from`, `to` | Logical state of origin / destination. Only filter `status.changed` (ignored on other events). |
| `label` | Exact label name. The rule matches **only** the addition of this label (`label.changed`). |
| `say` | Command word, **in lowercase** (Relais lowercases the typed word). The rule only matches `command`. Each `say` declared under `command` becomes a recognized command word. |

A rule with no condition always matches.

**Actions** (applied in this order):

| Field | Effect |
|---|---|
| `move` | Moves the ticket to this logical state. |
| `labels` | `{ add: [...], remove: [...] }`: adds / removes Linear labels. |
| `comment` | Posts this text as a comment on the ticket. |
| `do` | `stop`: stops the running run, empties waiting runs and blocks the ticket (« Stopped. Reply on this ticket to relaunch. »). `cleanup`: deletes the ticket's worktree. `propose_delegate`: replies that the ticket must be delegated to Relais for it to develop it. |
| `run` | Launches the job with this name (must exist in `jobs`). If the ticket was blocked, it is unblocked first. |
| `debounce` | With `run`: instead of launching right away, schedules the job after this delay. A new matching event before expiry pushes the delay back: messages close together produce a single run. `0s` = immediate. The delay is a timer in the database, written with the decision, specific to each project: a Relais restart does not lose it. |

A rule with no action is valid: it "consumes" the event without doing anything (and prevents the following rules from applying).

There is no `post` field in a rule: publishing the result is configured in `jobs.*.on_success`.

**Non-delegated ticket.** If the ticket is not delegated to Relais, a rule whose `run` targets a job from the `dev` queue is skipped (except on `ticket.delegated`) and Relais moves on to the next rule. Only jobs from the `questions` queue run on a non-delegated ticket.

### Pack rules

| Event | Rules (in order) |
|---|---|
| `ticket.delegated` | if `state in [todo, dev] && !blocked` → `dev` |
| `status.changed` | from `human_review` to `dev` → `dev-feedback`; to `ai_review` → `review` |
| `session.prompted` | if `blocked` → `dev-feedback` immediately; if `state in [dev, human_review]` → 3-minute grouping with no new message, then `dev-feedback` if no work is in progress (otherwise the end of that work hands the messages over); otherwise, the message stays in `humanInbox` |
| `session.mentioned` | → `ask` |
| `command` | `retiens` → `remember`; `fais-le` → `propose_delegate` |
| `ticket.commented` | if `blocked` → the blocked step, or `dev-feedback` if the block has none (ORC-196, [preset](preset.md#resuming-the-blocked-step-orc-196)) |
| `label.changed` | `agent:stop` → `stop` |
| `session.stopped` | → `stop` |
| `pr.checks_failed` | if `state in [human_review, ai_review] && !blocked` → `fix-ci`, at most `limits.ci_fix_attempts` times in a row, then block |
| `pr.conflicted` | if `state in [dev, human_review, ai_review] && !blocked` → `rebase` ([preset](preset.md#rebase-step-orc-146)), on the same count as `fix-ci`, then block |
| `pr.merged` | → moves to `done`, deletes the worktree, launches `learn` |

## 4. `when` grammar

A condition is a sequence of **atoms** joined by `&&` (all must be true).

| Atom | True when |
|---|---|
| `state == <state>` | The ticket's logical state is `<state>`. |
| `state != <state>` | It is not. |
| `state in [<state>, <state>, …]` | It is one of those. |
| `blocked` | The ticket is blocked (failure, limit, stop, pickup check…). |
| `!blocked` | It is not. |
| `job == <name>` | The job of the `dev` run in progress on the ticket is `<name>`. |

`<state>` is one of the logical states (`todo`, `dev`, `human_review`, `ai_review`, `done`, and `ready` for a workflow that still declares it), never a Linear column name. For an event without a known ticket, the state is `todo` and `blocked` is false.

Valid:

```text
state == dev
state != done && !blocked
state in [human_review, ai_review] && !blocked
blocked
job == review
```

Rejected (`on.<event>[<n>].when: invalid condition: …`):

```text
state == todo || blocked        # || forbidden: write two rules
!(state == done)                # no parentheses, and no ! before an atom other than blocked
!state in [todo]                # no negation of "in": list the other states
state == "In Progress"          # a logical state, not a column name
state == backlog                # unknown logical state
```

To express an "or", write several rules in a row: the first one that matches wins.

## 5. From YAML to action

1. Linear or GitHub sends an event (webhook, or periodic PR polling).
2. If it is a lifecycle event, Relais applies its fixed behavior. Otherwise, it takes the first rule of `on.<event>` that matches.
3. The rule produces commands. For `run: <job>`, it is a "launch a run" command that carries the job's name (or a delay, with `debounce`).
4. The orchestrator then reads `jobs.<job>`:
   - `dev` queue on a non-delegated ticket: refused;
   - `knowledge` job without a knowledge repository: ignored;
   - `dev` queue while a run or checks are in progress on this ticket: the job is put **on hold on the ticket** and launched as soon as the current run is finished. There is only one waiting slot per ticket: a new request replaces the previous one;
   - queue paused or the Claude account's usage limit reached: queued;
   - no free slot in the queue (`parallel_sessions` / `question_sessions`): queued;
   - otherwise: launch.
5. Launch: `pickup` checks if needed, preparation of the workspace (`workspace`), `on_start.move`, choice of session (`session`), prompt construction (`/<skill>`, ticket, `input`), then Claude Code with the job's `model` and `limits`.
6. End of the run: fixed behavior of `run.finished` (checks, `on_success`, or block).

The two queues:
- `dev`: work on the code of a delegated ticket (dev, feedback, CI, review). **Only one `dev` run at a time per ticket.**
- `questions`: answers and memory (`ask`, `learn`, `remember`). They do not block the ticket's development; only one at a time per ticket, the others wait their turn.

## 6. Recipes

Each example below is a complete and valid `.relais/workflow.yml` (a test in the repository loads them all with the pack).

### Increasing parallelism

```yaml
version: 1
limits:
  parallel_sessions: 5
  question_sessions: 3
workspace:
  ports: { base: 4200 }
```

Five simultaneous `dev` runs, on ports 4200 to 4204. Reminder: these two capacities are read from the workflow of the first project in `config.yaml`.

### Adding verification commands

```yaml
version: 1
jobs:
  dev:
    verify: ["npm run lint", "npm run typecheck", "npm test"]
limits:
  verify_attempts: 3
```

`dev-feedback` and `fix-ci` inherit this list. The checks do not apply to `review`, which does not extend `dev`: add a `verify` to it if needed.

### Changing the model for review

```yaml
version: 1
jobs:
  review:
    model: sonnet
    limits: { duration: 30m }
```

### Adding a custom job with its own skill

A read-only security audit, triggered by `@relais audite <details>`:

```yaml
version: 1
jobs:
  audit:
    queue: questions
    model: opus
    workspace: trunk-readonly
    session: new
    skill: "audit-securite"
    input: thread
    limits: { turns: 60, duration: 15m }
    on_success: { post: reply }
on:
  command:
    - { say: retiens, run: remember }
    - { say: "fais-le", do: propose_delegate }
    - { say: audite, run: audit }
```

- The pack's `command` rules are repeated, because declaring `on.command` replaces the pack's whole list.
- The skill must be available to Claude Code in the run's workspace: for example a project skill `.claude/skills/audit-securite/SKILL.md` versioned in the repository (it is then present in the copy of the main branch and in the worktrees). Check that it launches with `claude -p "/audit-securite"` in the repository.
- A new job must define `queue`, `model`, `workspace` and `skill`, or inherit them with `extends`.

### Triggering a job on a label

Launch the AI review by adding the `agent:review` label, then remove that label:

```yaml
version: 1
on:
  label.changed:
    - { label: "agent:stop", do: stop }
    - { label: "agent:review", run: review, labels: { remove: ["agent:review"] } }
```

Relais only creates the `agent:stop` and `Bloqué` labels: create `agent:review` in Linear. `review` is a job from the `dev` queue: it only runs on a delegated ticket.

### Disabling a pack behavior

You cannot delete a job from the pack, but a job that no rule launches never runs. To remove a behavior, redeclare the list of the event concerned without the rule to remove.

No AI review (moving to AI Review no longer launches anything):

```yaml
version: 1
on:
  status.changed:
    - { from: human_review, to: dev, run: dev-feedback }
```

No automatic CI fixing, and no learning after the merge:

```yaml
version: 1
on:
  pr.checks_failed: []
  pr.merged:
    - { move: done, do: cleanup }
```

### Adapting Linear column names

```yaml
version: 1
states:
  dev: "En cours"
  human_review: "Relecture"
```

The other states keep the pack's names. Missing statuses are created in Linear on « Connect Linear ».

### Requiring acceptance criteria

```yaml
version: 1
tracker:
  pickup:
    checks: [has_description, not_started, has_acceptance_criteria]
```

The list replaces the pack's: repeat the checks you want to keep.

### Starting with `intake`

```yaml
version: 1
on:
  ticket.delegated:
    - { when: "state in [todo, dev] && !blocked", run: intake }
```

Delegation then runs `intake` first: size and risk are recorded, and an incomplete ticket gets its questions (`clarify`, ORC-210) instead of starting `dev`. The pickup checks become inputs of that guard ([preset](preset.md#intake-step-and-the-guard-before-in-progress-orc-206)).

## 7. Common errors and validation

Relais validates the file when `relais up` starts and refuses to start if it is invalid; the message names the faulty key. There is no dedicated validation command: restart `relais up`, or run `relais plan` (which also loads the workflows, once Linear is connected). Only the **first** error is shown: fix it and run again.

| Error | Message |
|---|---|
| Unknown key at the root, in `states`, a job, `on_start`, `on_success` or a rule (e.g. a typo) | `<file>: jobs.dev: Unrecognized key: "verfy"` |
| Value not in the list | `<file>: jobs.dev.queue: Invalid option: expected one of "dev"\|"questions"` |
| Limit at 0 or negative | `<file>: limits.parallel_sessions: Too small: expected number to be >0` |
| `version` missing or different from 1 | `<file>: version: Invalid input: expected 1` |
| Unknown event (or `ticket.undelegated`, internal) | `on.ticket.created: unknown event type` |
| `run` to a nonexistent job | `on.label.changed[0].run: unknown job "audit"` |
| Invalid condition | `on.ticket.delegated[0].when: invalid condition: state == todo \|\| blocked` |
| Required field missing in a new job | `jobs.audit.queue: required` |
| `extends` to a nonexistent job | `jobs.<parent>: unknown job` (the message names the missing parent) |
| Circular `extends` | `jobs.a.extends: cycle` |
| Badly written duration | `invalid duration: 1h30m` (no path: look in `duration` and `debounce`) |
| Logical state missing after merge | `states.<state>: required` |

Silent pitfalls (no error):
- **Under `limits`, `limits.per_run`, a job's `limits`, `workspace` and `tracker`, an unknown key is ignored without a message.** `limits: { parallel: 5 }` is accepted and does nothing: double-check the spelling.
- A rule on a lifecycle event (`run.finished`, `verify.*`, `timer.fired`, `pr.opened`, `control.*`) never triggers.
- `from` / `to` on an event other than `status.changed` are ignored; `label` or `say` on the wrong event make the rule inapplicable.
- A `say` with an uppercase letter never matches.
- Declaring `on.<event>` in the project erases the pack's rules for that event: copy over the ones you keep.
- A `move` made by Relais (rule or `on_success`) does not trigger `status.changed` rules: for example, `on_success: { move: ai_review }` does not launch the review.
- Editing the file without restarting `relais up` has no effect.

## 8. No "unlimited" limit

All limits must be strictly positive (except `verify_attempts` and `ci_fix_attempts`, which accept 0: block on the first failure, not lift the limit): there is no `0`, `-1` or `unlimited` value that disables a cap. To lift a limit in practice, set a large value:

```yaml
version: 1
limits:
  per_run: { turns: 1000, duration: 8h }
```

Still, keep reasonable caps: they stop an agent running in a loop, bound the spending on a poorly specified ticket, and free a blocked run's slot for other tickets (a run holds its slot in the queue until the end). A run stopped by a limit is not lost: the ticket is blocked with a message, and a reply in the thread resumes the same session.
