# Idempotence des effets externes

L'exécuteur d'outbox (`src/runtime/outbox.ts`, ORC-150) exécute chaque effet **au moins une fois** : un effet qui a agi puis a été coupé avant d'être réglé (crash, bail perdu) est exécuté de nouveau par la réclamation suivante. Chaque effet externe est donc idempotent : exécuté deux fois, il ne laisse qu'**un seul effet visible**. Cette page est la table d'ORC-162, avec la colonne « comportement en doublon » tranchée par [ORC-138](decisions/ORC-138.md#la-table-didempotence) ; chaque ligne a son test.

## La règle commune

- **La clé est l'id de l'effet**, `ticket:seq:i` (l'id de la ligne d'outbox), suivi de l'id de l'installation : `<ticket:seq:i>@<installation>`, par exemple `REL-1:1:2@3f9c0a1b2d4e`. Elle est stable d'une exécution à l'autre, jamais tirée de l'horloge. L'id de l'installation (12 caractères hexadécimaux) est tiré une fois et gardé dans le store (`meta`, clé `instance-id`) : une autre instance sur le même espace Linear (préproduction, poste de dev), ou celle-ci après une base repartie de zéro, a d'autres clés et ne prend jamais un effet de l'autre pour le sien.
- **Seul un rejeu cherche** : une ligne réclamée pour la première fois (`attempts` = 1) n'a rien pu écrire avant, elle écrit directement ; une ligne réclamée de nouveau (bail perdu, crash, nouvel essai après un échec) cherche d'abord ce que l'exécution précédente a écrit. Le chemin normal ne coûte donc aucun appel de plus à Linear.
- **Un doublon détecté est un succès** (ORC-138, option B3) : l'exécution qui trouve l'effet déjà fait n'écrit rien, et son résultat `effect:<id>` (`effect.done`) porte `deduplicated: true` et, quand l'adaptateur la donne, la référence de l'objet trouvé (`ref` : id du commentaire, de l'activité…). `decide` n'en tire rien, mais le note dans sa trace (`effect <id> deduplicated`), et le démon l'écrit au journal : `effect <id> (<type>) already made (<ref>): not written again`.
- **Un effet « état final »** (labels, statut, lien) n'a rien à chercher : il réécrit le même état, et l'adaptateur n'écrit rien quand l'état y est déjà. L'outbox exécute les effets d'un ticket dans l'ordre de `seq` : un ancien effet rejoué ne passe pas après un plus récent.
- **La seule exception** est le push dont la branche a bougé vers un autre SHA : un conflit, jamais rejoué, rendu à `decide`.

## Ce que Linear permet

- **Commentaires** : `commentCreate` accepte un `id` client (UUID v4) et `comments(filter:)` filtre par `id` et par `body: { contains }`. L'adaptateur écrit les deux clés : le marqueur que le ticket demande, et un id dérivé de l'id de l'effet (sha256, aux bits de version et de variante d'un UUID v4). La recherche prend l'un **ou** l'autre : si Linear ne gardait pas le commentaire HTML dans le corps, l'id suffit.
- **Activités de session** : `agentActivityCreate` accepte aussi un `id` client, mais `AgentActivityFilter` ne filtre pas sur le contenu (seulement `id`, `type`, dates, session) : la clé d'une activité est donc son id, pas un marqueur, qui de plus s'afficherait dans le fil de l'agent.
- **Non vérifié en direct** (le test live du Tracker est en lecture seule) : que Linear accepte un id client sur ces deux créations pour une app (le schéma GraphQL public le décrit : « The identifier in UUID v4 format. If none is provided, the backend will generate one. »), et ce que Linear fait de `<!-- … -->` dans le corps d'un commentaire : le garder caché, le retirer (l'id suffit alors à la recherche) ou l'afficher en texte, ce qui serait visible sous chaque commentaire de l'usine. À vérifier sur un espace de test avant la mise en production ; si le marqueur s'affiche, l'id client suffit et le marqueur est à retirer.

## Ce que GitHub et Docker permettent

- **Check run** : seule une GitHub App peut créer ou modifier un check run (« OAuth apps and authenticated users are not able to create them ») : `ForgeWriter` n'est implémenté que par l'adaptateur GitHub App, pas par `gh`. L'API ne filtre pas sur `external_id` (paramètres : `check_name`, `status`, `filter`, `app_id`), mais le renvoie : la recherche se fait côté usine, sur les check runs du SHA qui portent le nom demandé, page par page (100 par page).
- **PR** : la doc de `POST /pulls` ne dit que « 422 : Validation failed » ; que GitHub refuse une seconde PR ouverte pour la même branche n'est **pas vérifié en direct**. `ensurePr` ne s'y fie pas : après un 422, il relit la PR ouverte, et rejette l'erreur s'il n'y en a pas.
- **Conteneur** (vérifié avec Docker 28.2.2) : une seconde création sous le même nom est refusée (`Conflict. The container name "…" is already in use`), et `docker ps -a --filter label=factory.attempt=<id>` retrouve le conteneur, même seulement créé.

## Limites

- **Bail perdu sous un exécuteur vivant** : deux exécutions peuvent lire « absent » puis écrire chacune (ORC-138). Le doublon reste rare et visible : deux commentaires avec le même marqueur (chez Linear, la seconde création sous le même id client devrait être refusée, non vérifié). Pour l'appel au modèle, rien côté serveur ne l'arrête : un lancement lent qui perd son bail peut être doublé.
- **La marque `effect:<clé>:started`** de l'appel au modèle est locale (`meta`, rangée avec les versions de workflow sur Postgres), une par `start_run`, jamais purgée. Un lancement l'écrit avec l'id de sa tentative **avant** d'écrire la tentative, donc avant que le runner la démarre (ORC-277), puis pose la tentative sur le ticket (`run.started`), puis l'écrit ; elle passe à `1` une fois le départ traité. Au rejeu : marque à `1`, ou tentative nommée écrite, rien n'est relancé ; tentative nommée jamais écrite (crash entre la marque et l'écriture), rien n'a été lancé et le départ est rejoué. Une tentative coupée après `run.started` est l'affaire de `recover()` : le ticket d'un run `dev` est bloqué, que la tentative soit écrite ou non, et le départ rejoué est refusé ; une **question** n'est pas relancée, et l'avis « Reposez la question » est le seul message de l'humain. Reste : un élément de la file `questions` sorti par `drain` puis coupé entre l'écriture de sa tentative et son retrait de la file est ressorti après son bail ; il n'a pas de marque (sa clé, projet, ticket et job, ne distingue pas deux questions successives).
- **Labels rejoués** : le moteur pose l'écho des labels ajoutés avant d'écrire ; un rejeu qui n'écrit rien en pose un pour rien, et un humain qui change ce même label dans la minute qui suit (`ECHO_MS`) est pris pour un écho.
- **Deux démons qui démarrent ensemble sur une base neuve** tirent chacun un id d'installation ; le dernier écrit gagne en base, mais le premier garde le sien en mémoire jusqu'à son redémarrage.
- **Lignes en attente** : Push et PR attendent le Publisher (ORC-125), qui fera pousser et ouvrir la PR par l'usine au lieu de l'agent (`--force-with-lease` est aujourd'hui interdit à l'agent dans `packs/standard/settings.json`) ; Check run attend le premier check publié par l'usine (`factory/review`, ORC-183) ; Conteneur attend le vrai `SandboxProvider` (ORC-204). Ces tickets branchent `ForgeWriter` et le port `SandboxProvider` sans changer la table.
