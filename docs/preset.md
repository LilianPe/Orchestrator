# The `factory/default` preset

The preset describes, in TypeScript, the sequence of a run's steps and the bound on each loop (ORC-187). Since ORC-391 it drives the chain: the end of each job walks the preset's steps (`step.next`) to the job it starts, the move it makes and what it posts ([the chain](#the-chain-orc-391)). What a human's event starts is coded in `decide`, one function per reaction, since ORC-392 ([default reactions](#default-reactions-orc-227-orc-392)). The engine takes its bounds from the preset too, compiled each time the workflow is built (see "What the engine already reads"). The workflow is built in TypeScript, `presetWorkflow()` in `src/presets/workflow.ts`; a repository's `.factory/workflow.yml` is ignored: `factory doctor` says so, and the daemon logs it at each start.

Code: `src/presets/preset.ts` (types and compiler), `src/presets/factory-default.ts` (the definition), `src/presets/workflow.ts` (the workflow the engine runs), `src/presets/runtime-bindings.ts` (how each step runs), `src/core/chain.ts` (the walk).

## Sequence

```
intake → clarify (if the ticket is unclear) → spec_draft → spec_check → spec_review (human gate)
  → tests → red → freeze_tests → build → verify → publish → AI review → human_review (merge gate)
  → merge (after a human moves it to Done) → after_merge
```

After publishing, a single `fix` step serves all loops: `fix → verify_fix → publish → AI review → human_review`. Its skill is `factory:feedback` whatever the cause (ORC-460): a red CI, by its « CI failures » section, an AI review, human feedback, an instruction while the ticket is In Progress (`instruction`) or the answer to a relayed question (`relay`, ORC-375). Only the first three come back by a failure edge, each on its counter; `instruction` and `relay` take no round. A conflict with the default branch takes its own way back: `rebase → verify_rebase → publish_rebase`, with no AI review after it (decided on 14/11: the ticket stays where it was, [below](#rebase-step-orc-146)).

Each step has a type: `spec_check`, `agent_step`, `verify` (modes `red`, `freeze`, `full`; the `red` step says whether its red is measured or blocking, `red: measure` in `factory/default`), `review` (its `lenses`, run one after the other), `fix`, `human_gate` (gate `spec` or `merge`), `publish` (modes `push`, `merge`), `factory_step` (a step the factory runs itself, with no agent: `after_merge`, ORC-197). A step has a follow-up on success (`next`) and, if it can fail, a step back (`onFailure`) that consumes a counter. Every `agent_step` step declares what it writes (`writes`: `nothing`, `spec`, `tests` or `code`): an omission makes compilation fail.

## Bounds

| Loop | Counter | Limit | Beyond |
| -- | -- | -- | -- |
| `spec_check` fails → `spec_draft` | `spec_check` | 1 | Blocked |
| `spec_review` « Modifier » → `spec_draft` | `spec_review` | 3 | Blocked |
| Unverified red → `tests` (blocking mode) | `red` | 2 | Blocked; the agent can also return `spec_impossible` |
| `verify` fails → `build` (or `verify_fix` → `fix`) | `verify` | 3 | Blocked |
| AI review or red CI → `fix` | `review_ci` | 2, a single counter per run | Blocked |
| Conflict with the default branch → `rebase` (ORC-146) | `review_ci`, the same | 2, shared with red CI | Blocked, cause « conflict » |
| Human feedback → `fix` | `human_review` | 3, separate from AI rounds | Blocked ([below](#human-review-feedback-orc-190)) |
| Same command, same failure, diff unchanged | `sameFailure` | 3 | Blocked, cause « boucle » (loop): between two `verify` runs and during the attempt ([stagnation](#attempt-stagnation-orc-136)) |
| Nothing written to the attempt's stream | `silentRun` | 30 min | Blocked ([stagnation](#attempt-stagnation-orc-136)) |

A red CI is the failure of a push: as long as the PR is open, including during the merge gate, it goes to `fix` on the `review_ci` counter (`redCi`, the sole source of this rule). Only the ticket's open PR counts, on a head it has not left behind (ORC-466): a red CI of another PR, of a merged or closed one, or of a head a push since went over (the factory's publication or a human's push, `leftHeads`, until a push puts the branch back on it), starts nothing, counts no round and is traced. A head the ticket never heard of is read: it may be a newer push whose event is late. A red CI journaled before ORC-466 names no head: only its PR is checked. A green CI is checked the same way (ORC-469): another PR's, or a head's left behind, lifts no block of the bound. No reaction relaunches `fix` outside this counter. A merged PR no longer has a step back. The count is the run's: another PR or a human who starts work (a reply, a label, a status change or a delegation that launches a run, blocked or not) starts it over, a green CI does not (ORC-184), or a review that keeps finding would loop between its fix and green CI.

`verify` and `verify_fix` share the `verify` counter, reset when a verification passes: the 3 returns count consecutive failures. The total stays bounded, because the number of passes through `verify` is bounded by the other counters.

## Models, effort, turns, network

| Step | Model | Effort | Max turns | Network |
| -- | -- | -- | -- | -- |
| `intake`, `clarify` | Sonnet | low | 150 | Limited |
| `spec_draft` | Sonnet | high | 150 | Limited |
| `tests` | Sonnet | medium | 150 | Limited |
| `build` | Sonnet | medium | 150 | Limited |
| `fix` | Sonnet | medium | 60 | Limited |
| `rebase` | Sonnet | medium | 60 | Limited |
| `review` | Opus | high | 25 | Claude API |
| `spec_check`, `verify*`, `red`, `freeze_tests` | (factory check) | | | None |
| `after_merge` | (the factory, no agent) | | | |

An attempt of an agent step runs 90 minutes at most (`attempt`, the former `per_run.duration`), whatever it writes; the answer agent, out of the steps, 5. The guard's deterministic checks are the preset's too (`guard.checks`: `has_description`, `not_started`).

The turns of steps the MVP doc does not quantify reuse the old `per_run.turns: 150`. Token caps remain to be calibrated: none by default, and `factory validate` refuses until each agent step has its `per_step_tokens` and the ticket its `per_ticket_tokens` (ORC-216).

A workflow job names its step (`step`, ORC-136): `dev` is `build`, `tests` is `tests`, `dev-feedback` and `fix-ci` are `fix`, `review` and `review-security` are `review`, `rebase` is `rebase` (ORC-146). Loading derives from it the effort, passed to `claude --effort` and recorded in the attempt's labels, and the turns. `factory.yml` can change a step's effort (`claude.effort.per_step`), lower its turns (`budgets.max_turns`) and give it a token cap (`budgets.per_step_tokens`). Like the whole workflow, these values are frozen with the ticket's version: a ticket already started keeps its own.

A token cap counts `input + output + cache_creation` of the attempt's messages, not cache reads. When exceeded, the run stops as on a turn cap: `limit`, and the runner says which cap (`overBudget: tokens | turns`, journaled on `run.finished`): the ticket is Blocked with the kind `budget` and the standard comment (ORC-216). A run stopped at its duration, or one journaled before ORC-216, blocks with the kind `limit` as before. The subscription's usage limit is no overrun: the run waits for the reset (`on_usage_limit: wait`, ORC-340).

The network level is chosen per repository (Limited by default); a step can only tighten it. A step declared above the repository's level makes compilation fail.

### The agent's tools per step (ORC-383)

Each agent step has a list of built-in tools, passed to `claude --tools` and enforced a second time by the pack's `PreToolUse` hook, which refuses any other tool and journals it (rule `tool-not-allowed`, [pack](pack-and-skills.md#pretooluse-hook-and-refusal-log)). The factory's MCP tools (`submit_result`, `kb_search`) are always beside them; the MCP has no `ask` (ORC-400).

| Steps | Default tools |
| -- | -- |
| `intake`, `clarify`, `spec_draft`, `review`, and the answer agent (`ask`, a job out of the preset) | `Read`, `Grep`, `Glob`: read-only, no write tool and no shell |
| `tests`, `build`, `fix`, `rebase` | `Read`, `Grep`, `Glob`, `Edit`, `Write`, `NotebookEdit`, `Bash`, `TodoWrite`, `Skill`: no subagent, no web tool |
| `spec_check`, `verify*`, `red`, `freeze_tests` | none: the factory's own checks, no agent |

`factory.yml` sets a step's list (`tools.per_step`, [configuration](configuration.md#factoryyml-orc-209)), and the repository's `.factory/config.yml` can only restrict it (`tools.per_step`, [repository configuration](repository-configuration.md#keys)): the run gets the tools of both lists. A list never gives a step more than its preset step and its network allow, and a value that would is refused when it is read: no write tool or shell for a read-only step, no `WebFetch` below network `limited` (a repository at `none` included), never `WebSearch`, and no tool the factory does not know (`Task` among them). At the launch, `WebFetch` is also dropped from a run whose network does not reach past the Claude API. Like the rest of the workflow, a step's tools are frozen with the ticket's version. `factory validate` shows each step's tools.

## What the engine already reads

`presetWorkflow` compiles the preset, puts it in the workflow, then carries its bounds over into `limits`, which is frozen with each ticket's workflow version (ORC-149). A ticket therefore keeps the bounds it started with.

| Preset bound | In the workflow | Effect |
| -- | -- | -- |
| `counters.verify` (3) | `limits.verifyAttempts` = 4 | 3 returns to the run after a failed check; the 4th failure blocks |
| `counters.review_ci` (2) | `limits.ciFixAttempts` = 2 | 2 runs per run of the ticket between `fix-ci` on red CI, `rebase` on a conflict (ORC-146) and `fix-review` on a blocking finding of the AI review (ORC-184); the next red CI, conflict or review that still finds blocks |
| `sameFailure` (3) | `limits.repeatedFailures` = 3 | same failure on an unchanged worktree, 3 times in a row: Blocked, cause « Loop » |
| `counters.red` (2) | `jobs.<job>.red.attempts` = 3 | in blocking mode, 2 returns to `tests` after an unverified red; the 3rd blocks. A human retry resets the count to zero |
| `counters.human_review` (3) | `limits.humanReviewRounds` = 3 | 3 rounds of human review feedback (`fix-human`, the fix the merge gate's failure edge sends the run to, ORC-190), apart from `ciFixAttempts`; the 4th feedback blocks |
| `regroup` (3 min) | `preset.regroup`, read by `decide` | the human messages for the agent at work regrouped 3 minutes before the round they start: In Progress (`instruction`) and in Human Review (`humanFeedback`); a reply to a block is not regrouped (ORC-392) |

A repository no longer overrides them: its `.factory/workflow.yml`, where `verify_attempts`, `ci_fix_attempts` and `human_review_rounds` did, is ignored since ORC-388.

## Resuming the blocked step (ORC-196)

A human reply on a Blocked ticket relaunches the step where it got blocked, not `dev-feedback`. The block remembers its job (`blockedJob`, from `ticket.blocked`), which the engine launches instead of the reaction's job, with the reply as input. A run published while the ticket was blocked (ORC-403) hands its next step to the block instead (`nextJob`, ORC-416): the reply starts that step as it would have started, the reply left for the agent in the human inbox, and the repair of a dead letter or the green CI that lifts the red-CI bound starts it too. The reaction to a reply on a blocked ticket (`resumeBlocked`, on `session.prompted` and `ticket.commented`) is still what lets the reply through. ORC-180's classification comes first: an instruction or a question from the ticket's session relaunches, a command (`/status`, `/stop`) relaunches nothing, a question from another thread gets its answer there and does not lift the block. An `@Orchestrator` mention on a blocked, delegated ticket is a reply too, a question or an instruction alike (ORC-415, ORC-426): it resumes the blocked step under the right to relaunch; a command relaunches nothing.

A reply resumes a job, the one of the step that blocked: a step without an agent is not resumed on its own. Hence what resuming can do today:

| Blocked at | A reply relaunches |
| -- | -- |
| `build`, `tests`, `fix`, `review`, `rebase` (end of run, cap, loop, lease, interruption, question, a conflict the rebase stops on) | that step's job: `dev`, `tests`, `dev-feedback`, `review` (its first lens: the review starts over, ORC-183), `rebase`. `fix-ci` goes through `dev-feedback`, same step: it reads its red checks, not a reply. `fix-review` resumes itself on the reply, then goes back through the review (ORC-184) |
| pickup, launch | the job being launched, its checks included |
| `verify`, `verify_fix`, `verify_rebase`, `red` (failure at the cap, loop, failure) | the job the check judges: that is the preset's step back. Not the check alone: `run_verify` needs the agent's output, which `verify.errored` does not carry |
| `publish` refused | `dev-feedback`: it writes, goes through `verify` then `publish` again, and the owed move follows (`owedMove`) |
| dead-letter, dead effect, `stop` | `dev-feedback`, these blocks have no step of their own |

**Not yet**: relaunching a step without an agent (`verify`, `red`, `freeze_tests`, `spec_check`, `publish`, `merge`) on its own, and resuming at the `human_review` gate: this needs an engine that executes the steps (ORC-177). `clarify` does not have a job yet; `after_merge` has none either, the factory carries it out itself without an agent (the reaction to `pr.merged`, ORC-197, [after the merge](#after-the-merge-orc-197)); `intake` and `spec_draft` have one, which the scenarios turn on, a repository no longer since ORC-388 ([intake](#intake-step-and-the-guard-before-in-progress-orc-206), [spec](#spec_draft-spec_check-and-the-spec_review-gate-orc-212)); `spec_check` and `spec_review` are decided at its end and on the gate's commands. A reply to the guard relaunches `intake`. The attempt number follows the counter that led to the block; a step without a counter shows 1/1. A debounce armed before the block keeps its job: its timer starts once the block is lifted (a reply to a block is never regrouped).

## `factory/fantome` (ORC-231)

The preset of the replay of closed tickets, at the Rapide level (`level: rapide`): `factory/default` without `clarify`, without
the spec gate and without anything after the publication. What `clarify` would ask is assumed, written in the spec and counted; the
spec that passes `spec_check` is approved by the preset; a human gate at that level is refused by the compiler. The engine walks
its own steps (`presetWorkflow(fantome)`, ORC-391): delegation runs `intake`, then the spec, the tests and `build`, whose publication
ends the run; at that level nothing moves nor is posted. Code: `src/presets/fantome.ts`; see [the replay of closed tickets](ghost-replay.md).

## `rebase` step (ORC-146)

A conflict of the ticket's PR with its base branch arrives in the inbox as `pr.conflicted` (GitHub webhook, ORC-134). It is the engine that starts the step that handles it; an agent at work on another step never resolves it: the `build`, `feedback` and `review` skills leave the base alone and hand back.

**Start.** The reaction to `pr.conflicted` (`prFailed`): `rebase`, on a ticket In Progress, in AI Review or in Human Review, not blocked, for the ticket's open PR only (another PR's conflict, a merged or closed one's, is only journaled), on a head it has not left behind (ORC-469, `leftHeads`: traced, nothing started). Each start counts on `review_ci` (`ciFixAttempts`), the counter of red CI (I5): the conflict's id carries the head and the base, so GitHub repeating it on the same pair starts nothing more. A rebase already running or waiting starts no second one either, whatever the head: it takes the branch onto the base as it is then. Past the bound, the conflict starts nothing and blocks the ticket, kind `conflict` (a green CI does not lift it, unlike the red-CI bound). On a ticket waiting on its blockers in review, the rebase waits for them, counted or blocked then ([above](#waiting-on-a-blocked-by-ticket-orc-363), ORC-464). A conflict during another step leaves that run alone: the start waits behind it, pending, and runs once that work is out (verified and published).

**The step.** The `rebase` job (agent, skill `factory:rebase`, Sonnet, effort medium, 60 turns, the repository's network) resumes the ticket's session in its worktree, in its sandbox like any dev job. It runs `git rebase origin/<base>` and resolves the ordinary conflicts, then the touched tests, types and lint. It moves nothing and posts nothing. Three cases stop it: `git rebase --abort`, then `submit_result` with `status: blocked`, `reason: conflict` and `conflict`:

| `conflict` | When |
| -- | -- |
| `logic` | the two sides contradict each other |
| `migrations` | two migrations change the same schema |
| `scope` | the resolution goes beyond the ticket's scope |

The ticket is then Blocked, kind `conflict`, with the standard comment (step `rebase`, the case in the reason, the agent's question). A reply relaunches `rebase` with the answer.

**Verify, then publish.** A rebase that ends well goes through `verify_rebase` (the repository's commands and the diff checks, in a fresh clone, like any job that writes code); failed checks send it back with them, bounded by `verify`. Only a green commit goes out (I1). The factory publishes it with `--force-with-lease` (ORC-125): the rebased branch no longer holds what was pushed, so its `publish` effect carries `rewrite`, and the push may replace the head the factory published last (the sha of the ticket's last `publish.done`, read from its journal), and only that head. A human's commit on the branch since is refused (`moved`), as for any publication. The ticket stays where it was (Human Review, AI Review or In Progress). In Human Review, the reviewed commit is no longer the head: a Done then goes back through the AI review, which shows the rebased head, as after any push since the review. Only the rebase step stops on a `conflict`: another step that reports one asks a plain question.

**Not yet**: a conflict created by a push to the default branch, with no event on the PR, waits for the reconciliation (ORC-185); the freeze reads a rebase as a change since the freeze, which needs a `/refreeze` (see the freeze's « not yet »); the rebase's summary is not posted (ORC-214's `OutputPolicy` will compose what a step posts).

## `intake` step and the guard before In Progress (ORC-206)

The `intake` job (agent, skill `factory:intake`, Sonnet, effort low, the repository's network, in the runner like any dev job) reads the ticket, the repository's architecture docs and decisions and the code it touches. It writes nothing and does not move the ticket: since ORC-367 the run itself holds it to that. It runs on a fresh clone of the default branch (workspace `trunk-readonly`, `_trunk/<runId>/`, gone with the run), never in the ticket's worktree, so a ticket found incomplete keeps no worktree made for nothing; and like the AI review's lenses it has the `Read`, `Grep` and `Glob` tools only (`claude --tools`), no write tool and no shell, whatever its skill says. A read-only step of the preset (`readOnly`: `intake`, `clarify`, `spec_draft`; not `after_merge`, which writes no code but keeps its shell) gives its job these tools ([tools per step](#the-agents-tools-per-step-orc-383)), and a job of a read-only step that writes nothing (`intake`, `clarify`) anywhere but a clone of its own (`trunk-readonly`) is refused when the workflow loads. It reads no other ticket (ORC-192): it judges the linked tickets from what the ticket says of them. It hands back, in the `intake` field of `submit_result`:

| Field | Values |
| -- | -- |
| `size` | `xs`, `s`, `m`, `l`, `xl` |
| `risk` | `low`, `medium`, `high` |
| `complete` | whether a developer can build it without asking anything |
| `missing` | the questions to answer: at least one when not complete, at most 3; each `{ question, options }` (2 to 5 hypotheses), or a bare question when the agent sees none (ORC-210) |
| `screen` | whether the ticket changes something a user sees |
| `duplicates` | optional, at most 3: the work in progress elsewhere that does the same, each its link and why ([below](#duplicates-existing-code-and-scope-orc-207)) |
| `reuse` | optional, at most 10: existing code close to the request (`path`, `symbol`, why), given to `build` |
| `scope` | optional: `refuse`, why the ticket is out of scope, and `split`, the sub-tickets proposed (a title and a summary each, at most 5) |

Before the ticket's first run (no Claude session yet), the factory runs the deterministic checks of `tracker.pickup.checks` (`src/core/pickup.ts`) and journals the failed ones with the attempt's end (`pickup` of `run.finished`): they no longer block on their own, they are inputs of the guard.

At its end, `decide` records the assessment in the ticket's state:

- `size`, the last assessment's;
- `risk`, the higher of the ticket's and the proposed one: within a run, the risk never goes down (I4, property in `test/properties/decide.prop.test.ts`);
- `visualProof: required` when the ticket speaks of a screen; never lifted within a run: the model cannot make visual proof `not_applicable`. Deciding it from the real diff is `verify`'s (ORC-176): required too when the diff touches `visual_paths`.

A new run starts again from its own level (ORC-365). A delegation whose decision starts a run, on a ticket already assessed, marks the run's boundary: `risk` and `visualProof` go to `null`, a run not yet assessed, so the new run's intake sets them from what it proposes. A delegation that starts nothing (refused by the matrix, made while a run is active, on a blocked ticket, or one waiting on its blockers) leaves the run as it is. A ticket from before ORC-365 has no boundary marked: it stays in its run and decides as before.

Each later attempt of the ticket carries its risk in its labels (`risk`, ORC-226).

Then the guard before In Progress: a failed deterministic check, a probable duplicate, a ticket out of scope or an incomplete ticket does not start, it goes to `clarify` ([below](#clarify-questions-reminder-and-expiry-orc-210)); nothing moves to In Progress. A complete ticket starts the spec (ORC-395). The guard's deterministic checks and the « blocked by » wait hold before the ticket's first run only: a ticket delegated again, whose ticket session the tests step started (ORC-217), is not checked again, nor is `dev` after `tests`.

`intake` is the preset's entry, and a delegation starts it (ORC-395): its end goes on to `clarify`, then to the spec. The ticket stays in Todo through `intake` and `clarify`, then shows Spec from the spec's start until the build (Todo with `statuses: { spec_draft: off }`, ORC-457): the end that reaches `build` moves it to In Progress. A chain started at `build`, as only tests start it, has no intake before it: `dev`'s pickup checks then block directly, as before.

### Waiting on a blocked-by ticket (ORC-363)

A ticket « blocked by » a Linear ticket that is not done waits instead of starting. Done is a status of Linear's `completed` type; a cancelled blocker delivered nothing and still holds; a deleted one (in Linear's trash), or one the factory's token cannot read, holds nothing. The blockers are read with the ticket (`blockedBy` of the [tracker port](ports/tracker.md)), before its first run, where the pickup checks run:

- **`intake` on**: they are an input of its guard, journaled with its end (`blockedBy` of `run.finished`). A ticket incomplete or failing a check is asked its questions first (`clarify`, below): the human has something to answer; `intake` runs again after the last answer, and the wait comes then. A complete one waits, and what `intake` would start (`dev`) is the start it waits for; what its step posts is posted at once, a move is not made (the start moves the ticket itself).
- **`intake` off** (`factory/default`): the guard lives at the launch of the job with `pickup: true` (`dev`), in the daemon's launch (`launchRun`), after the pickup checks: a failed check still blocks; else, an open blocker makes that very start wait, as it was decided (its input, its restrictions).

The wait is no block: no `Bloqué` label, no blocking comment, nothing to answer. The session gets a thought naming the blockers and their status. `/status` says it. The ticket stays where it is (Todo): nothing moves to In Progress. While it waits, a reply, a move or a debounced reply starts no dev work; a message stays in `humanInbox` for the run that starts later. A delegation again keeps the wait. A stop (a block), an undelegation or a dev run started all the same end it. A ticket blocked while it waits (a block that came another way than a stop, ORC-432) keeps its block when a human answers it: no step could run, and the lift would leave it neither blocked nor at work. The reply stays in `humanInbox`, the ack says the ticket resumes once its blockers are done, and the step it resumes is recorded on the wait (`lift`); the bounds a reply gives back are given back at once. A pending job no settle could start, which a reply or a debounce armed before the block would start at once (ORC-339), waits the same way (ORC-435): it is the wait's `lift`, started as it was set aside, and taken off the ticket, once the blockers are done. A red CI or a conflict while it waits (ORC-464) starts nothing and blocks nothing, at the bound or not: a block would end the wait, and its start would be lost. In AI Review or Human Review, its job (`fix-ci` reading the CI failures, or `rebase`) is the wait's `lift` (`round` says which), made in place of the start once the blockers are done, where its round of `review_ci` is counted; past the bound, the ticket is blocked then instead, as it would have been at once. A green CI of the ticket's PR meanwhile takes the `fix-ci` off the wait, another PR whatever it kept; a red CI leaves a kept conflict, which the same head never raises again. In Progress, a conflict is not kept: the start the ticket waits for comes first, and the head it publishes raises the conflict again. Moved by a human meanwhile out of review, the ticket gets the wait's own start.

**The resume comes from the reconciliation**, every 5 minutes ([Linear](linear.md)): it reads each waiting ticket's relations again and, when none is open (blockers done, or a relation taken off), sends `blockers.done`; `decide` makes the start it waited for (on a blocked ticket a human answered, it lifts the block and makes the step that answer resumed instead; with no answer, the block stays and nothing starts; an answered ticket moved meanwhile out of Todo and In Progress keeps its block, and the session hears nothing resumes), and the session hears it, unless a human moved the ticket meanwhile out of Todo and In Progress: then the wait only ends. Not a webhook: the blocker's move to Done comes on another issue, maybe of a team the factory does not follow, and a relation taken off sends no webhook the factory reads; the reconciliation already reads these tickets each pass, so the wait costs no extra call. The price is up to 5 minutes before the resume. `dev` reads the blockers again at its launch: one reopened meanwhile makes it wait again.

### Duplicates, existing code and scope (ORC-207)

At the launch of `intake`, before its first run, the factory searches for duplicates through the adapters: every open PR of the repository, the most recently updated first, with its first 30 files and their count (the [forge port](ports/forge.md), GraphQL, every page: a list of PRs it cannot read to its end fails the launch, never reads as « no duplicate »), the 100 most recently committed branches but the default one, and the tickets of the team the tracker finds close to the title (`Tracker.search`, its 10 best matches: a ranking, not a list). Then:

- **The ticket's own work** (a `factory/<id>-…` branch, every page of them, named by its open PR when it has one) is a certain duplicate, found without judgement: a failed check, with its link, journaled in `pickup` of `run.finished`. It is the `not_started` check, absorbed into the search: it runs when `pickup.checks` lists it (`factory/default`'s does), at intake's launch or at a `pickup: true` job's without intake. A PR from a fork names a branch of another repository: it is never the ticket's own, and hides no branch.
- **The rest** goes to intake as data, in a « Work in progress elsewhere » section of its prompt: the open PRs with their files (30 per PR), the close tickets, then the recent branches without an open PR, capped at 12,000 characters in that order, what is cut counted. Intake judges which is a probable duplicate (same files or same subject, for the same purpose) and names it in `duplicates`.
- **Existing code**: intake names the functions and modules close to the request in `reuse`. The ticket keeps the last assessment's (`reuse` of its state); `build` gets them in an « Existing code to reuse » section of its prompt.
- **Scope**: a ticket of performance, of architecture or a large refactor is refused in `scope.refuse`, with the sub-tickets intake proposes in `scope.split`. The factory creates none in Linear and starts none.

A probable duplicate and a refusal of scope are inputs of the guard, as a failed check: they go to `clarify` ([below](#clarify-questions-reminder-and-expiry-orc-210)) as one question that names each with its link, or the explanation and the split, and asks the human to confirm or lift them. Never a silent drop: once answered, intake reads the ticket again with the answer.

**Not yet**: creating the proposed sub-tickets in Linear, not delegated (the ticket leaves it open: refusing with the split in a question is its other branch); handing intake's understanding to `build`, after which `factory:build`'s « Understand » section can shrink (ORC-254). Each job runs at its step's network level narrowed by the repository's (ORC-183): `limited` for intake as for the build, `claude-api` for the review.

## `clarify`: questions, reminder and expiry (ORC-210)

`clarify` runs no agent of its own: the questions are `intake`'s (`missing`), the separate intent agent being EVP 1's ([decision](decisions/ORC-210.md)). At the guard, the factory asks at most 3 of them in the ticket's Linear session, one `elicitation` activity each, one at a time (the next once one is answered: Linear sends a picked option back as a plain reply, so the list on screen is the question it answers): with Linear's `select` signal and the question's options when it has some, a free answer always possible (Linear lets the human type instead of picking). A failed deterministic check comes first, as a free question asking to complete the ticket; past 3, the last of intake's are dropped, and intake asks them again on its next pass.

The ticket then waits, **not blocked** (`TicketState.clarify`): nothing moves, the `Blocked` label stays off. Two timers are armed (ORC-161), on the decision's clock:

| After | If questions are still open |
| -- | -- |
| 24 h (`clarify.remind`) | the question on screen is asked again, prefixed « Reminder » |
| 72 h (`clarify.expire`) | the ticket is blocked on `intake` at step `clarify`, cause « question », the open questions in the blocking comment; a reply relaunches `intake` (ORC-196) |

A timer only acts on the round that armed it (`at`): a round answered, asked again, or ended by whatever moves the ticket on (a block, an undelegation, a delegation again, a dev run, a move) does nothing.

**Answers.** A reply in the ticket's session is checked against the matrix (`answer_clarify`: the requester or a team member, ORC-186); refused, it is traced, answered in the session and counts for nothing. Accepted, it is kept in `humanInbox` as any reply (ORC-180) and answers the question on screen, a picked option or free text alike; any other authorized reply in the session counts too (a « +1 » included). A command (`/status`) answers none, nor does a question back (classified `question`): it is answered by `ask`, the question stays. A comment on the ticket is not read while it waits (`ticket.commented` awaits only a block's reply, and the matrix keeps `answer_clarify` to the session): the questions say to answer here. Once every question has its answer, `intake` starts again with the inbox as feedback, reads the ticket again and judges it anew: complete, `dev` starts; otherwise it asks again.

**Decisions.** Each accepted answer, signed (I12), is recorded on the ticket (`decisions`: question, answer, author, time). Every later run of the dev queue but intake (which reads them as its feedback) gets them in its prompt (« Decisions », as data), so the `tests` step writes them as tests; the freeze after `red` and `/refreeze` hold the ticket's decisions as they are then (`frozenTests.decisions`). Nothing clears them yet: a ticket delegated again keeps them.

**Not yet**: resuming intake's Claude session (`--resume`) after the answer: `intake` runs in a session of its own, not the ticket's (ORC-217, ORC-254), so it starts afresh with the answers; the `Questions` step of the session plan stays canceled (ORC-171); a `knowledge.candidate` event per answer (ORC-258); not asking again what was already decided (ORC-254).

## `spec_draft`, `spec_check` and the `spec_review` gate (ORC-212)

The `spec` job (agent, skill `factory:spec-draft`, Sonnet, effort high, the repository's network, in the ticket's worktree, its own session) writes the spec of the ticket and writes nothing else: since ORC-383 the run holds it to that, with `Read`, `Grep` and `Glob` only. It reads no other ticket (ORC-192): it judges the linked tickets from what the ticket says of them. It hands it back in the `spec` field of `submit_result` (`src/core/spec.ts`):

| Section | What it holds |
| -- | -- |
| `goal` | what the ticket delivers |
| `out_of_scope` | what it does not do |
| `criteria` | the acceptance criteria, each a testable example (« Given …, when …, then … »), at least one |
| `properties` | optional « for any input » properties, each with its `statement`, input `domain` and `target`: once approved, each becomes a property test, frozen ([below](#property-tests-orc-261)) |
| `files` | the files the change touches |
| `architecture` | its impact on the architecture |
| `risks` | what could go wrong |
| `assumed` | what is taken as correct without checking it: present even empty |
| `decisions` | the `clarify` answers it applies, by their question (ORC-210) |

Every section is optional to the schema: a missing one is `spec_check`'s verdict, not a refused result. Their sizes are capped like the rest of `submit_result` (ORC-214), the spec as published included.

**`spec_check`**, deterministic, at the end of the job: every section present (an empty list counts), at least one criterion and none empty, each property with its statement, domain and target, and each decision `clarify` recorded on the ticket carried in `decisions` with the answer given (read once `TicketState.decisions` exists, ORC-210). A spec that fails goes back to the job once (counter `spec_check`, `limits.specCheckReturns`), in a session of its own, with what is wrong and the refused draft (« Spec refused by spec_check »); the next failure blocks the ticket on the job, step `spec_check`, cause « failed ». A spec that passes resets the count.

**Publication** (ORC-382, decision ORC-139). A spec that passes is a new version of the ticket's spec (`TicketState.spec`: its job, its number, its content, when), without approval. The factory publishes it in a **comment of the ticket** (« **Spec, version 2** », the sections in a fixed order, then where to reply), through the `OutputPolicy` like every text it publishes; each version is a new comment. Past `spec.threshold` of `factory.yml` (5 000 characters by default) the spec goes to a **Linear document linked to the ticket** (« REL-12: spec, version 2 »), and the comment gives its goal, its criteria count and the document's link (`spec.publish: comment+doc`, the default; `comment` keeps it in the comment whatever its size, `doc` always uses the document; a tracker that keeps no document gets the whole spec in the comment). Then the ticket's Linear session, where the commands are replied, says « Spec published (risk: medium). 3 acceptance criteria → tests. Version 2, waiting for review. », where to read it, and the commands. One outbox effect, `publish_spec`, makes the three writes, each found again on a replay ([idempotency](idempotency.md)). The ticket is not blocked: it waits for the review. It shows Spec ([Linear statuses](#linear-statuses), ORC-457), or stays in Todo when `factory.yml` turns that status off (`statuses: { spec_draft: off }`).

**`spec_review`**, a human gate always at the MVP. Three commands, replied in the ticket's session (a reply, not only after a mention: `webhook.ts` reads them as commands, never as feedback), all three reserved for the project's designated validators and never the run's initiator (matrix row `validate_spec`, ORC-186), checked even on an event without resolved roles. Refused, the command is traced (`authz: refused validate_spec …`) and answered in the session; sent anywhere else (a mention, another session), it is refused as not through this channel; written as a plain comment on the ticket, it is not read (a comment is read only as the reply to a block).

| Command | Effect |
| -- | -- |
| `/approve` (or `/approve <version>`, which must be the version waiting) | records who approved the version and when (`spec.approval`), then passes the gate: the chain goes on to the step after it (`tests` in `factory/default`) |
| `/changes <comment>` | the comment goes into `humanInbox` as an instruction (ORC-180), and the job drafts the next version from it and its last one (« Spec under review »), in a session of its own, never the ticket's; a version is never approved by an earlier approval. Until it is published (`spec.drafting`, a start still in the queue included), nothing is approved, changed or rejected. 3 rounds since the last approval (counter `spec_review`, `limits.specChanges`): the 4th blocks the ticket on the job, step `spec_review`, cause « limit » |
| `/reject` | blocks the ticket on the job, step `spec_review`, cause « stopped »: a reply drafts again |

A command with no spec waiting (none yet, a ticket blocked or undelegated), on a version already approved, or while a new version is being drafted, is answered and changes nothing. A human's reply to a block on the job gives the return and the rounds back.

**The spec changed during the run.** A `/changes` on the approved version: the work on it stops (`work.cancelled`, `stop_run`, a start still in the queue included), the approval goes, and the job drafts the next version, which goes through `spec_check` and waits for a new `/approve`: the run starts again from the review.

**After approval.** Every later step of the ticket's dev queue reads the approved spec in its prompt (« Approved spec »): `tests` writes its criteria as the acceptance tests, the build works within it. The freeze after `red` (ORC-131) keeps the approved criteria with the frozen tests (`frozenTests.criteria`); like its files, a later freeze adds the criteria of a version approved since to those already frozen, and the tests of a changed criterion stay frozen until `/refreeze`, which keeps the criteria approved then. A new delegation clears the ticket's spec: the work starts afresh. A redraft reads its last version (« Spec under review »).

`spec` runs after `intake` and `clarify` (ORC-395): every ticket waits for a designated validator's `/approve` before its tests and its code. A project whose entry in `factory.yml` designates no validator (`authz.validators`, empty by default) approves no spec: its tickets stop at the gate; with a lone validator, the tickets they delegate. `factory doctor` and the daemon's start warn of it (ORC-421).

**Not yet**: the spec as an editable comment (ORC-139), and with it a spec edited by hand; a `knowledge.candidate` event for each `/changes` and `/reject` (ORC-258); the decisions of the scope given to `spec_draft` (ORC-254); « assumed without verification » in the PR description (ORC-195); the spec's critique (out of scope).

## `review` step (ORC-183)

Once `dev`'s commit is published (`build → verify → publish → review`: the move to AI Review, the build's summary, the first lens), the AI review starts: two agent sessions on Opus, effort high, 25 turns, one after the other, each a fresh session of its own (role `reviewer`), never the implementer's. Every job that writes goes back through it the same way: `fix-ci`, `fix-review`, `fix-human`, and `dev-feedback` since ORC-170. When `dev`'s publication is refused and a later job publishes, that end makes the move `dev` owed and starts the review it came with.

| Job | Lens | What it looks at |
| -- | -- | -- |
| `review` | `correctness` | the diff against the ticket, what it breaks elsewhere, the repository's rules, comments that contradict the code |
| `review-security` | `security` | unvalidated input, access, secrets, destructive changes; tests that cannot fail, weakened or missing |

Both flag over-engineering (an abstraction with one user, code outside the ticket). The skill is `factory:review`, built on `factory:code-review`; the prompt names the lens.

**What a lens reads.** A fresh clone of the commit the factory published (`verifiedSha`, the one `verify` found green), made by the factory, detached, under `_trunk/<runId>/` and gone with the run (workspace `published`): never the agent's worktree, nor a head pushed since. Its diff against the trunk is read on the factory's repository before the session starts and given in the prompt, past 60,000 characters the list of changed files instead (`capDiff`). The session has `Read`, `Grep` and `Glob` only (`claude --tools`): no write tool, no shell, no subagent. Its sandbox runs at network `claude-api`: the proxy lets the Claude API through, nothing else, whatever the repository's level. A reply on a ticket blocked on the review relaunches its first lens, which still reads the diff alone.

**What a lens hands back.** Through `submit_result`, a `findings` list (`[]` when it found nothing): `{ file, line, severity: blocking | minor | out_of_scope, explanation, suggestion, fact? }`, at most 50. `fact` is the id of a Claim Ledger fact the finding violates, for when the reviewers get them as a checklist (ORC-254, ORC-229). A lens without a findings list, or a ticket without a published commit, is blocked.

**What the factory publishes.** Each lens's findings are kept in the `findings` table, by ticket, commit and lens, a lens run again on the same commit replacing its own. At the end of `review-security`, the last lens of the step (it posts the review), every lens's findings on that commit go out as one GitHub review on the PR (a comment, it neither approves nor requests changes), each blocking or minor finding a comment on its line, the out-of-scope ones (on code the diff does not change) listed in the review's text; when GitHub cannot place one (a line the diff does not show), all of them are listed there instead, shortened if they would not fit in one text. The texts are vetted together, one secret scan for them all. Then the `factory/review` check on the commit: failed while a blocking finding stands, green otherwise, its title the count (« 1 blocking finding, 2 minor, 0 out of scope »). Every text goes through the `OutputPolicy`: a refused one is replaced by its notice, its place kept. Nothing goes to Linear. Then the move to Human Review, which records the reviewed commit as before. A review that fails to go out is retried by the outbox; a dead one blocks the ticket, and the move waits.

**No human move needed (ORC-170).** A commit `dev-feedback` publishes (a reply in In Progress, or to a block with no step of its own) ends as `fix-human` does, both jobs of `fix`: AI Review, its reply, the review, then Human Review on that commit. Messages that came in meanwhile are handed over at the review's end, in Human Review: a round of `fix-human`.

**Nothing new, no review (ORC-170).** The end of a job that writes and whose step leads to the AI review (`dev`, `dev-feedback`, `fix-ci`, `fix-review`, `fix-human`) starts it only when there is something new to review. With no PR (nothing ever published), or on the commit shown in Human Review, already reviewed (`reviewSha`: an answer that committed nothing), it posts its reply or summary, moves nothing and starts no review: the ticket stays where it is, and messages waiting are handed over as at any end with no step behind it. With no PR and nothing committed either (the publication found no commit beyond the base: a first `dev` that wrote nothing, or an answer before the first commit), and no human feedback waiting for the agent (which the end hands over as usual; a relayed question alone does not count), the ticket would sit with nothing running and nothing to show: it is blocked instead (kind `question`, label Bloqué), on a comment that asks a human what to do, and a reply resumes the work. A block already in place stays as it is. Only in Human Review: out of it (the review loop, or after a human's move, which keeps the reviewed commit), the end is judged again, a `fix-review` that contests without committing included. The lenses chain as before. A push by a human is verified (ORC-159), not reviewed: the AI review reads only what the factory published.

## Human review feedback (ORC-190)

```
human_review (gate) → feedback? [ fix → verify_fix → publish → AI review → human_review ]   ≤ 3 rounds
```

**What starts a round.** In Human Review, a reply in the ticket's session, or a review written on the open PR (`pr.reviewed`, from the GitHub webhook). Nobody moves the ticket: the move from Human Review back to In Progress starts nothing any more. A review must carry words and not be an approval (an approval, or a review with no text, asks for nothing), and its author must have write access to the repository: the matrix checks the GitHub login that signed the webhook (`review_feedback`, `github:<login>`); a refusal is only journaled and logged, never written in the ticket, since a stranger can comment on a public repository's PR. A review whose author was not resolved is not read at all; a preset with no round of human review (`factory/fantome`, no merge gate) only journals reviews. The feedback is kept in `humanInbox`, untrusted for a review (I12), and grouped for 3 minutes like any reply. Out of Human Review a review starts nothing: during other work (a fix running, the AI review) it waits for that work's end, which hands it over (`handOver`), else for the next step's launch. A round armed in Human Review does not start once the ticket left it (moved to Done or back to In Progress). A blocked ticket keeps a review in its inbox; only a reply in Linear relaunches.

**The fix.** `fix-human` (step `fix`, skill `factory:feedback`) resumes the ticket's session in its worktree, on the same branch and PR. Its input is the feedback: the session's messages, the reviews' text, and the PR's unresolved review threads, read from GitHub at the launch (an inline comment is read in its thread, not as the inbox kept it, so a thread resolved meanwhile is not sent). Then `verify_fix`, `publish`, both lenses of the AI review and Human Review again, never straight back. The feedback counts as blocking: the review that follows decides on the new commit, and its own blocking findings take the review loop below.

**Counted.** Each start of `fix-human` is a round (`humanReviewRounds` of the ticket, `limits.humanReviewRounds`), apart from `review_ci`: a relaunch after a cut and a return of `verify_fix` are no new round. With 3 rounds started, the next feedback blocks the ticket (kind `limit`, step `fix`) instead of starting `fix-human`, its feedback kept; a reply relaunches `fix-human` on it and gives the rounds back, as a human relaunch gives every bound back. Another PR starts them over too. A human who writes feedback starts work: the count of `review_ci` starts over with it (ORC-184's rule), so each human round gets the review loop's two rounds again.

## The review → fix loop (ORC-184)

```
loop ≤ 2 [ AI review → fix → verify_fix → publish → AI review ]
```

**Counted.** Each lens's blocking findings are counted on the commit it read (`reviewBlocking` of the ticket). Once `review-security` ends with one standing, of either lens, the review's failure edge starts in place of the move to Human Review: `fix-review` (the `fix` job of cause `review`), one round of `review_ci`, the counter red CI and conflicts use (`ciFixAttempts`). The review is published all the same, `factory/review` red, and the ticket stays in AI Review. Past the bound, nothing starts: the ticket is blocked (kind `limit`, step `fix`), the findings on the PR; a reply resumes `fix-review` on it, which then goes back through the review, and gives the counter back. A red CI during the merge gate uses a round too.

**The fix.** `fix-review` (step `fix`, skill `factory:feedback`, Sonnet, effort medium, 60 turns, the repository's network) resumes the ticket's session in its worktree. Its input (`findings`) is the review's blocking findings, read from the `findings` table on the reviewed commit, each under an id (its lens and its rank, `correctness-1`), then the PR's unresolved review threads as they are, untrusted. One commit per finding fixed, or the finding contested with a justification: its `submit_result` says which of each id, in `fixed` (`{ finding, commit }`) and `contested` (`{ finding, justification }`), and refuses two findings on one commit. Then `verify_fix`, `publish` and both lenses again; `fix-ci` takes the same way back since ORC-184. The review starts at the publication, as after `dev`, without waiting for the CI.

**Contested.** A contested finding stays open: the ticket keeps it (`contested`) with the commit it was found on, and the next review's lenses read it, with its justification, after the diff (« Contested findings »), resolved once for the round: the first lens replacing its findings on a commit reviewed again does not change what the second reads. They judge it again, and report it again unless the justification holds. Once that review has published, the findings standing are its own.

**Not yet.** That each finding fixed is in the commit it names is the agent's word: `verify` does not check the commits against `fixed`. The fix's summary goes to Linear (`post: reply`), not to the PR's threads.

## Attempt stagnation (ORC-136)

The runner watches the attempt's stream. It observes, stops it, and logs what it saw in `run.finished` (`stagnation` field). It is `decide` that blocks, based on this fact and on the frozen version's bound: replay decides the same way, and a journal from before ORC-136, without this field, decides as before.

**Loop.** For each `Bash` call the stream reports as failed (`is_error`), the runner computes a fingerprint: the command, the normalized output (colors, dates, durations, addresses, hashes, pids and temporary paths removed), and the worktree's content. This content is the git tree of the whole worktree, modified and untracked files included, read with a copy of the index: the agent's index does not move. It is read where the agent runs, in its sandbox if it has one. The same command on the same failure `sameFailure.limit` times (3), with no change of content between them: stop, then Blocked, reason « Loop: … », and the command in the block comment. Other commands between two failures do not reset the count. Any content change resets them all, even a return to content already seen. Committing without changing anything does not. A command that waits for an external state (`curl` on a server that is starting up) and fails 3 times the same way counts too. If the content could not be read (no git, more than 30 s), that failure does not count, and the daemon's log says so once per run, with the exit code and the first line of stderr: a disabled detector is visible. Only jobs of the `dev` queue are watched for loops.

**Silence.** Nothing written to the stream for `silentRun.minutes` (30): stop, then Blocked, « The run … has written nothing for 30 min ». The lease does not see it: it only says the container is alive. 30 min exceeds Claude Code's longest `Bash` call (10 min).

A human relaunches as usual, with a reply in the ticket, and the count starts over at zero. An attempt resumed after a restart (`attach`) is only watched for silence, whose delay restarts from the resumption; its loops remain bounded by its turns and its duration.

The guard between two `verify` runs (`repeatedFailure`, ORC-187) stays separate: same job, same commands and exit codes, same tree, without the output.

An attempt whose process stops without a `result` line, without having been stopped or having reached a cap (container killed, memory, process killed), is a failure: `errored`, ticket Blocked, nothing is sent back to the agent.

## `tests` step and `red` check (ORC-123)

The `tests` step (agent, skill `factory:tests`, Sonnet, effort medium, repository network) writes **only** the tests that translate the acceptance criteria, and commits them. The factory does not take its word for it: the `red` check (`src/checks/red.ts`) observes for itself.

1. When the step launches, the factory records the worktree's head (`baseSha`); a return to the step keeps the first one. The check reads the files changed by the step's commits only (`baseSha..HEAD`, on the factory's repository), plus the worktree's uncommitted or untracked files. A file that is not a test (single rule in `src/checks/test-files.ts`, helpers and data under a test folder included) is a scope violation (`scope`), observed without running anything.
2. It runs only the added or modified test files (`*.test.ts`, `test_*.py`…, not helpers or data) with the repository's test command (`commands.test` of its `.factory/config.yml`, ORC-391; with none, the check cannot run: `infra`, which `factory doctor` and `factory init` warn about, ORC-412). A command run by `npm`, `pnpm` or `yarn` without a `--` gets one before the files (ORC-412), except under Yarn Berry (2 and later, by the `packageManager` field of `package.json`, or by a `.yarnrc.yml` when that field names no Yarn), which would pass the `--` on to the script: none is added there, and one the command ends with is dropped (ORC-420). A program pnpm or yarn runs, which no script of `package.json` names (`pnpm vitest run`), gets none either (ORC-420). `git status` and the tests run in a separate sandbox, without network; without sandboxes (the test harness's fake runner alone), the stand-in runs no test (ORC-179).
3. It reads the runner's machine report (ORC-342): the JSON report of vitest (`--reporter=json`) or jest (`--json`), the JUnit report of pytest (`--junitxml`), written to a temporary file and printed after the output behind a random marker. The runner is the one the command names (`npx vitest run`, `python -m pytest`), or the one the `package.json` script runs when the last command of the line goes through `npm`, `pnpm` or `yarn` (`npm test`, ORC-412; under Yarn Berry, without the `--`, ORC-420), as the last command of that script. Only the report's failure messages and the errors of the files that did not load are classified, never a test's name: a passing test called "fails on an AssertionError" changes nothing. Without a known runner, or when the runner wrote no report (it crashed before, the flags went elsewhere), the text output is read as before, a word of a test's name included. It classifies (vitest, jest, pytest), errors before "no tests" (pytest writes `collected 0 items / 1 error` before an import error):

| Output | Cause | Red |
| -- | -- | -- |
| failure on an assertion (`AssertionError`, `expect(received)`, `E assert`) | `assertion` | verified |
| module not found ("Cannot find module", TS2307, `ModuleNotFoundError`) none of whose paths exist at `baseSha`: relative to the test file in TypeScript, in a package of the repository in Python | `missing_module` | verified |
| symbol an existing module does not export (TS2305, "does not provide an export named", `is not a function` for a function imported by the test, `cannot import name`), absent from the module at `baseSha`: not among the exports of its syntax tree in TS and JS (a mention in a comment or a string is not one, ORC-342), not defined, assigned or imported at the top level of a Python module (read line by line: no Python parser) | `missing_export` | verified |
| module not found that exists at `baseSha` | `module_at_base` | refused |
| package not found (bare name in TypeScript, Python package outside the repository): the build does not install any | `missing_package` | refused |
| syntax, type, loading or collection error; missing symbol that already exists at `baseSha` | `compile` | refused |
| failure without an assertion (runtime error), timeout | `error` | refused |
| no test run, or no test committed | `no_tests` | refused |
| tests already green | `passing` | refused |
| non-test file, committed or not | `scope` | refused |
| an approved property without its test, in the file the factory names (ORC-261), observed without running anything | `missing_property` | refused |
| the check could not run (git, worktree, sandbox) | `infra` | no verdict |

The verdict comes back like the result of `verify`: `verify.passed` or `verify.failed`, with the `red` field carrying the cause. A verified red starts the next agent step's job (`build`'s, `dev`, in `factory/default`).

### Property tests (ORC-261)

A spec may carry « for any input » properties (`properties`, [above](#spec_draft-spec_check-and-the-spec_review-gate-orc-212)), optional at the MVP (measure mode): a spec without one goes through as before. Each property the validator approves becomes a property test, which samples its inputs and proves nothing: fast-check in TypeScript or JavaScript, Hypothesis in Python.

- **The file is the factory's.** The `tests` step's prompt (« Property tests », that step's alone) names one file per approved property, in the language of its target, put where the repository keeps its tests: `rel-12.property-1.test.ts` (any `.test` or `.spec` JS or TS extension) or `test_rel_12_property_1.py` for property 1 of REL-12 (`src/checks/properties.ts`).
- **The red check wants it.** An approved property whose file is neither committed by the step nor at its head already (an earlier pass's) is a `missing_property` verdict, observed before anything runs; like any verdict of the check, it is measured or blocking as the job's `red` mode says (measured in `factory/default`).
- **It is frozen with its generators.** The freeze after `red` holds the property tests as it holds every test of the step, and with them every test file of the repository they import, then those import (relative JS and TS imports, `import()`, `require()` and `import x = require()`, not an alias of `tsconfig.json` or `package.json`; Python's relative imports, and its absolute ones looked for from the test's folder up to the root, a name imported from a package also as its submodule, with the `__init__.py` of each package on the way, and of the test's own folder and those above it, which pytest runs first): the generators they draw their inputs from, written in the step or before it. Never the code under test, which is no test file: a generator kept in a file that is no test file (`src/testing/arb.ts`) is not frozen, which is why the step's skill puts them in test files. A commit that changes a frozen generator, or the number of runs written in a frozen test, fails `factory/tests-gelés`, until a maintainer's `/refreeze`.

**Not yet**: `verify` running the properties again with the factory's number of runs (1 000, `numRuns` / `max_examples`) and a seed it draws, written in the check, whatever the repository sets; the defects a property found that the examples did not, as a measure. A property is numbered by its place in the spec: a later approved version that removes or reorders one keeps the old files frozen under the new numbers.

**Measurement mode.** For the first 20 tickets, the check is in measurement mode: it never blocks. An unverified red, a scope violation included, leaves in the decision the trace "red: would have blocked (<cause>), measure mode: the run goes on", and the build starts. The verdicts are in the ticket's measurements (`red` of `TicketMeasures`, ORC-235): a red that is not `verified` is what the check would have blocked.

**Blocking mode.** An unverified red, or a scope violation, makes the step fail: back to `tests` (resumed session, verdict as input), bounded by the `red` counter, then Blocked.

**Failure.** A check that could not run (`infra`) blocks the ticket in both modes, without relaunching the agent: it is not a verdict on its tests. It does not enter the measurements.

The flag lives in the job, frozen with each ticket's workflow version: `jobs.tests.red.mode: measure | blocking` (`measure` by default). Switching it to `blocking`, after validation on the golden tickets (ORC-236), is a change of the factory's workflow (`src/presets/workflow.ts`): a repository's `.factory/workflow.yml` is ignored since ORC-388.

The workflow's `tests` job runs once the spec is approved (ORC-395), then the red check and the freeze, then `build`; `factory/fantome` starts it on its own chain. Jobs without `red` keep the former `dev` flow.

## Freezing the tests and the harness (ORC-131)

After `red`, the factory freezes what judges the agent: the tests the `tests` step committed and the harness that runs them (`src/checks/freeze.ts`). The freeze **blocks from the first ticket**, red measurement mode included: only a return to `tests` in blocking mode postpones it to the next red.

**What is frozen**, read from the factory's repository at the step's final commit, never in the agent's worktree: the step's tests, and anywhere in the repository the harness files: `vitest.config.*`, `jest.config.*` (JSON included), their `setup` and `workspace`, `setupTests.*`, `tsconfig*.json`, `jsconfig.json`, `bunfig.toml`, what `npm test` runs of each `package.json`, `conftest.py`, `pytest.ini`, `.pytest.ini`, `pytest.toml`, `.pytest.toml`, and the section pytest reads in `pyproject.toml` (`[tool.pytest…]`), `tox.ini` (`[pytest]`) and `setup.cfg` (`[tool:pytest]`). And, since ORC-342, the configuration of any tool, by the shape of its name: `<tool>.config.*`, `<tool>.conf.*`, `.<tool>rc*` (`vite.config.ts`, which holds vitest's `test` and the aliases a test imports through, `babel.config.js`, `.swcrc`, `next.config.mjs`, `playwright.config.ts`, `.mocharc.yml`, `.npmrc`…), but those of the tools that change no test (ESLint, Prettier, Stylelint, commitlint, lint-staged, markdownlint, cspell, Tailwind, PostCSS, browserslist, Renovate, husky, nvm) and those under a `src/` folder, the application's own. Each file has its sha256 fingerprint (of its content, or of only the part read by the tests for `package.json` and the three shared files; a `tox.ini` or `setup.cfg` without a pytest section is not frozen). What `npm test` runs of a `package.json`: its `test`, `pretest` and `posttest` scripts, every script they run in turn (`npm run x`, `yarn x`, `run-s x`) with its own `pre` and `post`, and the keys of the test tools (`jest`, `mocha`, `ava`, `babel`, `c8`, `nyc`). A freeze made before ORC-342 keeps the harness and the `package.json` part (its `test` script) it was made with: a deploy blocks no ticket frozen before it on files it did not freeze; a `/refreeze` takes it to the new rules. The freeze of tox's and nox's own sections (`[testenv]`, `noxfile.py`) is not there: the factory runs the job's test command itself, not tox. The freeze (commit and fingerprints) is in the ticket's state (`frozenTests`), set by the journaled event that read it: who and when are in the journal.

**The check.** Once the freeze is set, every run of the ticket in its worktree (`dev`, `dev-feedback`, `fix-ci`; the AI review writes nothing since ORC-183) goes through verification, even without a `verify` command: the factory reads the files changed from the freeze commit up to the branch's head. A frozen file modified or deleted (an added `skip` or `only` is a modification), or an added harness file, makes `factory/tests-gelés` fail: the verification fails, the run starts again with the summary, then the ticket is Blocked at the end of `verify`, without moving to Human Review. The check does not look at the author: a human commit on a frozen test fails the same way. A check that cannot read the branch fails too, and a file of the commit that is unreadable at freeze time makes its reading fail: the freeze never opens on a failure. A second pass through `tests` adds its new tests to the freeze, without touching those already frozen; a harness file added since the first freeze does not enter it and keeps failing.

**`/refreeze`.** The only way out of the freeze: a designated maintainer (ORC-186's matrix) mentions the agent in the ticket with `/refreeze`, or replies `/refreeze` in its session. Before the decision, the factory reads the freeze at the branch's local head, without `fetch` (the already-frozen files and the harness), and journals it with the command; if accepted, it replaces the old one and the reply in the ticket gives the commit; the next verification starts from it. If refused (another role, unsigned actor, or no role resolved), the command is journaled (`authz: refused refreeze …`) and answered in the ticket, and the freeze does not move. Refreezing relaunches nothing: a Blocked ticket is relaunched as usual. On a ticket without a freeze, `/refreeze` does not create one: the reply says there is nothing to refreeze. The one exception is a diff of the verification configuration held for this very `/refreeze` (ORC-198, below): it freezes the harness at the head. The freeze records who refroze it (`frozenTests.refrozenBy`).

**Not yet**: the check published on the PR (ORC-273); the worktree's uncommitted files are not read: a test left uncommitted is not frozen, but since ORC-151, with sandboxes, the `verify` commands do not see them either: they and the freeze read the same commit, in a fresh clone; a trunk change brought in by a `merge` or a `rebase` counts as a change since the freeze, and requires a `/refreeze`; only setups and fixtures named like the harness are frozen, an existing `test/setup.ts` is frozen only if the step changed it; `/refreeze` from a PR comment; the `freezes` table separate from the journal; the scan for disabled tests outside frozen files remains that of `anti-triche` (ORC-158).

## The class of the diff and the review label (ORC-198)

**The class.** `verify` classifies the diff of the commit it checks against the default branch, on the same reads as the path rules (in the fresh clone, or, under the test harness's fake runner without sandboxes, on the factory's repository), and journals it in `verify.passed` (`diffClass`: the class and at most 20 of the paths that made it so); the ticket keeps it with `verifiedSha`. A commit found green again keeps the class read of it before. The classes, lowest to highest; a diff takes the highest it touches:

- `normal`: the rest;
- `sensitive`: a path of the repository's `sensitive_paths` (`.factory/config.yml`, read on the default branch);
- `verification-config`: what verifies the work, the frozen harness of the freeze above (a shared file such as `package.json` only when the part the tests read changed), `.factory/**` and `.github/workflows/**`. The last two are forbidden paths too, so a branch that touches them is refused by `factory/chemins-interdits` anyway.

**Approvers per class.** The preset declares them (`approvers`), as the authz actions their approval takes, whose roles are ORC-186's matrix: `done_merge` (Done by a human with merge rights) for every class, which `compilePreset` requires, so the factory never merges on its own; `verification-config` also takes `refreeze` (a designated maintainer). Such a diff is held **before publication**: the ticket is blocked, nothing is pushed, and the block names the paths and `/refreeze`. The maintainer reviews it and sends `/refreeze`, which freezes the harness as it is at the head (it opens a freeze on a ticket that had none); a reply in the thread relaunches, and the commit goes out, since `factory/tests-gelés` holds the harness as approved: changed again, it fails. A freeze made by the factory after `red`, not by a `/refreeze`, approves nothing. A verdict journaled before ORC-198 has no class and is published as before.

**The label.** When the ticket moves to Human Review, the factory labels its PR, one label of the group at a time (`setExclusiveLabel`: the others of the group taken off, the PR's other labels left alone, nothing written when it is already in place):

- `revue: requise`: a `sensitive` or `verification-config` diff, blocking findings of the AI review on the commit shown (`blockingFindings`), or a class unknown (none journaled, or read of another commit);
- `revue: échantillon`: of the rest, a deterministic 10 % draw on the ticket's id (sha256);
- `revue: auto`: the rest.

At the MVP the label changes nothing of the path: **every PR goes through Human Review**, whatever its label, and only a human's Done merges. No auto-merge in any form. Best effort, as the move out of draft: a label the forge refuses is logged.

**Not yet**: the active control plan (CUSUM, review-level switches, sampling that acts on the label) is out of scope; the classes and their approvers were decided by the coordinator for ORC-198 (see its PR), the MVP doc leaving them open.

## The `factory/anti-triche` check (ORC-158, ORC-342)

On each `verify` with sandboxes, in the clone, on what the branch changed since it left the base (`src/checks/anti-cheat.ts`). The diff is read with full context, so each changed file is whole in it, before and after. A finding is something on a line the diff adds; each finding blocks.

- **The four forms**: a test disabled (`skip`, `only`, `todo`, `xit`, `fit`, the runner's ignore lists), a check bypassed (checker directives, an assertion on constants, a success exit), code that behaves differently under test (`NODE_ENV` compared to `test`, the runners' variables). JS and TS files, the scripts of Vue, Svelte and Astro components included, are read on their syntax tree (ORC-342): an alias (`const later = it.skip`, `import { test as check } from 'vitest'`, `const { exit } = process`), another syntax (`it['skip']`, `test(name, { skip: true }, fn)`, a test context's `skip()`, `switch (process.env.NODE_ENV) { case 'test': }`, `['test'].includes(import.meta.env.MODE)`) or a constant spelled in parts (`'te' + 'st'`, a `const` bound to it) reads as the plain form. `expect(c)` on a constant counts only when its matcher compares with constants too (`expect(1).toBe(1)`, not `expect(1).toBe(count())`). Aliases are read in the file, by name, without scopes nor other files. Python and the other files are read line by line, with patterns, as before: there is no Python parser in the daemon.
- **A test removed or renamed**: the set of tests of each test file (`*.test.ts`, `test_*.py`…) before and after the diff. JS and TS tests by name under their suites (`scores > rounds`, a title that is not a constant by its source), Python ones by function under their classes (`TestScores::test_rounds`, read by indentation). A test file deleted or renamed removes all its tests; a case renamed, or moved under another `describe`, removes its old name. Each is a finding, unless a commit of the branch justifies the file with a `Removed-test: <path>: <reason>` trailer, which the summary sent to the agent recalls; a frozen test changed is already refused by the freeze. A helper or a fixture is not a test file.

## The chain (ORC-391)

The end of a job walks its step's `next` past the steps the engine runs itself around a run (the checks, `spec_check`, the publication of a push) to the next step that waits (`src/core/chain.ts`):

- an agent step: its job starts (the first lens of a review; a `fix` starts only by its cause, on a failure edge);
- a human gate, the merge, or the end of the run (`next: null`): nothing starts.

The ticket moves to the status of the step reached (the preset's `statuses`, to the Linear name `states` gives it, [Linear statuses](#linear-statuses): by default `build` In Progress, `review` AI Review, `human_review` Human Review); the chain's entry moves it at its own launch instead, wherever it starts from. What is posted comes from the step that ended (the preset's `posts`): the build's summary, a fix's reply, the review (by its last lens). A review lens hands over to the next lens of its step. A relayed answer ends where it is (ORC-375). At the Rapide level nothing moves nor is posted. `/approve` passes the spec gate: the walk goes on from it.

The chain's entry is the preset's, `intake` (ORC-395); only tests start a chain later, at `build`. The entry moves the ticket at its launch to its step's status, which `intake` has none of: the ticket shows In Progress from the end that reaches `build` on. The review's fix (`fix-review`) is the fix of the review step's failure edge; a round of human review (`fix-human`) is the fix of the merge gate's.

Every workflow carries its preset since ORC-393: a ticket frozen on a version from before ORC-391, whose jobs chained by their own `onSuccess`, is refused ([frozen versions](#frozen-versions-orc-393)).

## The workflow the engine runs (ORC-389)

The workflow carries the preset and the **jobs** that run its agent steps; what a human's event does is coded in `decide` since ORC-392 ([reactions](#reactions)). `presetWorkflow()` (`src/presets/workflow.ts`) builds it in TypeScript: the jobs come from the runtime bindings (`src/presets/runtime-bindings.ts`: queue, workspace, session, input, structured output, cause or lens, outside the `Preset` type), each job's skill, effort, turns, network, tools, attempt duration and red mode from its step, and `factory.yml`'s step settings apply. The YAML pack (`packs/standard/workflow.yml`), its loader and `docs/workflow.md` are gone since ORC-389; a repository's `.factory/workflow.yml` is ignored since ORC-388. Tests vary the workflow in TypeScript (`workflowWith`, [tests](tests.md)), and `factory replay --what-if <preset>` replays journals on a compiled preset ([CLI](cli.md)).

The values of `input`:
- `feedback`: the Linear thread messages accumulated since the last run, plus the PR's unresolved review comments (title « Feedback to address »).
- `ci_failures`: what the factory read on the forge of the PR's red CI, its run having no token (ORC-459, title « CI failures »): each failed check of the head (the factory's own left out) with its conclusion, the end of its log for the first five (an Actions job's log, else the report its CI attached, or a commit status's description; else why there is none), then the CI of the base branch on the commit the PR is compared with (passing, failing and which checks, running, none). A log is data, said so in the block: fenced so it cannot close its block, without colours, timestamps nor control characters, the secret shapes and the daemon's secret values masked, cut to its end (3,000 characters, the error lines before it kept); a run that reads it is marked as one that read untrusted content (`sensitive_paths`, ORC-338). Without a PR known to the ticket, or when the forge refuses the read for good, one line says the factory could not read it and the fix runs all the same; a transient refusal retries the start.
- `thread`: the text of the message that triggered the run (mention or command) (title « Message »). Empty if the event is not a message.
- `verify_failures`: used by the factory itself when it relaunches a job after failed checks (title « Failed checks »); no need to configure it.

The checks (`verify`): with sandboxes (`FACTORY_CONTAINER_CLI`), the factory pins the branch's last commit, exports it with `git bundle` to a fresh clone, and runs each command in a fresh container with network `none` (`bash -c`, 15 minutes maximum per command), **all of them** even if one fails. What is not committed is not checked. There is no `verify` on the host: without sandboxes (the test harness's fake runner alone), the checks run nothing (ORC-179). The same commit already found green is not rechecked. On top of these come, as blocking, `factory/chemins-interdits`, `factory/secrets` (gitleaks, on the commits added to the base branch), `factory/tests-gelés`, `factory/taille-du-diff` (the diff since the base against `max_diff` of the base's `.factory/config.yml`, ORC-333; with `max_diff: off` in `factory.yml`, only the bounds that file sets, ORC-381), `factory/dependances` (ORC-371: each package the branch adds to its manifests, npm and PyPI, must exist in its registry and be on `dependencies.allow` of the base's `.factory/config.yml`; the registries asked by the daemon through the egress proxy, never from a sandbox, see [`repository-configuration.md`](repository-configuration.md#dependencies)) and `factory/semgrep` (ORC-333: the runner image's Semgrep, in a sandbox at network `none` before any code of the agent runs, with the factory's security rules and the repository's own, on the lines the branch adds; a `nosemgrep` comment or a `.semgrepignore` of the branch is not read, see [`repository-configuration.md`](repository-configuration.md#semgrep-rules)). Once the commands have run comes `factory/qualité-diff` (ORC-280), a measure that never blocks: crapper's CRAP scores and dryer's near copies on what the diff changes, see [`repository-configuration.md`](repository-configuration.md#diff-quality-factoryqualité-diff).
**Flaky tests** (ORC-164). When a command runs vitest, jest or pytest (named in it, or in the `package.json` script it runs through `npm`, `pnpm` or `yarn`, with the `--` the red check adds, ORC-420), `verify` asks the runner for its machine report (vitest and jest JSON, pytest JUnit as `xunit1`) and names the failing tests from it. The failing tests are rerun once, together, with the repository's own command, in the same sandbox (at most 20 per command); the first five that count are also rerun on the base commit, checked out before any code of the agent runs and set up in a sandbox of their own at network `none`. Every attempt is journaled with the verdict (`verify.passed.flaky`, `verify.failed.flaky`: outcome, duration, output). The agent reads, under the command's output, what the reruns found: passed on its rerun (flaky on this commit), failing on the base too (not caused by this ticket). These still count: only a test listed in the repository's known flaky tests is **indicative**, and does not count. A command whose failing tests are all indicative runs once more without them, and passes only if that run passes: the report is written by the agent's code, and an exit can have a cause no test carries (a coverage threshold, an unhandled error). A human lists them with [`factory flaky`](cli.md#factory-flaky-project-orc-164); there is no automatic rule. A test frozen for the ticket (ORC-131) is never indicative unless its entry records a human's decision that it may be while frozen (`--frozen`). A command without a known runner, a timeout, or a report that does not load (a file that does not compile) reruns nothing. Only with sandboxes: the fake runner's stand-in reruns nothing and reads no known flaky test.

- All pass: the job's end applies ([the chain](#the-chain-orc-391)).
- One fails and attempts remain: the factory relaunches **the same job**, resuming the session, with the output of the failing commands, trimmed to its beginning, its end and its error lines (8,000 characters at most).
- After `limits.verifyAttempts` failed passes: the ticket is blocked and the factory posts the list of failing commands in the session.
- The check cannot run (engine down, silent sandbox, failing `setup`, unreachable forge or package registry): `verify.errored`, the ticket is blocked for infrastructure reasons, without sending anything back to the agent or touching the counter. When it refused the repository's `.factory/config.yml` (a rejected file, a `services` entry no backend provides (ORC-282), a `setup` that declares `setup_secrets`, which `verify` does not run on a commit nobody reviewed (ORC-461)), the event says so (`repoConfig`) and the ticket is blocked as the repository's to fix (kind `repo_config`, ORC-493), its reason `Repository configuration to fix: …` naming the service or the secrets and what to change; on a human's push, the block stays the push's (`human_push`), with that reason.
- The visual proof (ORC-176), on a job that writes the commit, once its commands pass; see below.
- Same failure three times in a row (same failing commands, same exit codes, unchanged commit content): the ticket is blocked with the cause « Loop », even if passes remain. The worktree's fingerprint is the git tree of its content, untracked files included, computed without touching its index or its objects (60 s at most), with no hook or fsmonitor of the repository's config and none of the daemon's credentials in the environment of a filter it declares (ORC-319). Files written by the checks must be ignored by git (`coverage/`, reports): otherwise the fingerprint changes on every pass and the guard never triggers, without ever blocking wrongly. The count resets to zero on a green check or a human relaunch. Outside a git repository, this guard does not apply. A fingerprint that cannot be read disables the guard for that failure, and the daemon's log says so (`verify of <ticket>: unreadable worktree fingerprint: …`). Its bound comes from the preset.

**The visual proof** (ORC-176, check `factory/preuve-visuelle`). `verify` decides it on the real diff and journals it with its verdict (`verify.passed.visualProof`): `required` when the diff touches a path of `visual_paths` (`.factory/config.yml` of the base branch, the paths that trigger it named) or when `intake` asked for it (a ticket that speaks of a screen, ORC-206), `not_applicable` otherwise. Nothing the agent submits enters the decision: a model's `not_applicable` is ignored. Required, the factory takes it itself, never the agent: the base's files are checked out from the clone before any code of the agent runs; then, in a sandbox of its own at network `none`, with a browser and nothing mounted, it starts the application (the base's `preview` in `.factory/config.yml`, ORC-397, otherwise the recipe learned in the knowledge base, see below) and shoots the page of `visual_scenario.url` from `submit_result` (a path of the application, `/` otherwise; its `steps` are not played) at three widths (1280, 768, 375 px), on the commit, then, set up as the commit was, on the base. Each capture passes the `OutputPolicy` (ORC-214) and is kept by its sha256 under the factory's artifacts dir (`<artifactsDir>/<ticket>/`), which no run mounts, with its row in `artifacts`. Back to the job, with the `verify` counter: an application that does not start on the commit, a console error or an uncaught exception on its page, a capture the policy refuses, captures identical to the base's at every width. What is no fault of the branch leaves the proof unavailable and its check neutral, indicative until the application starts reliably in the sandbox (ORC-152): no browser in the sandboxes (an instance without the capture image of `docker/browser.Dockerfile`, `FACTORY_BROWSER_IMAGE`, ORC-404: the daemon says at its start whether it has one, `factory doctor` too), no `preview`, a base that does not start. The check, published on the commit: the captures by hash, or « No visual proof applicable. ». Not there yet: a human command that forces the decision, and the captures shown in the PR (ORC-195, ORC-197).

**The start recipe learned in the knowledge base** (ORC-386). With nothing declared, `verify` starts the application by the recipe the knowledge base holds for the repository, `notes/preview/<owner>/<repo>.md` (the name read from its origin URL, else the project's id). Without one, and when the repository declares no `services` (the captures run without them), the `build` step's prompt asks the agent to find it, besides the ticket and within 10 minutes and 3 tries: it reads the repository, tries in its sandbox, and hands back `submit_result`'s `preview` (`setup` steps run without network, then `command`, on `PORT`). `verify` never guesses: once the commands pass, the factory starts that recipe itself. When the proof is required, the captures are its probe: started on the commit, it answered. Otherwise the factory starts it in a sandbox of its own at network `none`, nothing mounted, in the image the captures use, and asks `GET /` on `PORT` from bash for 60 s, so that the next ticket has it. Only a recipe that answered is recorded, by the factory's narrow writer, never by the agent nor by `learn` and `remember`, which still sleep (ORC-193): the note is shaped as a Claim Ledger `command` fact (ORC-239: command, setup, validating SHA and port, date, ticket), passes the `OutputPolicy`, and is written beside the verdict, never delaying it: the clone pulled first (a clone off its default branch is not written to), the note written only if it is still as the ticket read it before its check, committed as `<product name> factory` with a message naming the ticket, and pushed; a refused push is logged and its commit undone in the clone (the recipe has served this check). A recipe, learned or found, that starts the application neither on the commit nor on the base is a bad recipe, no fault of the branch (one the base still starts with is the branch's to fix, as a declared start): the proof is unavailable; a learned one and the note is rewritten `status: invalid`; the next `build` searches once more, and a recipe of that search invalidated in turn, or that search finding none, owes no other: the proof stays unavailable until a human declares `preview` or deletes the note. A search that finds nothing is noted too (ORC-406): `status: not_found`, the number of such searches and the fingerprint of the files that decide how the application starts on the default branch (package.json's scripts, the Makefile, pyproject.toml's scripts and entry points, the compose files; no lockfile, since a dependency bump does not change how it starts), read at the `build` launch. After 3, no search is asked while that fingerprint holds, and the proof is unavailable saying why; a changed fingerprint counts again from one, and a declared `preview` sets the count back to zero. A note that does not parse is never written over. A replayed ticket (ORC-376) reads the knowledge base at its start, never searches and never writes. The proof says where its start command came from, `declared`, `learned`, `found` (by the agent on this ticket, and probed) or `none`, on its check and in the PR's Evidence. Dormant on an instance without the capture image (ORC-404): the search is asked only where a proof can be taken.

### Linear statuses

The **logical states** and the Linear status each one names (`states`), ORC-170's and Spec (ORC-457) by default:

| Logical state | Linear status | Step that shows it (`statuses` of the preset) |
|---|---|---|
| `todo` | `Todo` | `intake` (set by a human, never by the factory) |
| `spec` | `Spec`, none with `statuses: { spec_draft: off }` | `spec_draft` |
| `dev` | `In Progress` | `build` |
| `ai_review` | `AI Review` | `review` |
| `human_review` | `Human Review` | `human_review` |
| `done` | `Done` | none: a human's merge decision |

**The step → status table** (ORC-382) is part of the preset, frozen with its version (decided 15/11), as is the step → post table (`posts`: the build's summary, a fix's reply, the review). The ticket moves to a step's status when the chain reaches that step (the chain's entry at its launch); a step with no status, such as `tests`, leaves the ticket where it is. **`statuses` in `factory.yml`** gives the Linear name of each step's status, by step: `statuses: { spec_draft: Drafting, build: Doing }` renames the « Spec » status, shown while the spec is drafted and reviewed, and In Progress; `spec_draft: off` turns the Spec status off, the ticket staying in Todo until `build` (ORC-457), and is refused for any other step. The daemon refuses to start on a step the preset does not have, a step with no status of its own, two steps of one status named differently, or one Linear name for two logical states. Whether the Linear team has the statuses is not known at load: `factory doctor` reads the team and warns of a missing one; « Connect Linear » creates the missing ones; the daemon's start, once Linear is connected, creates Spec only (ORC-457), its log saying what it created, and warns of the other missing ones. A repository's `.factory/config.yml` cannot rename them (ORC-388).

The `ready` state is gone (ORC-170). `cancelled` has no name: it is read on the Linear type *Canceled* ([`linear.md`](linear.md#5-states-columns-and-labels)). No other state name is accepted. During « Connect Linear », the factory creates the missing statuses in the team. A Linear status that is not mapped to any logical state is seen as "unknown": a move to it produces a `status.changed` with an empty `to`, which no reaction acts on.

### Pickup checks

The pickup checks, `tracker.pickup.checks` (`has_description` and `not_started` in `factory/default`), made before the **first** run of a job with `pickup` (`dev`):
- `has_description`: the ticket description is at least 30 characters long.
- `not_started`: no branch of the ticket's already exists on the forge (its name under the repository's naming, any type, or the legacy `factory/<ticket-id>-…`, ORC-283) (read through the forge port, every page, ORC-207). With `intake` on, its duplicate search makes this check at its launch, whatever the list says, and names the branch's open PR when it has one.
- `has_acceptance_criteria`: the description holds acceptance criteria, however they are written (ORC-353): the words « critères d'acceptation » (or « critère d'acceptation », « criteres… ») or "acceptance criteria", case-insensitively; or a section of its own with something in it, under a heading such as « Definition of done », « Expected behavior », « Résultat attendu », « Acceptance tests »; or an example « Given … then » / « Étant donné … alors », on one line or the lines of its list item (a Gherkin `Scenario:` included); or a checklist (`- [ ]`). No model reads it: whether the criteria are enough is `intake`'s judgement (`complete`), when it runs. `factory/default` does not list it (ORC-395 will settle where it goes).

If a check fails, the ticket is blocked and the factory says so in its block comment, with the failed checks (« Can you fix this, then reply here? »); under `intake`, they are a question of its guard instead (ORC-206).

### Limits

`limits.perRun` (150 turns, 90 minutes) is the limit of a job without limits of its own; a job of a step never exceeds its step's turns.

What happens when a run hits a limit (`limit`) or fails?
- Job in the `dev` queue: the ticket is **blocked** and the factory says so in the ticket's block comment (« The run <job> reached a limit (turns, duration or budget). », or « … failed. »; an attempt stopped at its token or turn cap says « The run <job> spent its token budget … » or « … its turn budget (max_turns of its step). », kind `budget`, ORC-216). A reply in the ticket relaunches that job, or `dev-feedback` if the block has none (`resumeBlocked`, [resuming the blocked step](#resuming-the-blocked-step-orc-196)).
- Job in the `questions` queue: the factory replies « I could not finish (failure or limit reached). ».

What happens when CI stays red or the AI review keeps finding (`ciFixAttempts`)?
- One count per run for the review and CI loop (ORC-184). Each red CI that starts a run (`fix-ci`), each conflict (`rebase`), and each end of the AI review with a blocking finding standing (the fix on the review's failure edge, started by the lens that publishes: `fix-review` in `factory/default`) counts that run against the ticket, the merge gate included. Once `ciFixAttempts` runs have been launched, the next one starts nothing: the ticket is **blocked** and the factory says so in the block comment (« CI still failing after 2 attempts of fix-ci. », plus the failing checks; « The AI review still has 1 blocking finding on <sha>, and the review and CI loop has used its 2 runs: I am not starting fix-review. »). Subsequent red CIs relaunch nothing and do not repeat the message.
- The count resets to zero when another PR is detected for the ticket (`pr.opened` with another number), or when a human starts work on the ticket, blocked or not (reply in the ticket, status change or delegation that launches a run). A green CI does not reset it (it did before ORC-184): a review that keeps finding would loop between its fix and green CI. It still lifts the block of the red-CI bound. Neither a new push by the agent (that is the loop itself) nor a `debounce` timer armed before the block resets it.
- A round of human review feedback (`fix-human`, ORC-190) does not count here: it has its own count, `humanReviewRounds`. A human who writes feedback starts work, so the count of the review and CI loop starts over with it.
- Unlike `verifyAttempts`, which counts passes (including the first run), `ciFixAttempts` counts relaunches: with `2`, two `fix-ci` runs, then a block on the third red CI. This is the unit of invariant I5 ([`decisions/ORC-138.md`](decisions/ORC-138.md), point 8), checked as a property on the three sources of the loop (`test/properties/decide.prop.test.ts`).

What happens when human review keeps sending the PR back (`humanReviewRounds`)?
- Each start of the fix the merge gate's failure edge sends the run to (`fix-human` in `factory/default`) is a round of human feedback (ORC-190): a review written on the PR or a reply in the ticket's session while it is in Human Review, after the 3-minute grouping, or what waited for the end of other work. A relaunch after a cut, and the returns of `verify`, are no new round. Once `humanReviewRounds` rounds have started, the next feedback starts nothing: the ticket is **blocked** (« The 3 rounds of human review feedback are used: I am not starting fix-human on the new feedback. »), the feedback kept in `humanInbox`.
- A reply in the ticket relaunches `fix-human` on that feedback, and gives the rounds back, as a human relaunch gives every bound back. Another PR starts the count over too.

Durations: a number (milliseconds) or a `<integer><unit>` text with the unit `ms`, `s`, `m` or `h` (`90m`, `30s`, `2h`). Combinations such as `1h30m` are rejected: write `90m`.

There is no budget in dollars (ORC-216): Budgets count tokens and turns: `budgets` of `factory.yml` ([`configuration.md`](configuration.md)).

> Queue capacities are global to the instance and set outside the workflow (ORC-390): `concurrency` of `factory.yml` for the `dev` queue (3 by default), a fixed 2 for the `questions` queue. The sandbox of a check (`verify`, `red`) takes a `dev` slot too, and waits for a free one before any new launch (ORC-353). Beyond that, runs wait in a persistent queue. Each run in the `dev` queue receives `PORT = workspace.portBase + slot number` (4200) (0 to `concurrency - 1`). The other limits are specific to each project.

### The relayed answer (`relayJob`)

The job a question relayed to the agent that implements starts (ORC-375), when nothing runs on the ticket and no human feedback waits beside the question, in place of the job the reply's reaction starts (`replyReaction`); nothing starts where that reaction would start none. The workflow names `answer-relayed`. It is the `fix` job of cause `relay`: the `dev` queue, the ticket session resumed (`session: resume`), the `feedback` input, no counter. Its end moves, posts and reviews nothing, without checks; if the run moved the head of the worktree since its launch (a commit), that commit goes the way of the reply's job instead: `verify`, publication, then that job's end (in Human Review, `fix-human`'s: AI Review and both lenses again), as no round of human review. Where the reply's reaction starts no job by the end of the run (a human moved the ticket meanwhile), the commit stays unpublished in the worktree until the next job that publishes. Every workflow has it, but one at the Rapide level (`factory/fantome`, no `fix` step), where nobody asks (`workflowViolations`).

### Reactions

What an event starts or does, once its built-in behaviour has decided it, is coded in `decide` (ORC-392): one function per reaction, listed in [default reactions](#default-reactions-orc-227-orc-392), read on the ticket as the event leaves it. The `on` rules of the former pack, their fields and their `when` conditions are gone, and a repository adds none. An event no reaction answers does nothing more (its trace says `no rule for <event>`, the name the journals recorded), except a reply in the ticket's dev session, which is always kept (see `session.prompted`).

#### Events a human or the PR sends

| Event | When | Specifics |
|---|---|---|
| `ticket.delegated` | The ticket is delegated to the factory in Linear. | — |
| `ticket.commented` | A workspace user comments on a blocked ticket, outside a session (ORC-196). | A reply to the block comment: checked against the matrix, kept for the run, which launches the blocked step (`resumeBlocked`). |

| `session.mentioned` | `@Orchestrator …` in a comment, when the first word is not a command. | The answer agent (`askQuestion`); an instruction goes to the agent that implements (`replyReaction`). |
| `session.prompted` | Reply in one of the factory's Linear sessions. | The accepted message always enters `humanInbox`, whether a reaction starts a job or not: in Todo, AI Review or Done, it waits for the next run of the implementing agent. The reply's reaction (`replyReaction`) receives an instruction from any session, and any reply in the dev session; a question there also launches `ask`. A question from a thread launches `ask`, without that reaction ([details](linear.md#human-messages-during-a-run)). |
| `session.stopped` | "Stop" button in Linear, or ticket taken away from the agent. | In a question session, the factory stops the answer in progress; otherwise the ticket's work stops (`stopped`). |
| `label.changed` | A label is added to or removed from the ticket (by a human). | No label starts or stops work: `agent:stop` stops nothing since ORC-201, its addition on a delegated ticket is answered by a comment that says how to stop. A label naming another repository, on a ticket at work, is answered by the routing comment (ORC-291). A removal enters the inbox and the journal (`change: removed`) but triggers nothing. |
| `push.human` | A human pushes a commit to the ticket's branch. | No reaction: the engine decides it on its own (ORC-159). On a delegated ticket at work, the agent's work pauses (the run in flight stops, the check, the publication and the waiting job are dropped) and the ticket is blocked (kind `human_push`) on the job the push interrupted; `verify` checks the pushed commit as the forge holds it, in a fresh clone, under the checks of the job the factory publishes, the freeze included (no sandboxes: no verdict, an infrastructure failure). Its verdict is told by the block's comment; green, the commit is the one verified last. The ticket stays paused either way: a reply resumes the interrupted job, which rebases its work on the push, and every later `verify` refuses a commit that does not carry the last human push (`factory/commits-humains`), until a publication of the factory carries it or a human puts the branch back on the commit verified last. A ticket already blocked for another reason keeps that block and the job a reply resumes; its push is checked all the same. The commit under review is no longer reviewed (as soon as the factory publishes, whether it works on the ticket or not): a Done merges nothing until the factory shows a new head in Human Review. A push of the commit `verify` last found green is the factory's own publication, and neither pauses nor counts as human; nor does anything happen on a ticket not delegated, delivered, stopped or whose PR is closed. Received through the GitHub `push` webhook (account that is not a bot), marked untrusted ([`github.md`](github.md#github-webhooks)). |
| `command` | `@Orchestrator /<word> …`, a command of the factory: `/refreeze` (ORC-131), `/approve`, `/changes` and `/reject` (ORC-212). | Decided by the factory itself, no reaction. A workflow declares no command of its own since ORC-392: another first word is a mention. |
| `pr.checks_passed` | The PR's CI passes. | The factory lifts the block caused by the red-CI bound. The count of the review and CI loop (`limits.ciFixAttempts`) stays: one per run (ORC-184). |
| `pr.checks_failed` | The PR's CI fails. | `fix-ci` (`prFailed`), bounded by `limits.ciFixAttempts`: once the bound is reached, the factory blocks the ticket instead of starting it. |
| `pr.conflicted` | The PR conflicts with its base branch (ORC-146). | Only for the ticket's open PR. `rebase` (`prFailed`) counts on the same bound as red CI (`limits.ciFixAttempts`): once it is reached, the factory blocks the ticket (cause « conflict ») instead of starting it. |
| `pr.merged` | The PR is merged. | First, the factory records the PR as merged and stops work on the ticket like a `stop`, without blocking it: the running `dev` run is stopped, waiting or queued runs and `debounce` timers are deleted. After that, no job from the `dev` queue starts on the ticket any more, whatever reaction, timer or wait requests it (reply, red CI, waiting or queued job): the refusal is only traced, with no message in Linear. The end of the stopped `dev` run and its checks are ignored. Its reaction comes after the stop (`merged`): Done, the `after_merge` step and the cleanup; a block is lifted, and jobs from the `questions` queue (`ask`) still run. It starts no run: the memory in writing sleeps (ORC-193). The ticket becomes active again when a human changes its status to something other than *Done* (also when the factory could not move it to *Done*), delegates it again, or a new PR (another number) is detected for it. The GitHub reconciliation no longer reads a ticket in *Done* whose PR is merged: a new PR is only seen once the ticket has left *Done*. |
| `pr.closed` | The PR is closed without merging. | If it is the ticket's known PR, open, and the ticket is not *Done*, the factory cancels work on the ticket: the running `dev` run is stopped, the waiting job and the expected check are deleted, the ticket is blocked (« PR #n closed without merge ») with a message in the session. A human relaunches as after a `stop` (reply in the ticket); a new PR (another number) is followed like any PR, and the same PR reopened becomes open again (`pr.opened`). |

Neither `pr.checks_passed` nor `pr.closed` has a reaction beyond what the table says.

#### Lifecycle events (not configurable)

The factory handles these types in hard-coded fashion: no reaction follows them.

| Event | Fixed behavior |
|---|---|
| `run.finished` | Success: checks if the job has any, otherwise the job's end ([the chain](#the-chain-orc-391)). Failure or limit: ticket blocked (`dev` queue) or error message (`questions` queue). An answer with `relay` (ORC-182): its question enters the run inbox (`relayed`) for the next launch of the ticket session, and the human is told so; the end of the run it was handed to, whatever its outcome, posts that agent's answer (`answers`) in the question's thread, or says there was none. When nothing is at work on the ticket (ORC-374), the job of the reply's reaction (`replyReaction`) starts at once to ask it, as no round of human review (it answers a question), unless a human change request waits beside it, which that job reads: then it is a round. Without a change request, the workflow's `relayJob` (`answer-relayed`, ORC-375) starts in its place, where that reaction would start a job: its end moves, posts and reviews nothing, unless the run moved the head of its worktree since its launch (`committed`), a commit that goes through `verify` and publication under the reply's job, then that job's end. With no reply's job to start, or waiting on its blockers, the question waits for the launch still to come. A blocked ticket keeps nothing: the human is told no answer will come. A question relayed while a step that does not resume the session ran (the AI review) resumes it at that step's end, by the same reaction. When the work ends with questions still relayed (`pr.merged`, `ticket.undelegated`, or the ticket cancelled by a human: `status.changed` with `cancelled`), each human is told in the question's thread that no answer will come, and they leave (`relay.dropped`). Work cancelled to go on (a stop, a pause, a spec changed, a check lost) keeps them. `dev` queue, depending on the attempt's outcome (ORC-289): agent question (`needs_input`) or disputed ticket (`spec_impossible`), ticket blocked with the question or the justification; infrastructure failure (`errored`: runner or sandbox down, unreadable output; not an error after the run has ended), ticket blocked, without a fix run; an already blocked ticket (the agent called `ask`) keeps its block, without a second message. A `done` returned by a failing run is a failure. Stopped run: nothing. End of a `dev` queue run after the PR is merged: nothing. |
| `verify.passed` / `verify.failed` | The job's end, or a new attempt, or a block (see `verify`). After the PR is merged: nothing. |
| `timer.fired` | A timer set by a decision expires (event `timer:<key>:<due>` written to the inbox). Kind `debounce`: launches the job whose `debounce` delay just expired (and unblocks the ticket). Kinds `clarify.remind` and `clarify.expire` (ORC-210): at 24 h the open `clarify` questions are asked again, at 72 h the ticket is blocked on `intake`; a round answered or ended since does nothing ([preset](#clarify-questions-reminder-and-expiry-orc-210)). Kind `usage.reset` (ORC-340): asks again the question the usage limit cut, as a relaunch of its run (a code step's, armed before ORC-357, relaunches it the same way); without a job: nothing. |
| `pr.opened` | Records the PR and attaches it to the Linear session. |
| `control.pause` / `control.resume` / `control.stop` | Pause / resume of the queue, which no command or route sends any more (ORC-200); stop of a ticket (UI, `factory stop`). |

**Delegation withdrawn** (`ticket.undelegated`, internal). The reconciliation writes it when a human takes the ticket back from the agent in Linear, after a `session.stopped` when a run is under way, which stops that run as Linear's Stop does. On a delegated ticket that is not blocked, the factory cancels its work as a cancel of the ticket stops it (ORC-227): the run is stopped, the verdict of a check in progress is ignored, the waiting job and the `debounce` timers are deleted, nothing is published. It writes nothing in Linear and blocks nothing. A blocked ticket keeps its block and its job: its work already ended, by the `session.stopped` when a run was under way. Unlike a cancel, the block and the messages kept in `humanInbox` stay.

Events about a ticket that the factory does not follow yet are ignored, except `ticket.delegated`, `session.mentioned`, `session.prompted` and `command`, which add it to the followed tickets.

**Untrusted events.** Each event carries a trust label (`taint`). An event marked `untrusted` (content from a source the factory does not consider trustworthy) does not change what starts: the runs the event requests carry a mark of it (`sensitivePaths`, a list kept for the decisions the journals record, of which only the presence is read): the recorded run and the runner request carry it. Linear ingestion marks as `untrusted` whatever Linear does not attribute to a workspace user: reply or comment without a user id, coming through a bot or from outside the workspace, ticket change made by an integration or an OAuth app, delegation or move found by reconciliation without a signed actor ([Linear](linear.md), ORC-160); GitHub ingestion always marks a `push.human` and a `pr.reviewed` as `untrusted` ([GitHub](github.md#github-webhooks), ORC-134). The runner enforces nothing while the run writes: `checkClone`, which `verify` and the publication both run on every commit of the branch since the base, refuses the diff (`factory/chemins-interdits`, ORC-338), and so does the fake runner's check without sandboxes, with the same function (`checkBranchPaths`) on the branch read on the factory's repository against the forge's default branch, fetched first: the same verdict as on the clone. As on the clone, what gives no verdict (no worktree, a git read that fails, a config the default branch refuses) is an infrastructure or config failure that blocks the ticket, never sent to the agent, and no command runs on a refused branch. The rules:

- **Every run, trusted or not:** the unconditional forbidden paths: `.github/**` (workflows, actions, `dependabot.yml`…), `CODEOWNERS` at any depth (GitHub reads it at the root, in `.github/` and in `docs/`), `.env`, `.envrc` and every `.env.*` but the templates `.env.example`, `.env.sample` and `.env.template`, which leave this rule only, not the forbidden directories they may sit in (dotenv, Vite and Next.js load `.env`, `.env.local`, `.env.<mode>` and `.env.<mode>.local`, and direnv runs `.envrc`: they hold values or run; an unknown `.env.*` is treated as one of them), `.factory/**`, `.claude/**`, and what runs at checkout or install (git hooks, `.gitattributes`, `.gitmodules`, `.npmrc`, `.yarnrc*`, `.yarn/releases/**`, `.yarn/plugins/**`, `.pnpmfile.cjs`, `setup.py`, `package.json#scripts`, `.husky/**`, `.vscode/**`, `Dockerfile*`, `.devcontainer/**`), plus `claims/**`.
- **Untrusted branch:** when a run that read untrusted content first starts in the ticket's worktree, the ticket records the branch's head at that moment (`untrustedSince`, sticky until a worktree is made again on a branch made anew from the default branch, nothing on it beyond that branch: that ends the mark and the human pushes kept with it, and the ticket's Claude session, which read under the mark, is not resumed: the next implementer run starts a new one, ORC-358. A merge alone does not end it: it says nothing of what the branch still holds). From then on, what the agent's commits since that head touch in the repository's [`sensitive_paths`](repository-configuration.md), read on the default branch, is refused, at every later verification and publication of that ticket, whoever runs next: the untrusted run's commits stay on the branch. What a trusted run committed before stays the human reviewer's, as on a trusted branch, and so do the commits a human pushed to the branch (`push.human`: the ticket keeps each push's `before` and `after`, and only the commits between them are the human's, not the agent's they were built on) and the default branch's: a teammate's edit of a sensitive path never wedges the ticket. A push recorded without its `before` leaves out nothing. A merge counts by what it changed beyond the clean merge. A head that was not read, or that is no longer an ancestor of the branch (a rewritten history), reads all the agent's commits since the branch left the default branch, human pushes still left out. A ticket from before this mark is read once in its run records, at its first verification, publication or untrusted launch, and the answer kept on it: its whole branch when an untrusted run of a worktree job worked on it, and a later untrusted run does not narrow that. Without sandboxes, `verify` reads the branch on the factory's repository: for a marked branch, against the forge's default branch, its `HEAD` fetched as the clone fetches it, whatever `origin/HEAD` still names; without a mark, against the repository's default branch as the launch last fetched it, no forge read (ORC-358). An entry of `sensitive_paths` that names nothing is left out of the check with a warning (`factory validate`, the daemon's log); an untrusted branch is then refused as a config failure until it is fixed, and trusted branches go on.
- **Trusted branch:** a branch no untrusted run ever worked on may change the repository's `sensitive_paths`. Nothing blocks it; the human review of the draft PR is the control, as for any other file.

 Each pending piece of feedback keeps the label of the event that brought it: a run that reads feedback (`input: feedback`) is untrusted as soon as one of those pieces of feedback is, even if launched later by a trusted event (end of `debounce`, a move). A run's label is set at its **launch**, based on what it reads then, and not when the decision requests it: a job put on hold behind a run (launched by `settle` at the end of that run) or left in the queue reads the feedback that arrived in the meantime, and becomes untrusted if any of it is. The run also keeps the sensitive paths it was requested with. Unresolved review comments that the forge returns to an `input: feedback` run are always untrusted: anyone who can comment on the PR writes them, and nothing authenticates them as coming from the team (ORC-160). Feedback recorded before this rule, without a label, counts as trusted, like an event from the first version of the journal: no source marked any event `untrusted` back then. **What a run reads beyond its input takes the label of who wrote it, not of who started the run** (ORC-349): a run that resumes the ticket's Claude session (a `verify` relaunch, a reply) carries the sensitive paths when the ticket's branch carries the mark of an untrusted run (`untrustedSince`, ORC-338), since that session read what that run read. The mark is read at the launch, outside any decision: a recorded journal replays as it was decided. The other runs only take the label of their event.

**Authorizations.** Before any reaction, `decide` checks the [authorization matrix](linear.md#authorizations-who-can-do-what) against the event's signed actor and the roles journaled with it (ORC-186): a delegation, a mention or a command requires the right to trigger, and a mention that answers a block (ORC-415) the right to relaunch too; a reply in the session, the right to reply (or to relaunch, if the ticket is blocked); a status change only when its reaction starts a run (a move to AI Review, `reviewAgain`), the right to trigger or, for a blocked ticket, to relaunch. No label starts a run. A refusal starts nothing and replies in the ticket.

**Non-delegated ticket.** On a ticket not delegated to the factory, a reaction that would start a job of the `dev` queue starts nothing (except the delegation itself): only jobs of the `questions` queue (`ask`) run on it.

### From an event to a run

1. Linear or GitHub sends an event (webhook, the 5-minute reconciliation), or a timer of the database fires: its source writes it to the **inbox** and answers once the row is committed (ORC-147).
2. The **worker** takes the event under its ticket's lock and, in one transaction, has `decide` apply the event's built-in behavior, then its reaction, if it has one ([default reactions](#default-reactions-orc-227-orc-392)); `reduce` writes the new projection, and the decision's effects and timers go to the **outbox** and the `timers` table in the same transaction (ORC-149, `planDecision`).
3. A reaction that starts a job produces a "launch a run" effect (`start_run`) that carries the job's name, or arms a regrouping timer (the preset's `regroup`).
4. An outbox executor then carries out `start_run` (ORC-150) and the daemon reads the job:
   - `dev` queue on a non-delegated ticket: refused;
   - `dev` queue while a run or checks are in progress on this ticket: the job is put **on hold on the ticket** and launched as soon as the current run is finished. There is only one waiting slot per ticket: a new request replaces the previous one;
   - queue paused or the Claude account's usage limit reached: queued;
   - no free slot in the queue (`concurrency` of `factory.yml` / 2 for questions): queued;
   - otherwise: launch.
5. Launch: `pickup` checks if needed, preparation of the workspace (`workspace`), `onStart.move`, choice of session (`session`), prompt construction (`/<skill>`, ticket, `input`), then Claude Code with the job's `model` and `limits`.
6. End of the run: its result comes back to the inbox as `run.finished`, whose fixed behavior decides the rest (checks, the job's end, or block).

The two queues:
- `dev`: work on the code of a delegated ticket (dev, feedback, CI, review). **Only one `dev` run at a time per ticket.**
- `questions`: answers (`ask`). They do not block the ticket's development; only one at a time per ticket, the others wait their turn.

### After the merge (ORC-197)

The reaction to `pr.merged` (`merged`) runs the `after_merge` step of the preset, carried out by the factory itself, without an agent. Its effect (`after_merge`, one outbox row):

1. appends an entry to the **changelog**, once by its merge, named as the inbox names the `pr.merged` event (`pr:<ticket>:<number>:merged`): a replay, or the event decided again, writes nothing, and an entry is never changed: the ticket and its title, what changed (the `summary` of the work the factory published last, the ticket's title when none was), where (the page the visual proof shot, and the paths of the diff in `visual_paths` that asked for it), the captures before and after `verify` took (ORC-176), each by the id of the artifact kept of it, or « no visual proof applicable » (`not_applicable`), or why the factory could not take it (`unavailable`), the PR's link and merge commit, and when GitHub merged it. The changelog needs nothing of Linear: it is written first.
2. mentions the requester, the issue's creator in Linear, in the ticket's session with the merged PR's link, best effort as an ack (a refusal or an issue gone is logged, and does not hold back the cleanup): « Delivered, <their profile>: `[PR #n](url)` is merged. » (Linear turns a profile's link into a mention). An issue with no creator (made by an integration) gets the same text without the mention.

Then the worktree is deleted (`cleanup`). The changelog is read through `GET /api/changelog` ([interface-and-security.md](interface-and-security.md#what-the-server-exposes)).


## Compilation and version

`compilePreset(preset, { repoNetwork, budgets })` checks the core invariants and returns the preset's hash, or throws a `PresetError` listing all violations:

- **bounded cycles**: `next` links alone form no cycle, and every step back names a declared counter, with a positive integer limit;
- **tests frozen before the build**: no step that writes code (`fix`, or `agent_step` with `writes: code`) is reachable without going through a `verify` in `freeze` mode;
- **merge gate**: from written code, a `publish` in `merge` mode is only reachable through a `merge` human gate;
- **read-only reviewer**: every `review` step is read-only, Claude API network at most;
- **offline checks**: every `verify` step runs without network;
- **network**: no step at Full (reserved for `setup`), none above the repository's level;
- **budget caps**: every agent step has a maximum number of turns; given `budgets` (`factory validate` gives them, the daemon does not yet: the values are to calibrate), every agent step has its `per_step_tokens`, the ticket its `per_ticket_tokens`, and the worst case stays under it (ORC-216).

**Worst case** (`src/presets/budget.ts`): from the entry, the run follows `next` and, at each step with a failure edge (red CI and conflict included) whose counter is not spent, may take it instead. The worst case is the exact maximum over these runs of Σ cap of each agent step run, in tokens (`per_step_tokens`) and in turns (`maxTurns`, lowered by `max_turns`). A `verify` step that passes refills its own counter, as the engine's `verify.passed` resets `verifyAttempts` and `redAttempts`: each entry into a checked loop gets all its retries. A way back that refills the counter it spends has no bound, and is refused. On `factory/default` that is 41 agent attempts at most: `spec_draft` 5, `tests` 3, `build` 4, `fix` 20 (5 entries, the review loop twice and the human one three times, each with its 3 retries of `verify`), `review` 6, the others once. A conflict spends the same `review_ci` as a red CI, and its way back (`rebase`, 60 turns, through `verify_rebase` with its 3 retries) weighs what `fix`'s does with equal caps: the worst case takes `rebase` instead where its `per_step_tokens` is higher, up to 8 attempts (2 entries × 4) in place of 8 of `fix`, and `factory validate` needs `per_step_tokens.rebase` like any agent step's (ORC-146). Not counted: a human relaunch, which gives every bound back and is the ticket's `per_ticket_tokens` to bound at run time; and what an attempt spends past its cap before it is stopped (the cap is checked as each message reports its usage). With the review loop at 5 rounds, the worst case was almost twice the cap per ticket of the MVP doc: it is 2 (`review_ci`), the count shared with red CI, and `limits.review_rounds` (« Max review rounds » of the review prompt) defaults to it.

The hash is the sha256 of the preset's canonical JSON (sorted keys): it does not depend on key order and changes as soon as a bound, a model or a step changes. Each run will be frozen on the hash it started with (`workflow_versions` table, ORC-149).

### Frozen versions (ORC-393)

A ticket decides on the workflow version it started with (ORC-149). That version carries a format, `version`: 2 since ORC-393, the only one this factory reads (`WORKFLOW_FORMAT`). A version of another format is refused: format 1 is every version frozen before ORC-393, the preset-driven ones of ORC-391 and ORC-392 as well as the older ones (no preset, jobs chained by their own `onSuccess`, a block told as free text in the session, knowledge jobs, the review that verified, the 3-minute regrouping as a fallback). Such a ticket is refused rather than decided on rules the engine no longer has: no decision is taken for its ticket, each of its events is set aside in `dead_letter` (« its decision threw »), and the daemon logs once `<ticket> refused: workflow version <hash> is of format 1, not 2: its ticket is refused (format 1: frozen before ORC-393)`; a start of it still in the queue leaves it, never launched. The ticket is not blocked, but it is told on Linear (ORC-419): the daemon that refuses it posts the standard block comment (step `workflow version`, the version's hash, « it is refused, and none of its events is decided »), asking for a new ticket, since nothing resumes this one (`waits: 'never'`); its key, `refused:<ticket>:<hash>`, is found on the ticket by any later daemon, which posts none again. A notice that fails is logged, and the ticket's next event tries again. A project without effects posts none. A replay of a journal recorded on such a version stops on the same error. No instance ran a v1 version (decision of 14/11): nothing is migrated, and such a ticket has no way back; a new ticket starts on the current version.
