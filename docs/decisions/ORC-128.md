## Décision

**2026-10-22 — retenue par le dev : toutes les recommandations** de cette page, celles des trois besoins comme celle d'ensemble. Elle est aussi écrite dans le ticket ORC-128.

| Point tranché | Option retenue |

Les affirmations marquées « non vérifié » plus bas le restent : la décision ne les vérifie pas.

> **Statut : tranché** (voir ci-dessus). Les tickets qui en dépendent sont ORC-205 et ORC-217 (bloqués jusqu'à cette décision), puis ORC-136, ORC-188, ORC-213 et ORC-215.
>
> Version mesurée : **Claude Code 2.1.306** (`claude --version`), le 21 octobre 2026. Le doc MVP cité par le ticket est un artefact claude.ai que la session n'a pas pu ouvrir. Cette page s'appuie sur le ticket, les tickets liés et des mesures réelles.

## La question

Le doc MVP fixe trois besoins pour l'agent lancé par l'usine, sans donner les options exactes :

1. **Ignorer tous les réglages du dépôt** (`.claude/settings.json`, `.claude/settings.local.json`, `CLAUDE.md`, `.mcp.json`, hooks, skills et plugins du dépôt). Ne charger que ce que l'usine impose.
2. **Couper les outils web intégrés** (WebFetch, WebSearch) s'ils ouvrent un chemin réseau que le proxy de sortie ne voit pas.
3. **Reprendre la session d'un ticket**, et savoir ce qui casse cette reprise.

Point de départ dans Relais : `buildClaudeArgs` (`src/adapters/runner/claude-code.ts`) passe `--setting-sources project,local`, `--settings <run-settings.json>`, `--plugin-dir <pack>`, et `--session-id` ou `--resume`. Le pack (`packs/standard/settings.json`) ne met ni WebFetch ni WebSearch en `allow`, ni en `deny`.

## Critères

Dans l'ordre du ticket, puis ceux des tickets liés :

- **C1. Rien du dépôt n'est chargé** comme réglage. C'est le test d'isolation n° 11 d'ORC-205 : réglages, mémoire, MCP, `.claude/`.
- **C2. Ce que l'usine impose reste chargé** : `--settings`, le pack (`--plugin-dir`, avec ses hooks et ses skills), et les MCP de l'usine (`submit_result`, `ask`, puis `kb_search` : ORC-188).
- **C3. Aucun chemin réseau ne contourne le proxy de sortie** (ORC-213).
- **C4. La session d'un ticket se reprend** après une question, une review ou un crash (ORC-217, ORC-220).
- **C5. Compatible avec les comptes par abonnement** (ORC-215 : le seul secret monté est le jeton OAuth).
- **C6. Vérifiable à chaque version** : une option qu'on ne peut pas tester sera cassée en silence par une mise à jour.

### Recommandation pour le besoin 1

```bash
claude -p … --setting-sources "" \
  --settings <run-settings.json> --plugin-dir <pack> \
  --strict-mcp-config --mcp-config <mcp-usine.json>
```

- **`--setting-sources ""`** à la place de `project,local`. C'est ce qui coupe l'injection de `CLAUDE.md` (appel 13 contre appel 11 : même prompt, sans outils, seule la source change), les hooks de `.claude/settings*.json` et les skills du dépôt.
- **`--strict-mcp-config` + `--mcp-config`**. Combiné aux sources vides, il coupe `.mcp.json`. Il coupe aussi **les connecteurs claude.ai du compte** (Drive, Docs, Canva…), qui sinon seraient chargés dans chaque run avec un compte par abonnement (ORC-215). Sources vides ou non, seul `--strict-mcp-config` les retire (appels 2 et 8).
- **`CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`**, comme le prévoit ORC-205. Son effet n'est pas vérifié.
- **Pas de `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`** (point 2) : il doublerait les sources vides, mais n'est pas documenté.
- **Garder la remise à zéro de `.claude/**`** prévue par ORC-205, en défense en profondeur. Les pièges testés n'en ont pas besoin, mais tous les pièges possibles n'ont pas été testés.

## Besoin 2 — Outils web intégrés

### Passent-ils par le réseau du processus ?

**Appel 6.** Un proxy CONNECT local journalise chaque hôte (`proxy.mjs`, 25 lignes de Node). Claude Code le reçoit par `HTTPS_PROXY=http://127.0.0.1:18128`, avec `--setting-sources "" --strict-mcp-config --allowedTools WebFetch WebSearch --max-turns 4`. On demande un WebFetch de `https://example.com`, puis un WebSearch.

```text
tool_use WebFetch  {"url":"https://example.com", …}   → « Le titre de cette page est « Example Domain ». »
tool_use WebSearch {"query":"IANA example domain RFC 2606"} → « Links: [{"title":".example","url":"https://en.wikipedia.org/wiki/.example"} … »

proxy.log :
15:37:13 CONNECT api.anthropic.com:443      (×8 : appels au modèle)
15:37:16 CONNECT example.com:443            ← WebFetch
15:37:16 CONNECT api.anthropic.com:443
15:37:22 CONNECT http-intake.logs.us5.datadoghq.com:443   ← télémétrie
15:37:23 CONNECT api.anthropic.com:443
```

- **WebFetch** passe par le réseau du processus, donc par `HTTPS_PROXY`. Le proxy voit `example.com` dans le CONNECT, et un proxy filtrant pourrait donc le refuser. Le proxy de l'essai ne faisait que journaliser : rien n'a été filtré.
- **WebSearch** : le proxy ne voit **aucune connexion** vers un moteur de recherche. Les résultats arrivent dans la réponse de `api.anthropic.com` : la recherche tourne chez Anthropic. Le proxy ne voit que `api.anthropic.com`, qu'il doit autoriser pour que l'agent fonctionne. **C'est un chemin qu'il ne voit pas** : il ne peut ni filtrer ni journaliser les domaines visités. (Seul le trafic qui suit `HTTPS_PROXY` a été observé. Sous `--network none` avec le proxy comme seule sortie, il n'y a de toute façon pas d'autre chemin.)
- **Télémétrie (constat annexe)** : Claude Code envoie de la télémétrie à `http-intake.logs.us5.datadoghq.com`. ORC-213 doit choisir de la bloquer au proxy ou de la couper.
- **Variables `*_USE_CCR_PROXY`** : le binaire contient `CLAUDE_CODE_WEBFETCH_USE_CCR_PROXY` et `CLAUDE_CODE_WEBSEARCH_USE_CCR_PROXY`. Dans certains environnements, WebFetch pourrait donc lui aussi passer par Anthropic. Elles ne sont pas posées sur le runner. Non vérifié.

### Comment les retirer

Les deux voies retirent les outils de la liste annoncée au modèle (`tools` de l'événement `init`) :

- `permissions.deny: ["WebFetch","WebSearch"]` dans le fichier passé à `--settings` : **vérifié** (appels 3 et 5 : `web: []`) ;
- `--disallowedTools WebFetch WebSearch` : **vérifié** (appel 4 : `web: []`).

Sans l'une des deux, les outils sont présents (appels 1, 2, 6). L'appel 6 les autorisait par `--allowedTools`. Ce qui se passe sans règle `allow` (refus ou demande de permission) n'a pas été mesuré : **non vérifié**.

### Recommandation pour le besoin 2

- **WebSearch : le couper**, par `deny` dans les réglages imposés. Il contourne le proxy (C3) : c'est le cas que la règle du ticket vise.
- **WebFetch : la règle du ticket ne demande pas de le couper**, puisqu'il passe par le proxy. ORC-213 dit même que l'agent garde « son outil de fetch ». Le couper aussi serait allé au-delà des mesures : il est gardé (point 1).

Mettre l'interdit dans le fichier `--settings` de l'usine plutôt que dans `--disallowedTools` : c'est le même endroit que le reste de la deny-list. Il faut l'ajouter à la deny-list d'ORC-205, qui ne contient aujourd'hui ni WebFetch ni WebSearch, et à son test « un interdit par entrée », qui reste à écrire.

## Besoin 3 — Reprendre la session d'un ticket

### Options

- `--session-id <uuid>` : démarre une session avec cet identifiant. Déjà utilisé au premier run `dev`.
- `-r, --resume <id>` : reprend la session. Déjà utilisé quand la reprise est demandée (`opts.resume`, ou à défaut `job.session === 'resume'`) **et** que le ticket a déjà un `claudeSessionId` ; sinon un nouvel identifiant part en `--session-id` (`src/core/orchestrator.ts` l. 583-586).
- `--fork-session` : reprend dans une copie, sous un nouvel identifiant. Pas nécessaire : `review` démarre déjà en session neuve.
- `--no-session-persistence` : n'écrit pas de session. À ne pas utiliser pour l'implémenteur.

### Mesures

La session `22222222-…` a été créée à l'appel 5 dans `/tmp/orc128-Q9ZT/repo`. Sa première réponse est `INCONNU`. Son fichier est `~/.claude-perso/projects/-tmp-orc128-Q9ZT-repo/22222222-2222-4333-8444-555555555555.jsonl`, c'est-à-dire `$CLAUDE_CONFIG_DIR/projects/<cwd encodé>/<id>.jsonl`.

| Appel | Changement | Prompt | Résultat |
|---|---|---|---|
| 7 | `--resume 22222222-…`, même dossier, mêmes options que l'appel 5 | « Qu'as-tu répondu à ma question précédente ? Recopie ta réponse exacte, en une ligne. » | **reprend** : `INCONNU`, sa réponse de l'appel 5 |
| 8 | `--resume 22222222-…` depuis **un autre dossier** (`/tmp/orc128-Q9ZT/autre`), `--setting-sources "" --tools ""` | « Qu'as-tu répondu à ma toute première question dans cette conversation ? Recopie-la mot pour mot, en une ligne ; si tu n'as aucun historique, dis AUCUN-HISTORIQUE. » | **reprend** : `INCONNU`, pas `AUCUN-HISTORIQUE` |
| 9 | `--resume 22222222-…` avec un **autre `CLAUDE_CONFIG_DIR`** (dossier vide) | « Une ligne. » | **échoue** avant tout appel API : `No conversation found with session ID: 22222222-…` |
| 10 | `--session-id 22222222-…` sur un identifiant **déjà existant** | « Une ligne. » | **échoue** : `Error: Session ID 22222222-… is already in use.` |

Après l'appel 8, la suite est écrite dans le **fichier d'origine**, rangé sous le dossier du premier lancement. Le `cwd` y passe de `…/repo` (18 lignes, appels 5 et 7) à `…/autre` (9 lignes, appel 8) :

```text
$ jq -r 'select(.cwd) | .cwd' ~/.claude-perso/projects/-tmp-orc128-Q9ZT-repo/22222222-….jsonl | uniq -c
     18 /tmp/orc128-Q9ZT/repo
      9 /tmp/orc128-Q9ZT/autre
```

Non vérifié :

- **Changement de compte** (autre jeton OAuth, même `CLAUDE_CONFIG_DIR`) : le fichier de session est local et ne porte pas le compte, donc la reprise devrait marcher. Il n'y a pas de second compte sur ce poste pour le vérifier.
- **Prompt système à la reprise** : l'aide de `--system-prompt-snapshot` (activé par défaut) dit que le prompt système du premier appel est enregistré, puis renvoyé tel quel à chaque reprise, « even when a later launch passes different text ». Un `CLAUDE.md` injecté par `--append-system-prompt` (ORC-205) resterait donc figé à sa valeur du premier run, jusqu'à une compaction.
- **Reprise depuis un autre dossier** : elle marche en 2.1.306 (appel 8), mais n'est pas documentée. Ne pas s'y fier.

### Recommandation pour le besoin 3

- **Garder `--session-id` au premier run et `--resume` ensuite**, comme aujourd'hui.
- **Ce qui casse la reprise, c'est `CLAUDE_CONFIG_DIR`** (appel 9), pas le dossier de travail (appel 8). Le volume du ticket (ORC-217) doit porter `$CLAUDE_CONFIG_DIR/projects/`, et chaque runner du ticket doit lancer Claude avec le même `CLAUDE_CONFIG_DIR`. Garder aussi le même chemin de worktree d'un runner à l'autre, puisque la reprise depuis un autre dossier n'est pas documentée.
- **`--session-id` sur un identifiant existant échoue** (appel 10). Un premier run relancé après un crash (ORC-220) doit passer en `--resume` dès que le fichier de session existe, ou prendre un nouvel identifiant.

## Points tranchés

Le dev a retenu l'option recommandée pour chacun des cinq points : voir le tableau de la section [Décision](#décision). Les arguments pesés restent ci-dessous.

1. **WebFetch : le couper aussi ?** Les mesures ne l'imposent pas : il passe par le proxy. ORC-213 prévoit que l'agent garde son outil de fetch. Le couper irait donc au-delà de la règle des tickets et contredirait ORC-213. L'argument pour : une surface de moins, et un outil dont `build` peut se passer, puisque `curl` à travers le proxy fait le même travail. Option retenue : **le garder**, comme le prévoit ORC-213, puisque le proxy le voit et peut donc le filtrer. WebSearch seul est coupé.
2. **Ajouter `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` en défense ?** `--setting-sources ""` suffit pour `CLAUDE.md` (appel 13 contre appel 11). La variable n'est pas documentée, et son effet seul n'a pas été isolé. Option retenue : ne pas la poser, et laisser le test n° 11 surveiller `CLAUDE.md` à chaque version.
3. **Télémétrie de Claude Code (`http-intake.logs.us5.datadoghq.com`) : la bloquer au proxy ou la couper par variable ?** Option retenue : la couper par variable, et la bloquer au proxy en défense. Les variables candidates (`DISABLE_TELEMETRY`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`) sont **non vérifiées** ici : à mesurer dans ORC-213.
4. **Volume de session : tout `CLAUDE_CONFIG_DIR` par ticket, ou seulement `projects/` ?** Option retenue : tout `CLAUDE_CONFIG_DIR` par ticket, avec le jeton par l'environnement. C'est plus simple à monter, et rien d'un autre ticket ne fuit.
5. **Doubler le `deny` des outils web par `--disallowedTools` ?** Option retenue : non, le `deny` dans les réglages de l'usine suffit, une fois couvert par le test de la deny-list d'ORC-205.
