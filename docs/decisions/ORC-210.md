# ORC-210 — `clarify`: who writes the questions, and what the wait is

## Decision

**2026-11-08 — proposed by the ticket's session, to confirm in review.**

| Point | Option adopted |
|---|---|
| 1. Who writes the questions? | **`intake` itself**, in `missing`: each `{ question, options }` (or a bare question). No second agent run for `clarify`. |
| 2. What is the ticket while it waits? | **Not blocked**: a wait of its own (`TicketState.clarify`), ended by what ends the usage-limit wait. Blocked only at 72 h. |
| 3. Which reply answers which question? | **One reply per question, in order**, a picked option or free text alike. |
| 4. After the last answer? | **`intake` again**, fed the answers, as a new session. |
| 5. Linear's `select`? | `signal: "select"`, `signalMetadata.options: [{ label, value }]`, the option text as both. |

## Why

1. The ticket's out-of-scope puts a separate intent agent at EVP 1, and intake already wrote its questions "with the options you see". A `clarify` agent would cost a run to restate intake's questions. The preset keeps `clarify` as an optional agent step; the engine does not execute the preset yet (ORC-177).
2. Blocked would reserve the answer to `relaunch_blocked` (team members only). The MVP doc lets the requester answer (`answer_clarify`). It would also put the ticket in the Flow's « Blocked » column during an ordinary wait.
3. Linear sends a picked option back as an ordinary `prompt` activity, with no link to its elicitation. Counting replies in order is deterministic and replays the same way. A human who answers everything in one message is asked the rest again at 24 h.
4. Intake's session is not the ticket's (`session: new`): `--resume` there would resume nothing. Making intake the ticket's session would hand its context to `dev`, which is ORC-254's to decide.
5. From Linear's agent-signals page. **Not checked on a real workspace**: `tracker.live.test.ts` has no case for it yet.

## Open

- A comment on the ticket is not an answer while it waits: the matrix keeps `answer_clarify` to the session. It stays in the inbox for intake's next pass.
- Beyond 3 (a failed check plus 3 of intake's), the last of intake's are dropped; intake asks them again on its next pass.
