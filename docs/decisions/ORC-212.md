# ORC-212 — `spec_draft`, `spec_check`, `spec_review`: what the ticket leaves open

## Decision

**2026-11-08 — proposed by the ticket's session, to confirm in review.**

| Point | Option adopted |
|---|---|
| 1. Where is the spec published? | **In the ticket's Linear session**, as a `response` activity; the ticket stays in Todo. ORC-139 (a « Spec » status, or a comment) is not decided. |
| 2. Who may send `/changes` and `/reject`? | **The same validators as `/approve`** (`validate_spec`), never the run's initiator. |
| 3. Where are the commands accepted? | **A reply in the ticket's session**, where the spec is. A mention or another session is refused by the matrix as « not through this channel ». |
| 4. What is « a spec changed during the run »? | **A `/changes` on the approved version** while the ticket works on it: the work stops, the next version goes through `spec_check` and waits for a new `/approve`. |
| 5. What does `/reject` do? | **Blocks the ticket on the spec job**, cause « stopped »: a reply drafts again. |
| 6. Where do the bounds live? | `limits.specCheckReturns` (1) and `limits.specChanges` (3), carried from the preset's counters as `verify` and `red` are. |

## Why

1. The session is where every factory message of a run already goes, and the ORC-139 decision changes only where the text is posted. A dedicated status needs a Linear setup change on every team: the conservative option waits for the decision.
2. A `/changes` resets the spec the validator will approve; a `/reject` stops the run. Giving them to the initiator would let the requester steer the contract the validator is the second look on. The matrix has no finer row; ORC-187 can split it.
3. The matrix keeps `validate_spec` to the Linear session. A mention opens a separate session, where no spec was published.
4. Linear sends no edit of an agent activity, and no event carries a hand-edited spec today. A new version asked by a validator is the one modification the factory can see. A hand-edited spec comes with ORC-139's comment option.
5. A rejection is a human stopping the run; blocking on the spec job keeps the way back a plain reply.

## Open

- The spec's `decisions` are checked against `TicketState.decisions`, which ORC-210 (PR #147) adds; until it is merged, no ticket has any, and the check finds nothing to require.
- A version approved, then the ticket delegated again: the next draft starts a new version, without approval; nothing clears the old one.
