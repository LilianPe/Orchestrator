# ORC-213 — Proxy de sortie des sandboxes : quelle brique, et que voit-il ?

## Décision

**2026-11-02 — points 1 à 3 et 5 proposés par la session du ticket. 2026-11-03 — point 4 tranché par le dev : interception TLS, dans cette PR.**

| Point | Option retenue |
|---|---|
| 1. Comment le conteneur sort-il, en `--network none` ? | **Par un socket Unix par run**, monté dans le conteneur, et un relais local (`127.0.0.1:3128`) devant lui. `HTTP(S)_PROXY` pointent sur le relais. |
| 2. Quelle brique de proxy ? | **Un proxy de l'usine en Node** (`src/network/proxy.ts`), dans le démon. Ni smokescreen ni Envoy. |
| 3. Comment savoir de quel run vient une connexion ? | **Un socket par run** : le journal sait le run sans croire ce que le conteneur envoie. |
| 4. Les méthodes vers un hôte HTTPS ? | **Interception TLS** par une autorité de l'usine (2026-11-03, le dev) : chaque tunnel est déchiffré, chaque requête vérifiée (méthode, chemin), pour tous les hôtes permis. Signature des certificats par **`node-forge` 1.4.0**, version exacte. |
| 5. Le journal ? | **Un JSONL par run** dans `<home>/network/`, en attendant la base et le tableau de bord. |

## La question

Le doc MVP (N2) veut un runner en `--network none`, avec « seul le socket du proxy de l'usine monté » : pas de DNS, UDP et QUIC coupés, chaque connexion journalisée. Le proxy applique le niveau de l'étape :

- **Aucun** : rien, sauf l'API Claude pour une étape qui appelle l'agent ;
- **Limité** (défaut) : API Claude, registres npm et PyPI, domaines de doc, GitHub en lecture ; **méthodes GET, HEAD et OPTIONS seulement**, sauf vers l'API Claude ;
- **Personnalisé** : Limité plus le `network.allow` du dépôt ;
- **Complet** : tout, réservé à `setup`.

Le ticket laisse ouvert le choix de la brique (smokescreen ou Envoy). Il y a aussi une contrainte cachée : la restriction des méthodes. Un proxy HTTP voit une requête HTTPS comme un `CONNECT hôte:443` suivi de TLS chiffré. Il ne voit ni la méthode ni le chemin. Le critère d'acceptation 2 (« un `git push` ou une création de gist refusés ») ne tient donc pas avec un simple filtre par hôte.

Avant ce ticket, le conteneur avait le pont du moteur, ouvert à Internet (« réseau ouvert provisoire », ORC-204).

## Critères

- **C1. Aucune sortie hors du proxy** : ni route, ni DNS, ni UDP, quel que soit l'outil (un outil qui ignore `HTTPS_PROXY` n'a pas de réseau du tout).
- **C2. Le niveau appliqué hors de portée de l'agent** : rien dans le conteneur ne choisit son niveau.
- **C3. Journal par run** : hôte, méthode, chemin, taille, refus.
- **C4. Les écritures refusées** vers GitHub, les registres et tout hôte permis (critère 2 du ticket) : c'est là qu'un agent exfiltrerait du code (push, gist, publication, formulaire).
- **C5. L'agent garde ses outils** : npm, Yarn, pip, git en lecture, `factory-agent` et le MCP de l'usine, `claude` lui-même.
- **C6. Simple à déployer et à tester** : pas de service de plus sans besoin, testable sur un vrai moteur (`test/isolation/network.test.ts`).

## Options

### Point 1 — Sortir d'un conteneur sans réseau

| Option | Pour | Contre |
|---|---|---|
| **a. Socket Unix monté + relais local** (retenue) | `--network none` reste vrai (C1) : aucune interface hors `lo`. Le socket est un fichier : le monter suffit. | Un relais dans le conteneur. Il tient en une ligne de Node, déjà dans l'image : c'est le PID 1 du conteneur. |
| b. Un réseau interne du moteur, avec le proxy seul dessus | Pas de relais. | Le conteneur a une interface et un DNS : une erreur de réglage du réseau rouvre la sortie. Contraire au doc. |

Mesuré ici : un socket créé sur un hôte Windows ne passe pas dans la VM de Docker Desktop. Le démon est sous Linux de toute façon (les sandboxes l'exigent). Le test d'isolation fait donc tourner le proxy dans un conteneur à lui, du côté du moteur.

### Point 2 — La brique

| Option | Pour | Contre |
|---|---|---|
| **a. Proxy Node de l'usine, dans le démon** (retenu) | Quelques centaines de lignes. Un socket par run, ouvert et fermé avec le conteneur. Règles par méthode et chemin dans le même code que les niveaux. Testé en unitaire et sur un vrai moteur. | Code de sécurité à nous. Il tourne dans le processus du démon : une faille du proxy est une faille du démon. |
| b. smokescreen (Stripe, Go) | Éprouvé, liste d'hôtes, refus des adresses privées. | Liste par hôte seulement (`CONNECT`) : C4 non tenu. Un service de plus, une identité par run à faire passer. |
| c. Envoy | Tout est possible (filtres HTTP, TLS). | Lourd à configurer et à faire évoluer par run ; un service de plus. |

Le proxy Node peut passer dans un service `proxy` de `compose.yaml` (ORC-203) sans changer le conteneur : seul le chemin du socket change.

### Point 4 — Voir les méthodes

| Option | Pour | Contre |
|---|---|---|
| a. Hôte seulement, partout | Le plus simple. | `git push`, gist et `npm publish` passent : C4 non tenu. |
| b. Hôtes à API d'écriture en `http://`, le proxy continue en HTTPS (proposée le 2026-11-02) | C4 tenu pour GitHub, npm et PyPI sans autorité. | Les docs, téléchargements et `network.allow` restent au niveau de l'hôte : un POST y passe. Deux mécanismes, et des variables par outil (`insteadOf`, registre, index). |
| **c. Interception TLS par une autorité de l'usine** (retenue) | Méthode et chemin vus pour **tout** hôte permis : C4 tenu partout. Un seul mécanisme : les redirections `http://` de (b) sont retirées. | Une autorité à créer et à garder (sa clé est un secret du démon), reconnue dans le conteneur par variables ; une dépendance pour signer les certificats. Un client qui épingle un certificat échoue. |

### Point 4 bis — La bibliothèque de certificats

Node génère les clés (`crypto.generateKeyPairSync`) et lit les certificats (`X509Certificate`), mais ne signe pas de X.509.

| Option | Pour | Contre |
|---|---|---|
| **`node-forge`** (retenue, `1.4.0` exacte, publiée en mars 2026) | Un seul paquet, **aucune dépendance**, très répandu (signature X.509, extensions SAN, AKI/SKI). | RSA en JavaScript, lent pour générer : on ne lui fait que **signer**, les clés viennent de `crypto` de Node. Historique de failles dans son ASN.1 : la version retenue suit les correctifs de 2025. |
| `@peculiar/x509` | API moderne, WebCrypto. | Plusieurs dépendances (`asn1-*`, `tsyringe`, `reflect-metadata`, `pvtsutils`). |
| `openssl` en sous-processus | Rien à installer côté npm. | Pas sur tous les hôtes, un processus par hôte, des fichiers temporaires. |

## Ce qui est appliqué

- **Conteneur** (`src/adapters/sandbox/docker-rootless.ts`) : toujours `--network none`. Avec le proxy, il monte le socket du run en `/run/factory/egress.sock` et le **certificat** de l'autorité en lecture seule en `/run/factory/egress-ca.crt` (jamais sa clé). Il lance le relais en PID 1 et pose `HTTP(S)_PROXY` (et ceux de Yarn), `NO_PROXY=localhost,127.0.0.1`, `NODE_USE_ENV_PROXY=1` (le `fetch` de Node : `factory-agent`), et l'autorité comme seule confiance : `NODE_EXTRA_CA_CERTS` (Claude Code, npm, Yarn), `SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`, `PIP_CERT`, `GIT_SSL_CAINFO`, `npm_config_cafile`, `YARN_CAFILE`, `YARN_HTTPS_CA_FILE_PATH`. L'image ne change pas. Sans proxy, rien ne sort.
- **Après un redémarrage du démon**, un conteneur vivant a un socket mort (le montage tient un inœud supprimé) : le provider ne le rend plus (`findByAttempt`), le détruit et en refait un.
- **Autorité** (`src/network/ca.ts`) : faite au premier run sandboxé, dans `<home>/egress-ca/` (`ca.key` en `0600`, dans un dossier `0700`). RSA 2048, dix ans, `pathLenConstraint: 0`. Un certificat par hôte (SAN = l'hôte), signé à la demande, gardé 7 jours en mémoire (valable 30), une seule clé pour tous.
- **Niveaux** (`src/network/levels.ts`) : une étape resserre seulement le niveau du dépôt, `full` est refusé à l'agent, `custom` ajoute `network.allow` (en minuscules) au niveau `limited`.
- **Proxy** (`src/network/proxy.ts`) :
  - `CONNECT` vers le port 443 seulement (sauf en `full`), aux hôtes du niveau, **déchiffré** : ALPN `http/1.1` seulement (un client HTTP/2 seul est refusé), une mise à niveau (WebSocket) ou ce qui n'est pas HTTP est refusé et journalisé ;
  - chaque requête vérifiée contre l'hôte du `CONNECT`, jamais contre son en-tête `Host` (pas de *domain fronting*), puis envoyée en TLS vers cet hôte, **certificat vérifié** par le magasin de Node, `Host` remis à l'hôte vérifié ;
  - GET, HEAD et OPTIONS partout ; plus le POST de `git fetch` (`git-upload-pack` de `github.com`) ; `service=git-receive-pack` refusé ; l'API Claude garde toutes ses méthodes ; le renouvellement OAuth de Claude Code (POST `/v1/oauth/token` de `console.anthropic.com` et `platform.claude.com`, non mesuré : ORC-128 n'a vu que `api.anthropic.com` avec un jeton longue durée) ;
  - HTTP en clair : vérifié de même, renvoyé en HTTPS (en `full`, tel quel) ;
  - aucune adresse privée, même en `full`, même par un nom qui y mène : réseaux privés, boucle locale, `169.254.0.0/16`, `100.64.0.0/10`, `192.0.0.0/24`, `198.18.0.0/15`, multicast et réservé, IPv6 locales, NAT64 (`64:ff9b::/96`), 6to4 (`2002::/16`), IPv4 mappées ;
  - l'API agent (`FACTORY_API`, dont le MCP de l'usine en `/agent/mcp`) relayée vers le démon, en clair ou en tunnel non déchiffré ; le démon n'écoute plus que sur la boucle locale ;
  - la télémétrie de Claude Code refusée : ses hôtes ne sont sur aucune liste (ORC-128, point 3) ;
  - le journal s'écrit par un flux par run : une écriture qui échoue est signalée au journal du démon, jamais levée ; la requête amont meurt avec celle du client.
- **Runs** : tous en `limited`, le défaut du doc (`src/core/orchestrator.ts`, commentaire `ponytail`) : `stepPolicy` n'a pas encore d'appelant en production.

## Risques restants

1. **La clé de l'autorité est un secret du démon.** Qui la lit peut se faire passer pour n'importe quel site auprès des sandboxes de cette instance (et d'elles seules). Elle n'est jamais montée ; un run sans sandbox, sur l'hôte, peut la lire comme `secrets.json`.
2. **Un client qui épingle un certificat**, ou qui ignore les variables d'autorité, échoue : fermé par défaut, journalisé.
3. **Redirections** : une redirection vers un hôte hors du niveau est refusée (dépôt GitHub renommé, paquet servi par un autre CDN).
4. **Le proxy tourne dans le démon** : une faille de son analyse HTTP ou TLS (Node) est une faille du démon.

## Points ouverts

1. **`network` du dépôt et niveau par étape au lancement** : la config du dépôt n'est lue au lancement qu'avec ORC-209 C. D'ici là, tous les runs sont en `limited`, `allow` vide, et `stepPolicy` n'est appelé que par ses tests.
2. **`setup` en `full`** : il tourne dans le conteneur du run, à son niveau (`limited`). Basculer le niveau du proxy le temps du `setup` laisserait en `full` tout processus que le `setup` a lancé en arrière-plan, tant qu'il vit ; le doc veut un `setup` avant l'agent, dans un conteneur à lui. Non fait ici : un `setup` qui sort des listes échoue.
3. **Dépôt en `none`** : le doc dit « rien, sauf l'API Claude pour une étape qui appelle l'agent ». `repoNetworkCeiling` donne `none`, et le préréglage `factory/default` est alors refusé (comportement d'ORC-209, inchangé ici).
4. **Journal en base et au tableau de bord** : aujourd'hui un JSONL par run. Une table et sa migration viendront avec l'écran du journal de sécurité (ticket à ouvrir).
5. **Liste des domaines de doc** : une première liste courte dans `levels.ts`. À compléter à l'usage.
6. **Podman rootless** : le test d'isolation réseau n'a tourné que sous Docker Desktop. Le job CI `isolation` le passera sous Podman.
