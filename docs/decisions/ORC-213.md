# ORC-213 — Proxy de sortie des sandboxes : quelle brique, et que voit-il ?

## Décision

**2026-11-02 — proposée par la session du ticket, à valider par le dev.** Le point 4 reste ouvert : il demande un choix humain.

| Point | Option retenue |
|---|---|
| 1. Comment le conteneur sort-il, en `--network none` ? | **Par un socket Unix par run**, monté dans le conteneur, et un relais local (`127.0.0.1:3128`) devant lui. `HTTP(S)_PROXY` pointent sur le relais. |
| 2. Quelle brique de proxy ? | **Un proxy de l'usine en Node** (`src/network/proxy.ts`), dans le démon. Ni smokescreen ni Envoy pour l'instant. |
| 3. Comment savoir de quel run vient une connexion ? | **Un socket par run** : le journal sait le run sans croire ce que le conteneur envoie. |
| 4. Les méthodes vers un hôte HTTPS ? | **Vues sans interception pour les hôtes à API d'écriture** (GitHub, npm, PyPI) : le conteneur les joint en `http://`, le proxy continue en HTTPS. **Pour les autres, l'hôte seul.** L'interception TLS (une autorité de l'usine) est le **point ouvert**. |
| 5. Le journal ? | **Un JSONL par run** dans `<home>/network/`, en attendant la base et le tableau de bord. |

## La question

Le doc MVP (N2) veut un runner en `--network none`, avec « seul le socket du proxy de l'usine monté » : pas de DNS, UDP et QUIC coupés, chaque connexion journalisée. Le proxy applique le niveau de l'étape :

- **Aucun** : rien, sauf l'API Claude pour une étape qui appelle l'agent ;
- **Limité** (défaut) : API Claude, registres npm et PyPI, domaines de doc, GitHub en lecture ; **méthodes GET, HEAD et OPTIONS seulement**, sauf vers l'API Claude ;
- **Personnalisé** : Limité plus le `network.allow` du dépôt ;
- **Complet** : tout, réservé à `setup`.

Le ticket laisse ouvert le choix de la brique (smokescreen ou Envoy). Il y a aussi une contrainte cachée : la restriction des méthodes. Un proxy HTTP voit une requête HTTPS comme un `CONNECT hôte:443` suivi de TLS chiffré. Il ne voit ni la méthode ni le chemin. Le critère d'acceptation 2 (« un `git push` ou une création de gist refusés ») ne tient donc pas avec un simple filtre par hôte.

Avant ce ticket, le conteneur avait le pont du moteur, ouvert à Internet (« réseau ouvert provisoire », ORC-204).

## Critères

- **C1. Aucune sortie hors du proxy** : ni route, ni DNS, ni UDP, quel que soit l'outil (un outil qui ignore `HTTPS_PROXY` n'a pas de réseau du tout).
- **C2. Le niveau appliqué hors de portée de l'agent** : rien dans le conteneur ne choisit son niveau.
- **C3. Journal par run** : hôte, méthode, taille, refus.
- **C4. Les écritures refusées vers GitHub et les registres** (critère 2 du ticket) : c'est là qu'un agent exfiltrerait du code (push, gist, publication d'un paquet).
- **C5. L'agent garde ses outils** : npm, pip, git en lecture, `factory-agent`, `claude` lui-même.
- **C6. Simple à déployer et à tester** : pas de service de plus sans besoin, testable sur un vrai moteur (`test/isolation/network.test.ts`).

## Options

### Point 1 — Sortir d'un conteneur sans réseau

| Option | Pour | Contre |
|---|---|---|
| **a. Socket Unix monté + relais local** (retenue) | `--network none` reste vrai (C1) : aucune interface hors `lo`. Le socket est un fichier : le monter suffit. | Un relais dans le conteneur. Il tient en une ligne de Node, déjà dans l'image : c'est le PID 1 du conteneur. |
| b. Un réseau interne du moteur, avec le proxy seul dessus | Pas de relais. | Le conteneur a une interface et un DNS : une erreur de réglage du réseau rouvre la sortie. Contraire au doc. |

Mesuré ici : un socket créé sur un hôte Windows ne passe pas dans la VM de Docker Desktop. Le démon est sous Linux de toute façon (les sandboxes l'exigent). Le test d'isolation fait donc tourner le proxy dans un conteneur à lui, du côté du moteur.

### Point 2 — La brique

| Option | Pour | Contre |
|---|---|---|
| **a. Proxy Node de l'usine, dans le démon** (retenu) | Environ 200 lignes sans dépendance. Un socket par run, ouvert et fermé avec le conteneur. Règles par méthode et chemin dans le même code que les niveaux. Testé en unitaire et sur un vrai moteur. | Code de sécurité à nous. Il tourne dans le processus du démon : une faille du proxy est une faille du démon. |
| b. smokescreen (Stripe, Go) | Éprouvé, liste d'hôtes, refus des adresses privées. | Liste par hôte seulement (`CONNECT`) : C4 non tenu. Un service de plus, une identité par run à faire passer (en-tête ou certificat client). |
| c. Envoy | Tout est possible (filtres HTTP, TLS). | Lourd à configurer et à faire évoluer par run ; un service de plus. Ne voit pas non plus dans TLS sans interception. |

Ni smokescreen ni Envoy ne règlent le point 4 seuls. Le proxy Node tient les critères avec le moins de pièces. Il peut passer dans un service `proxy` de `compose.yaml` (ORC-203) sans changer le conteneur : seul le chemin du socket change.

### Point 4 — Voir les méthodes

| Option | Pour | Contre |
|---|---|---|
| a. Hôte seulement, partout | Le plus simple. | `git push`, gist et `npm publish` passent : C4 non tenu. |
| **b. Hôtes à API d'écriture en `http://`, le proxy continue en HTTPS** (retenue) | C4 tenu sans autorité ni certificat. git (`url.<http>.insteadOf`), npm (`npm_config_registry`) et pip (`PIP_INDEX_URL`) se règlent par variables d'environnement, posées par le sandbox. Un outil qui force `https://` vers ces hôtes est **refusé** (le proxy ne les tunnelle jamais) : l'erreur est du côté sûr. | Les autres hôtes permis (docs, téléchargements, `network.allow`) restent au niveau de l'hôte. Le `WebFetch` de Claude Code ne lit pas GitHub (il passe en HTTPS). Le jeton GitHub de l'agent passe en clair dans le socket local, jusqu'au proxy. |
| c. Interception TLS (MITM) par une autorité de l'usine | Méthodes et chemins vus partout. | Une autorité de l'usine à créer, garder et faire reconnaître dans l'image (`NODE_EXTRA_CA_CERTS`, git, pip) ; des certificats par hôte à générer (une dépendance, Node ne sait pas en signer) ; l'API Claude à exclure. **C'est un choix humain** : point ouvert. |

## Ce qui est appliqué

- **Conteneur** (`src/adapters/sandbox/docker-rootless.ts`) : toujours `--network none`. Avec le proxy, il monte le socket du run en `/run/factory/egress.sock`, lance le relais en PID 1 et pose `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY=localhost,127.0.0.1`, `NODE_USE_ENV_PROXY=1` (le `fetch` de Node, donc `factory-agent`), et les formes `http://` de git, npm et pip. Sans proxy, rien ne sort.
- **Niveaux** (`src/network/levels.ts`) : une étape resserre seulement le niveau du dépôt, `full` est refusé à l'agent, `custom` ajoute `network.allow` au niveau `limited`.
- **Proxy** (`src/network/proxy.ts`) :
  - `CONNECT` vers le port 443 seulement (sauf en `full`), aux hôtes tunnelés ;
  - HTTP en clair vers le port 80, renvoyé en HTTPS (en `full`, tel quel) : méthode et chemin vérifiés ;
  - GitHub, npm et PyPI : GET, HEAD et OPTIONS, plus le POST de `git fetch` (`git-upload-pack`) ; `service=git-receive-pack` refusé ;
  - aucune adresse privée, même en `full`, même par un nom qui y mène (résolution vérifiée) ;
  - l'API agent (`FACTORY_API`) relayée vers le démon, qui n'écoute plus que sur la boucle locale ;
  - la télémétrie de Claude Code (`statsig`, Sentry…) refusée : seul `api.anthropic.com` est permis (ORC-128, point 3).
- **Runs** : tous en `limited`, le défaut du doc (`src/core/orchestrator.ts`).

## Points ouverts

1. **Interception TLS** (point 4 c) : à trancher par un humain. Sans elle, un POST vers un hôte tunnelé passe (docs, téléchargements, `network.allow` du dépôt).
2. **`network` du dépôt et niveau par étape au lancement** : la config du dépôt n'est lue au lancement qu'avec ORC-209 C. D'ici là, tous les runs sont en `limited`, `allow` vide. Le `setup` tourne dans le conteneur du run, à son niveau, pas en `full`.
3. **Dépôt en `none`** : le doc dit « rien, sauf l'API Claude pour une étape qui appelle l'agent ». `repoNetworkCeiling` donne `none`, et le préréglage `factory/default` est alors refusé (comportement d'ORC-209, inchangé ici). À revoir avec le préréglage par dépôt.
4. **Journal en base et au tableau de bord** : aujourd'hui un JSONL par run. Une table et sa migration viendront avec l'écran du journal de sécurité (ticket à ouvrir).
5. **Liste des domaines de doc** : une première liste courte dans `levels.ts` (MDN, Node, npm, TypeScript, Python, GitHub Docs). À compléter à l'usage.
6. **Podman rootless** : le test d'isolation n'a tourné que sous Docker Desktop. Le job CI (ORC-218) le passera sous Podman.
