# ORC-213 — Sandbox egress proxy: which component, and what does it see?

## Decision

**2026-11-02 — points 1 to 3 and 5 proposed by the ticket's session. 2026-11-03 — point 4 decided by the dev: TLS interception, in this PR.**

| Point | Option adopted |
|---|---|
| 1. How does the container get out, under `--network none`? | **Through one Unix socket per run**, mounted in the container, with a local relay (`127.0.0.1:3128`) in front of it. `HTTP(S)_PROXY` point to the relay. |
| 2. Which proxy component? | **A factory proxy in Node** (`src/network/proxy.ts`), in the daemon. Neither smokescreen nor Envoy. |
| 3. How do we know which run a connection comes from? | **One socket per run**: the log knows the run without trusting what the container sends. |
| 4. Methods towards an HTTPS host? | **TLS interception** by a factory authority (2026-11-03, the dev): each tunnel is decrypted, each request checked (method, path), for all allowed hosts. Certificates signed by **`node-forge` 1.4.0**, exact version. |
| 5. The log? | **One JSONL per run** in `<home>/network/`, until the database and the dashboard. |

## The question

The MVP doc (N2) wants a runner under `--network none`, with "only the factory proxy's socket mounted": no DNS, UDP and QUIC cut off, every connection logged. The proxy applies the step's level:

- **None**: nothing, except the Claude API for a step that calls the agent;
- **Limited** (default): Claude API, npm and PyPI registries, doc domains, GitHub read-only; **GET, HEAD and OPTIONS methods only**, except towards the Claude API;
- **Custom**: Limited plus the repository's `network.allow`;
- **Full**: everything, reserved for `setup`.

The ticket leaves the choice of component open (smokescreen or Envoy). There is also a hidden constraint: method restriction. An HTTP proxy sees an HTTPS request as a `CONNECT host:443` followed by encrypted TLS. It sees neither the method nor the path. Acceptance criterion 2 ("a `git push` or a gist creation refused") therefore does not hold with a simple per-host filter.

Before this ticket, the container had the engine's bridge, open to the Internet ("provisional open network", ORC-204).

## Criteria

- **C1. No egress outside the proxy**: no route, no DNS, no UDP, whatever the tool (a tool that ignores `HTTPS_PROXY` has no network at all).
- **C2. The level applied out of the agent's reach**: nothing in the container chooses its level.
- **C3. Per-run log**: host, method, path, size, refusals.
- **C4. Writes refused** towards GitHub, the registries and any allowed host (the ticket's criterion 2): this is where an agent would exfiltrate code (push, gist, publish, form).
- **C5. The agent keeps its tools**: npm, Yarn, pip, git read-only, `factory-agent` and the factory's MCP server, `claude` itself.
- **C6. Simple to deploy and test**: no extra service without need, testable on a real engine (`test/isolation/network.test.ts`).

## Options

### Point 1 — Getting out of a container with no network

| Option | For | Against |
|---|---|---|
| **a. Mounted Unix socket + local relay** (adopted) | `--network none` stays true (C1): no interface besides `lo`. The socket is a file: mounting it is enough. | A relay in the container. It fits in one line of Node, already in the image: it is the container's PID 1. |
| b. An internal engine network, with only the proxy on it | No relay. | The container has an interface and DNS: a network misconfiguration reopens egress. Contrary to the doc. |

Measured here: a socket created on a Windows host does not pass into the Docker Desktop VM. The daemon runs on Linux anyway (sandboxes require it). The isolation test therefore runs the proxy in a container of its own, on the engine side.

### Point 2 — The component

| Option | For | Against |
|---|---|---|
| **a. Factory Node proxy, in the daemon** (adopted) | A few hundred lines. One socket per run, opened and closed with the container. Per-method and per-path rules in the same code as the levels. Unit-tested and tested on a real engine. | Security code of our own. It runs in the daemon process: a proxy flaw is a daemon flaw. |
| b. smokescreen (Stripe, Go) | Battle-tested, host list, refusal of private addresses. | Per-host list only (`CONNECT`): C4 not met. One more service, a per-run identity to pass along. |
| c. Envoy | Anything is possible (HTTP filters, TLS). | Heavy to configure and to evolve per run; one more service. |

**2026-11-05, ORC-203:** the Node proxy moves into the `proxy` service of `compose.yaml`, without changing the container; the daemon drives it through a control socket (`src/network/proxy-service.ts`). smokescreen and Envoy remain ruled out for the reasons in this table. Outside compose, the proxy stays in the daemon process.

### Point 4 — Seeing the methods

| Option | For | Against |
|---|---|---|
| a. Host only, everywhere | The simplest. | `git push`, gist and `npm publish` get through: C4 not met. |
| b. Hosts with a write API over `http://`, the proxy continues in HTTPS (proposed on 2026-11-02) | C4 met for GitHub, npm and PyPI without an authority. | Docs, downloads and `network.allow` stay at host level: a POST gets through. Two mechanisms, and per-tool variables (`insteadOf`, registry, index). |
| **c. TLS interception by a factory authority** (adopted) | Method and path seen for **every** allowed host: C4 met everywhere. A single mechanism: the `http://` redirections of (b) are removed. | An authority to create and safeguard (its key is a daemon secret), trusted in the container through variables; a dependency to sign certificates. A client that pins a certificate fails. |

### Point 4 bis — The certificate library

Node generates keys (`crypto.generateKeyPairSync`) and reads certificates (`X509Certificate`), but does not sign X.509.

| Option | For | Against |
|---|---|---|
| **`node-forge`** (adopted, exact `1.4.0`, published in March 2026) | A single package, **no dependencies**, very widespread (X.509 signing, SAN extensions, AKI/SKI). | RSA in JavaScript, slow at generating: we only make it **sign**, the keys come from Node's `crypto`. History of flaws in its ASN.1: the adopted version follows the 2025 fixes. |
| `@peculiar/x509` | Modern API, WebCrypto. | Several dependencies (`asn1-*`, `tsyringe`, `reflect-metadata`, `pvtsutils`). |
| `openssl` as a subprocess | Nothing to install on the npm side. | Not on every host, one process per host, temporary files. |

## What is applied

- **Container** (`src/adapters/sandbox/docker-rootless.ts`): always `--network none`. With the proxy, it mounts the run's socket at `/run/factory/egress.sock` and the authority's **certificate** read-only at `/run/factory/egress-ca.crt` (never its key). It launches the relay as PID 1 and sets `HTTP(S)_PROXY` (and Yarn's), `NO_PROXY=localhost,127.0.0.1`, `NODE_USE_ENV_PROXY=1` (Node's `fetch`: `factory-agent`), and the authority as the only trust: `NODE_EXTRA_CA_CERTS` (Claude Code, npm, Yarn), `SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`, `PIP_CERT`, `GIT_SSL_CAINFO`, `npm_config_cafile`, `YARN_CAFILE`, `YARN_HTTPS_CA_FILE_PATH`. The image does not change. Without the proxy, nothing gets out.
- **Isolation test**: on Linux (CI, the server), the proxy runs in the test process, as in the daemon, its socket mounted in the container. Elsewhere (Docker Desktop on Windows or macOS), in a container of its own. This second setup does not work under rootless Podman: the socket there belongs to a sub-uid of the container's namespace, which the sandbox's `keep-id` user cannot open (measured in CI: `ECONNRESET`, empty log).
- **After a daemon restart**, a live container has a dead socket (the mount holds a deleted inode): the provider no longer returns it (`findByAttempt`), destroys it and makes a new one. *Changed by ORC-220: the container mounts the socket's directory, read-only, at `/run/factory/egress`; the daemon puts the socket back there, and `reattach` takes over the container of an attempt in progress.*
- **Authority** (`src/network/ca.ts`): created on the first sandboxed run, in `<home>/egress-ca/` (`ca.key` in `0600`, in a `0700` directory). RSA 2048, ten years, `pathLenConstraint: 0`. One certificate per host (SAN = the host), signed on demand, kept 7 days in memory (valid for 30), a single key for all.
- **Levels** (`src/network/levels.ts`): a step can only tighten the repository's level, `full` is refused to the agent, `custom` adds `network.allow` (lowercased) to the `limited` level.
- **Proxy** (`src/network/proxy.ts`):
  - `CONNECT` to port 443 only, to the level's hosts; under `full`, another port is relayed as is over TCP (private addresses always refused, host, port and bytes logged);
  - the `CONNECT` host normalized once (lowercase, no trailing dot): lists, certificate, SNI, `Host`, log and agent API all see the same spelling;
  - the `CONNECT` on 443 **decrypted**: ALPN `http/1.1` only (an HTTP/2-only client is refused), an upgrade (WebSocket) or anything that is not HTTP is refused and logged;
  - each request checked against the `CONNECT` host, never against its `Host` header (no *domain fronting*), then sent over TLS to that host, **certificate verified** by Node's store, `Host` reset to the verified host;
  - GET, HEAD and OPTIONS everywhere; plus the POST of `git fetch` (`git-upload-pack` on `github.com`); `service=git-receive-pack` refused; the Claude API keeps all its methods (*changed by ORC-337: only Claude Code's calls, method and path, get through, and the proxy sets the run's token on them in place of the client's credentials, see [interface-and-security.md](../interface-and-security.md#sandbox-network)*); Claude Code's OAuth refresh (POST `/v1/oauth/token` on `console.anthropic.com` and `platform.claude.com`, not measured: ORC-128 only saw `api.anthropic.com` with a long-lived token; *removed by ORC-337: the sandbox holds no refresh token*);
  - plain HTTP: checked the same way, forwarded over HTTPS (under `full`, as is);
  - no private address, even under `full`, even via a name that leads to one: private networks, loopback, `169.254.0.0/16`, `100.64.0.0/10`, `192.0.0.0/24`, `198.18.0.0/15`, multicast and reserved, local IPv6, NAT64 (`64:ff9b::/96`), 6to4 (`2002::/16`), mapped IPv4;
  - the agent API (`FACTORY_API`, including the factory's MCP server at `/agent/mcp`) relayed to the daemon, in plaintext or through an undecrypted tunnel; the daemon now only listens on loopback;
  - Claude Code telemetry refused: its hosts are on no list (ORC-128, point 3);
  - the log is written through one stream per run: a failing write is reported to the daemon log, never thrown; a response cut upstream in the middle of the body cuts the client's and is logged as a failure; the upstream request dies with the client's; when the run closes, whatever was in progress is logged before the log ends; logs are purged after 30 days, along with the transcripts;
  - an open run keeps its policy: reopening it with another one (level, `allow`) is refused, since the container's mount holds that socket; two simultaneous openings share the same one.
- **Runs**: all under `limited`, the doc's default (`src/core/orchestrator.ts`, `ponytail` comment): `stepPolicy` has no production caller yet.

## Remaining risks

1. **The authority's key is a daemon secret.** Whoever reads it can impersonate any site to the sandboxes of this instance (and only to them). It is never mounted; a run without a sandbox, on the host, can read it like `secrets.json`.
2. **A client that pins a certificate**, or that ignores the authority variables, fails: closed by default, logged.
3. **Redirections**: a redirection to a host outside the level is refused (renamed GitHub repository, package served by another CDN).
4. **The proxy runs in the daemon, outside compose**: a flaw in its HTTP or TLS parsing (Node) is a daemon flaw there. Under compose (ORC-203), it stays in the `proxy` service, which holds the authority's key but none of the daemon's secrets, apart from the Claude token of each open run, in memory (ORC-337).

## Open points

1. **The repository's `network` and the per-step level at launch**: decided by ORC-209 C for the repository (each agent run takes `stepPolicy(config)`, `agentPolicy` in `levels.ts`). The per-step level waits for ORC-322: the review skill runs `gh` and `git fetch`, which `claude-api` would cut off.
2. **`setup` under `full`**: since ORC-211, it runs in a container of its own, destroyed before the agent's, but still under `limited`: it holds the repository's secrets there, and `full` would open every egress to them. A `setup` that goes beyond the lists fails.
3. **Repository under `none`**: the doc says "nothing, except the Claude API for a step that calls the agent". Decided by ORC-209 C: its agent runs run under `claude-api`. `repoNetworkCeiling` always yields `none`, and `compilePreset` then refuses the `factory/default` preset; nothing at launch calls it yet.
4. **Log in the database and on the dashboard**: today one JSONL per run. A table and its migration will come with the security log screen (ticket to be opened).
5. **List of doc domains**: a first short list in `levels.ts`. To be completed with use.
6. **Rootless Podman**: the network isolation test has only run under Docker Desktop. The CI job `isolation` will run it under Podman.
