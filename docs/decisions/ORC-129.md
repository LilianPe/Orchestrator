# ORC-129 : inbox + outbox maison ou DBOS Transact

## Décision

Date : 2026-10-22. Retenue par le dev : toutes les recommandations de cette page. La décision est aussi écrite dans le ticket [ORC-129](https://linear.app/liliantest/issue/ORC-129).

| Point | Option retenue |
|---|---|
| 1. Option A ou B | **A : inbox + outbox maison sur Postgres.** |
| 2. Bail et backoff de l'outbox (ORC-150) | Bail de 60 s renouvelé toutes les 20 s tant que l'effet tourne ; baux libérés au démarrage du serveur ; backoff `1 s × 2^(essai − 1)` plafonné à 5 min ; dead-letter après 8 essais. |
| 3. Ordre ORC-162 / ORC-150 | L'idempotence par effet (ORC-162) arrive avec l'outbox (ORC-150). |
| 4. DBOS pour ORC-220 | Fermé pour le MVP ; à rouvrir seulement si ORC-220 décrit un vrai workflow à plusieurs étapes. |

La suite de la page est la proposition que le dev a relue (les options, les critères, les preuves du spike et la recommandation), mise à jour après sa décision et après la review de la PR.

## La question

Le moteur v2 doit garantir qu'un `kill -9` à n'importe quel moment ne perd ni un événement ni un effet. Faut-il écrire nous-mêmes l'inbox, l'outbox et les timers sur Postgres, ou s'appuyer sur DBOS Transact (bibliothèque TypeScript de workflows durables sur Postgres) ?

Temporal et LangGraph sont écartés comme cœur par le doc MVP : ils ne sont pas évalués ici.

Je n'ai pas pu ouvrir le doc MVP (artefact claude.ai, hors de portée de la session). La page s'appuie sur ORC-129 et les tickets qu'il bloque. Deux phrases de ces tickets, reprises du doc, orientent déjà vers l'option maison : « l'usine a ses propres tables inbox, outbox et timers » (ORC-132) et « Pg-boss n'est pas utilisé » (ORC-132). Si le doc dit autre chose de DBOS, il faut le relire avant de trancher.

## Les options

**A. Maison sur Postgres.** Les tables `inbox`, `journal`, `tickets` (projection) et `outbox` ; le worker prend `pg_try_advisory_xact_lock` sur un ticket qui a des lignes en attente, puis lit sa ligne d'inbox la plus ancienne, appelle `decide`, écrit journal + projection + outbox dans une transaction ; les exécuteurs réclament l'outbox avec `FOR UPDATE SKIP LOCKED`, un bail et un backoff, et renvoient leur résultat dans l'inbox. C'est le modèle que décrivent ORC-147, ORC-149, ORC-150 et ORC-161, sauf l'ordre du verrou et de la lecture dans ORC-149 (voir sa ligne plus bas).

**B. DBOS Transact** (`@dbos-inc/dbos-sdk` 5.3.0, licence MIT). Un workflow durable par événement, dont l'id est celui de l'événement (ce qui remplace l'inbox) ; une transaction DBOS appelle `decide` et écrit journal + projection, DBOS y enregistre sa sortie ; chaque effet est une étape DBOS (`DBOS.runStep`) avec ses réessais ; le résultat repart comme un nouveau workflow `effect:<id>`. Une file DBOS partitionnée par ticket (`partitionConcurrency: 1`) remplace le verrou par ticket.

## Les critères

1. **Le critère du ticket : rejeu des journaux et pureté de `decide` intacts.**
2. Après un `kill -9` en plein effet : l'événement n'est pas perdu, l'effet est appliqué une seule fois.
3. Ce que l'option impose à la logique de décision (décorateurs, appels au framework).
4. Code à écrire et à maintenir.
5. Dépendances et licences.
6. Ce que ça change pour ORC-132, ORC-147, ORC-149, ORC-150, ORC-161.

## Le spike

Deux prototypes jetables dans [`spikes/orc-129/`](../../spikes/orc-129/README.md), chacun avec son `package.json`, hors de `src/`, de la CI et de `npm test`. **Ils ne doivent pas être repris tels quels** : un ticket, une sorte d'effet, aucun test, aucune gestion d'erreur sérieuse.

Même scénario pour les deux, sur un Postgres 17 jetable (`postgres:17-alpine`, conteneur arrêté après la mesure) :

1. le webhook de délégation arrive **deux fois** avec le même id de livraison ;
2. `decide` (une copie minimale et pure, [`shared/decide.ts`](../../spikes/orc-129/shared/decide.ts), commune aux deux) rend l'effet « poster un commentaire » ;
3. l'effet appelle une fausse API externe ([`shared/fake-api.ts`](../../spikes/orc-129/shared/fake-api.ts)) qui **applique le commentaire dès réception puis retient sa réponse 3 s** : c'est la fenêtre dangereuse, l'effet est fait dehors mais son résultat n'est pas revenu ;
4. `kill -9` du worker dans cette fenêtre, puis redémarrage ;
5. comptage des appels reçus et des commentaires appliqués côté API ;
6. rejeu du journal à travers `decide`, décision par décision, comparé au journal enregistré ;
7. contrôle négatif du rejeu : une décision enregistrée est falsifiée, le rejeu doit la signaler.

Deux variantes de contrôle : l'API **ignore la clé d'idempotence** (`IGNORE_IDEMPOTENCY=1`), et, pour DBOS, **un déploiement de code neuf** entre le crash et la reprise (`WORKER2_ENV=DBOS__APPVERSION=v2`, une version d'application forcée).

Commande : `bash spikes/orc-129/shared/run-all.sh`. Sorties complètes : `spikes/orc-129/results/<variante>/run.txt`. Le délai de reprise est chronométré du lancement du worker 2 jusqu'au ticket `done` lu en base (une même sonde `psql` pour les deux options) : il compte donc aussi le démarrage de Node et, pour DBOS, son `launch` et l'intervalle de sondage de sa file (1 s par défaut). L'écart entre les deux appels reçus par l'API, tiré de ses horodatages, isole la reprise de l'effet lui-même.

### Comment « une seule fois » a été vu

Par le journal de la fausse API (`fake-api.jsonl`, recopié dans `run.txt`). Option A :

```text
{"type":"received","key":"ORC-1:1:0", ...}
{"type":"applied","key":"ORC-1:1:0","commentId":"comment-1"}       ← worker 1, tué juste après
{"type":"received","key":"ORC-1:1:0", ...}                          ← worker 2, à l'expiration du bail (5 s)
{"type":"deduplicated","key":"ORC-1:1:0","commentId":"comment-1"}
{"received":2,"applied":1}
```

Option B, même forme : DBOS relance l'étape non terminée au démarrage du worker 2, l'API reconnaît la clé.

Ce que le rejeu vérifie : `decide` est rappelé sur chaque événement du journal, à partir de l'état qu'il a lui-même reconstruit, et sa décision (état et effets avec leurs ids) est comparée à celle enregistrée. Le contrôle négatif ne falsifie qu'un champ d'état (`commentId` de la décision 2) : un écart sur les effets n'est pas testé à part, mais passe par la même comparaison.

**Les deux options sont « au moins une fois », pas « exactement une fois ».** Dans les deux cas l'effet est **appelé deux fois** ; c'est la clé d'idempotence (l'id de l'effet `ticket:seq:i`, envoyé en `Idempotency-Key`) qui fait qu'il n'est **appliqué qu'une fois**. Sans elle, les deux options postent deux commentaires (variantes « sans idempotence » : 2 / 2). DBOS le dit d'ailleurs de ses étapes : « This ensures "at least once" execution of the step » (`dbos-sdk/dist/src/dbos.d.ts`, doc de `registerStep`). L'idempotence par effet (ORC-162) est donc requise dans les deux cas : DBOS ne l'apporte pas.

### Ce que DBOS rejoue, et ce qu'il ne rejoue pas

Au redémarrage, DBOS réexécute la fonction de workflow depuis le début et rend, pour chaque étape déjà terminée, la sortie enregistrée. Le log du worker 2 le montre (`results/dbos/run.txt`) :

```text
[dbos 40947] worker up
[dbos 40947] decided linear:delivery-1 -> 1 effect(s)   ← le corps du workflow repasse
[dbos 40947] executing ORC-1:1:0                          ← l'étape non terminée est relancée
[dbos 40947] effect ORC-1:1:0 done -> comment-1
[dbos 40947] decided effect:ORC-1:1:0 -> 0 effect(s)
```

La transaction `decideTx` n'est pas réexécutée : DBOS rend sa sortie enregistrée, et le journal n'a que deux lignes (une réexécution aurait buté sur la clé unique `event_id`). DBOS garde sa propre trace dans `dbos.operation_outputs` (extrait de `status.json`, recopié dans `run.txt`) :

```text
linear:delivery-1  0  decideTx          [{"id":"ORC-1:1:0","effect":{...}}]
linear:delivery-1  1  effect:ORC-1:1:0  {"commentId":"comment-1"}
linear:delivery-1  2  handleEvent       (démarrage du workflow effect:ORC-1:1:0)
```

C'est un journal d'exécution (sorties d'étapes sérialisées en `superjson`, rangées par workflow et numéro d'étape), pas le journal métier : le rejeu de `decide` se fait, dans les deux options, sur **notre** table `journal`.

### Le piège mesuré : un déploiement pendant un effet en vol (DBOS)

DBOS calcule une **version d'application** : un hash MD5 du source des fonctions de workflow enregistrées, de la version de DBOS et du nom de l'application (`computeAppVersion`, `dbos-sdk/dist/src/dbos-executor.js`). Il ne reprend au démarrage que les workflows de sa version. Le hash ne couvre pas `decide`, la transaction ni le corps de `runEffect` (`shared/effects.ts`) : un déploiement qui ne change que ceux-là reprend normalement. Il change dès qu'on modifie le source d'une fonction de workflow, y compris l'appel d'étape écrit dedans (son nom, ses réessais, son backoff : `DBOS.runStep` dans `handleEvent`), ou qu'on monte de version DBOS.

Variante `dbos-nouveau-code` : worker 1 tué en plein effet, worker 2 démarré avec une autre version, **simulée en forçant `DBOS__APPVERSION=v2`** (pas un vrai changement de code). Extrait de `results/dbos-nouveau-code/run.txt` :

```text
=== worker 2 restarts (env: DBOS__APPVERSION=v2)
TICKET NOT DONE 20 s after restart
{"received":1,"applied":1}
 "workflows": [ { "workflow_uuid": "linear:delivery-1", "status": "PENDING",
                  "application_version": "5f5c3c1b801a8ca7340632e5c090cf9e", "executor_id": "local", "recovery_attempts": "1" } ]
--- worker-2.log
[dbos 43433] worker up
```

Le workflow reste `PENDING` sans être repris : le ticket reste `acknowledging`, l'effet n'est pas relancé. DBOS a des parades : fixer `applicationVersion` dans la config (une ligne, mais on perd alors la protection contre un workflow modifié rejoué avec ses anciennes sorties d'étapes), `DBOS.patch()` dans le code du workflow, ou `DBOS.forkWorkflow` pour relancer un workflow sur la nouvelle version. Il faut en choisir une et l'outiller. Dans l'option A, un effet en vol n'est qu'une ligne d'outbox que le code neuf reprend : c'est vrai par construction, **pas mesuré** (pas de variante « code neuf » pour A).

### `decide` est-il resté pur ?

Oui, dans les deux options. `shared/decide.ts` n'importe rien, ne lit ni horloge ni hasard ; `decide` n'attribue pas les ids d'effets (le fichier définit le format `effectId`, mais c'est le journal, `shared/journal.ts`, qui l'appelle). **DBOS n'impose aucun décorateur ni aucun appel dans `decide`** : l'API fonctionnelle (`DBOS.registerWorkflow`, `DBOS.runStep`, `datasource.registerTransaction`) s'applique à la coquille autour (`dbos/main.ts`), pas à la logique de décision.

DBOS impose en revanche des règles à la coquille : la fonction de workflow doit être déterministe (elle est rejouée), tout appel externe doit passer par une étape enregistrée, et la forme de la coquille est liée à la version d'application (ci-dessus). Ces règles ne touchent pas `decide`, mais elles valent pour le code du worker et des exécuteurs.

## Analyse

- **Critère du ticket :** les deux options le tiennent. Le rejeu dépend de notre table `journal` et de la pureté de `decide`, pas de l'option : il est identique (0 écart) et sait détecter un écart (contrôle négatif) dans les deux.
- **Garantie de livraison :** identique. Pas d'événement perdu, effet appliqué une fois grâce à la clé d'idempotence, et à elle seule.
- **Ce que DBOS apporte :** des réessais d'étape et un backoff configurés en une ligne, une file avec concurrence par partition, un `sleep` durable, une reprise dès le redémarrage (sans attendre de bail), des outils pour lister, relancer ou forker un workflow.
- **Délai de reprise :** dans l'option A, le spike, qui ne libère pas les baux au démarrage, attend l'expiration du bail (second appel 5,1 s après le premier, avec un bail de 5 s). DBOS reprend dès le démarrage parce que le processus redémarré se reconnaît (`executor_id = local`). La décision (point 2) fait de même pour l'option A sur le serveur unique du MVP : au démarrage, il libère tous les baux, puisqu'aucun autre exécuteur n'existe. Cela repose sur la même hypothèse d'un seul processus que la reprise de DBOS au démarrage.
- **Ce que DBOS coûte :** un deuxième journal (d'exécution) à côté du nôtre ; 15 tables et des migrations qui ne passent pas par Drizzle ; une version d'application qui bloque les effets en vol à chaque déploiement qui touche une fonction de workflow ou la version de DBOS, si on ne l'outille pas ; un vocabulaire (workflow, step, queue, partition) qui ne recoupe pas celui des tickets (inbox, outbox, `ticket:seq:i`, bail) ; une dépendance jeune qui change chaque semaine.
- **La forme de notre moteur réduit l'intérêt de DBOS.** Notre « workflow » est la machine d'état de `decide`, rejouée depuis notre journal ; chaque événement ne donne qu'une transaction suivie de quelques effets indépendants. Avec DBOS, on se servirait d'un moteur de workflows comme d'une outbox, sans profiter de ce qu'il fait le mieux : des workflows longs, à plusieurs étapes, écrits comme du code séquentiel.

## Recommandation

**Option A : inbox + outbox maison sur Postgres.**

Les garanties mesurées sont les mêmes, `decide` reste pur dans les deux cas, et l'option A colle aux tickets tels qu'ils sont écrits. Elle garde un seul schéma (Drizzle), un seul journal, et pas de piège de version au déploiement. Le code à écrire est petit : le prototype tient en 138 lignes, plus le journal et le rejeu communs. Ce qui reste à écrire (dead-letter, heartbeat de bail, métriques) l'est de toute façon, en partie, dans les tickets liés. DBOS mérite d'être regardé de nouveau si un jour un effet devient un vrai workflow à plusieurs étapes (par exemple la supervision des tentatives d'agent, ORC-220), pas pour l'outbox.

## Points tranchés

Les points 1 à 4 sont tranchés : la réponse retenue pour chacun est dans le tableau de la [décision](#décision). Le point 5 reste ouvert. Ci-dessous, les points tels qu'ils ont été soumis au dev.

1. **Option A ou B.** Recommandation : A.
2. **Bail et backoff de l'outbox (ORC-150)**, que le doc ne fixe pas. Proposition : bail de 60 s renouvelé toutes les 20 s par l'exécuteur tant que l'effet tourne (un run d'agent dure des heures : un bail fixe court le ferait reprendre en double, un bail fixe long retarderait la reprise d'un exécuteur mort) ; au démarrage du serveur unique du MVP, libérer tous les baux, pour ne pas attendre 60 s ; backoff `1 s × 2^(essai − 1)` plafonné à 5 min ; dead-letter après 8 essais (ORC-175). Le spike utilisait 5 s sans heartbeat, juste pour mesurer vite.
3. **Ordre ORC-162 / ORC-150** : faire arriver l'idempotence par effet avec l'outbox (recommandé, vu les variantes « sans idempotence »), ou accepter des doublons d'effets entre les deux.
4. **Revoir DBOS plus tard pour la supervision des tentatives d'agent (ORC-220)**, ou fermer la question pour le MVP. Recommandation : la fermer pour le MVP, et la rouvrir seulement si ORC-220 décrit un vrai workflow à plusieurs étapes.
5. **Le doc MVP** (ouvert) : je n'ai pas pu le lire. Si sa section « Mécanismes de sûreté » attend de DBOS quelque chose qui n'est pas dans les tickets, cette page ne l'a pas évalué.
