# ORC-129: home-made inbox + outbox or DBOS Transact

## Decision

Date: 2026-10-22. Adopted by the dev: all the recommendations on this page. The decision is also written in ticket [ORC-129](https://linear.app/liliantest/issue/ORC-129).

| Point | Option adopted |
|---|---|

## The question

The v2 engine must guarantee that a `kill -9` at any moment loses neither an event nor an effect. Should we write the inbox, the outbox and the timers on Postgres ourselves, or rely on DBOS Transact (a TypeScript library of durable workflows on Postgres)?

Temporal and LangGraph are ruled out as the core by the MVP doc: they are not evaluated here.

I could not open the MVP doc (a claude.ai artifact, out of the session's reach). The page relies on ORC-129 and the tickets it blocks. Two sentences from these tickets, taken from the doc, already point to the home-made option: "the factory has its own inbox, outbox and timers tables" (ORC-132) and "Pg-boss is not used" (ORC-132). If the doc says something else about DBOS, it must be reread before deciding.

## The options

**A. Home-made on Postgres.** The tables `inbox`, `journal`, `tickets` (projection) and `outbox`; the worker takes `pg_try_advisory_xact_lock` on a ticket that has pending rows, then reads its oldest inbox row, calls `decide`, writes journal + projection + outbox in one transaction; the executors claim the outbox with `FOR UPDATE SKIP LOCKED`, a lease and a backoff, and send their result back into the inbox. This is the model described by ORC-147, ORC-149, ORC-150 and ORC-161, except for the order of the lock and the read in ORC-149 (see its row below).

**B. DBOS Transact** (`@dbos-inc/dbos-sdk` 5.3.0, MIT license). One durable workflow per event, whose id is the event's (which replaces the inbox); a DBOS transaction calls `decide` and writes journal + projection, and DBOS records its output there; each effect is a DBOS step (`DBOS.runStep`) with its retries; the result goes back as a new workflow `effect:<id>`. A DBOS queue partitioned by ticket (`partitionConcurrency: 1`) replaces the per-ticket lock.

## The criteria

1. **The ticket's criterion: journal replay and purity of `decide` intact.**
2. After a `kill -9` in the middle of an effect: the event is not lost, the effect is applied only once.
3. What the option imposes on the decision logic (decorators, framework calls).
4. Code to write and maintain.
5. Dependencies and licenses.
6. What it changes for ORC-132, ORC-147, ORC-149, ORC-150, ORC-161.

## The spike

Two throwaway prototypes in [`spikes/orc-129/`](../../spikes/orc-129/README.md), each with its own `package.json`, outside `src/`, the CI and `npm test`. **They must not be reused as is**: one ticket, one kind of effect, no tests, no serious error handling.

Same scenario for both, on a throwaway Postgres 17 (`postgres:17-alpine`, container stopped after the measurement):

1. the delegation webhook arrives **twice** with the same delivery id;
2. `decide` (a minimal, pure copy, [`shared/decide.ts`](../../spikes/orc-129/shared/decide.ts), shared by both) returns the effect "post a comment";
3. the effect calls a fake external API ([`shared/fake-api.ts`](../../spikes/orc-129/shared/fake-api.ts)) that **applies the comment on receipt then holds its response for 3 s**: this is the dangerous window, the effect is done outside but its result has not come back;
4. `kill -9` of the worker in this window, then restart;
5. count of the calls received and comments applied on the API side;
6. replay of the journal through `decide`, decision by decision, compared with the recorded journal;
7. negative control of the replay: a recorded decision is tampered with, the replay must report it.

Two control variants: the API **ignores the idempotency key** (`IGNORE_IDEMPOTENCY=1`), and, for DBOS, **a deployment of new code** between the crash and the recovery (`WORKER2_ENV=DBOS__APPVERSION=v2`, a forced application version).

Command: `bash spikes/orc-129/shared/run-all.sh`. Full outputs: `spikes/orc-129/results/<variante>/run.txt`. The recovery delay is timed from the launch of worker 2 until the ticket is read as `done` in the database (the same `psql` probe for both options): it therefore also counts Node's startup and, for DBOS, its `launch` and its queue's polling interval (1 s by default). The gap between the two calls received by the API, taken from its timestamps, isolates the recovery of the effect itself.

### How "only once" was observed

Through the fake API's log (`fake-api.jsonl`, copied into `run.txt`). Option A:

```text
{"type":"received","key":"ORC-1:1:0", ...}
{"type":"applied","key":"ORC-1:1:0","commentId":"comment-1"}       ← worker 1, killed right after
{"type":"received","key":"ORC-1:1:0", ...}                          ← worker 2, when the lease expires (5 s)
{"type":"deduplicated","key":"ORC-1:1:0","commentId":"comment-1"}
{"received":2,"applied":1}
```

Option B, same shape: DBOS relaunches the unfinished step when worker 2 starts, and the API recognizes the key.

What the replay checks: `decide` is called again on each journal event, starting from the state it has itself rebuilt, and its decision (state and effects with their ids) is compared with the recorded one. The negative control only tampers with a state field (`commentId` of decision 2): a discrepancy in the effects is not tested separately, but goes through the same comparison.

**Both options are "at least once", not "exactly once".** In both cases the effect is **called twice**; it is the idempotency key (the effect id `ticket:seq:i`, sent as `Idempotency-Key`) that makes it **applied only once**. Without it, both options post two comments ("without idempotency" variants: 2 / 2). DBOS says so itself about its steps: « This ensures "at least once" execution of the step » (`dbos-sdk/dist/src/dbos.d.ts`, doc of `registerStep`). Per-effect idempotency (ORC-162) is therefore required in both cases: DBOS does not provide it.

### What DBOS replays, and what it does not

On restart, DBOS re-executes the workflow function from the start and returns, for each step already finished, the recorded output. Worker 2's log shows it (`results/dbos/run.txt`):

```text
[dbos 40947] worker up
[dbos 40947] decided linear:delivery-1 -> 1 effect(s)   ← the workflow body runs again
[dbos 40947] executing ORC-1:1:0                          ← the unfinished step is relaunched
[dbos 40947] effect ORC-1:1:0 done -> comment-1
[dbos 40947] decided effect:ORC-1:1:0 -> 0 effect(s)
```

The `decideTx` transaction is not re-executed: DBOS returns its recorded output, and the journal has only two rows (a re-execution would have hit the unique key `event_id`). DBOS keeps its own trace in `dbos.operation_outputs` (excerpt from `status.json`, copied into `run.txt`):

```text
linear:delivery-1  0  decideTx          [{"id":"ORC-1:1:0","effect":{...}}]
linear:delivery-1  1  effect:ORC-1:1:0  {"commentId":"comment-1"}
linear:delivery-1  2  handleEvent       (start of workflow effect:ORC-1:1:0)
```

This is an execution log (step outputs serialized with `superjson`, stored by workflow and step number), not the business journal: the replay of `decide` is done, in both options, on **our** `journal` table.

### The measured trap: a deployment during an in-flight effect (DBOS)

DBOS computes an **application version**: an MD5 hash of the source of the registered workflow functions, the DBOS version and the application name (`computeAppVersion`, `dbos-sdk/dist/src/dbos-executor.js`). On startup it only recovers workflows of its own version. The hash does not cover `decide`, the transaction or the body of `runEffect` (`shared/effects.ts`): a deployment that only changes those recovers normally. It changes as soon as the source of a workflow function is modified, including the step call written inside it (its name, its retries, its backoff: `DBOS.runStep` in `handleEvent`), or the DBOS version is upgraded.

Variant `dbos-nouveau-code`: worker 1 killed in the middle of an effect, worker 2 started with another version, **simulated by forcing `DBOS__APPVERSION=v2`** (not a real code change). Excerpt from `results/dbos-nouveau-code/run.txt`:

```text
=== worker 2 restarts (env: DBOS__APPVERSION=v2)
TICKET NOT DONE 20 s after restart
{"received":1,"applied":1}
 "workflows": [ { "workflow_uuid": "linear:delivery-1", "status": "PENDING",
                  "application_version": "5f5c3c1b801a8ca7340632e5c090cf9e", "executor_id": "local", "recovery_attempts": "1" } ]
--- worker-2.log
[dbos 43433] worker up
```

The workflow stays `PENDING` without being recovered: the ticket stays `acknowledging`, the effect is not relaunched. DBOS has countermeasures: set `applicationVersion` in the config (one line, but then you lose the protection against a modified workflow replayed with its old step outputs), `DBOS.patch()` in the workflow code, or `DBOS.forkWorkflow` to relaunch a workflow on the new version. One must be chosen and tooled. In option A, an in-flight effect is just an outbox row that the new code picks up: this is true by construction, **not measured** (no "new code" variant for A).

### Did `decide` stay pure?

Yes, in both options. `shared/decide.ts` imports nothing, reads neither clock nor randomness; `decide` does not assign effect ids (the file defines the `effectId` format, but it is the journal, `shared/journal.ts`, that calls it). **DBOS imposes no decorator and no call in `decide`**: the functional API (`DBOS.registerWorkflow`, `DBOS.runStep`, `datasource.registerTransaction`) applies to the shell around it (`dbos/main.ts`), not to the decision logic.

DBOS does, however, impose rules on the shell: the workflow function must be deterministic (it is replayed), every external call must go through a recorded step, and the shape of the shell is tied to the application version (above). These rules do not touch `decide`, but they apply to the worker and executor code.

## Analysis

- **The ticket's criterion:** both options meet it. The replay depends on our `journal` table and the purity of `decide`, not on the option: it is identical (0 discrepancies) and can detect a discrepancy (negative control) in both.
- **Delivery guarantee:** identical. No lost event, effect applied once thanks to the idempotency key, and to it alone.
- **What DBOS brings:** step retries and backoff configured in one line, a queue with per-partition concurrency, a durable `sleep`, tools to list, relaunch or fork a workflow.
- **Recovery delay:** in option A, the spike, which does not release leases at startup, waits for the lease to expire (second call 5.1 s after the first, with a 5 s lease). DBOS recovers right at startup because the restarted process recognizes itself (`executor_id = local`). The decision (point 2) does the same for option A on the MVP's single server: at startup, it releases all leases, since no other executor exists. This release assumes a single process.
- **What DBOS costs:** a second (execution) journal next to ours; 15 tables and migrations that do not go through Drizzle; an application version that blocks in-flight effects on every deployment that touches a workflow function or the DBOS version, unless it is tooled; a vocabulary (workflow, step, queue, partition) that does not match the tickets' (inbox, outbox, `ticket:seq:i`, lease); a young dependency that changes every week.
- **The shape of our engine reduces DBOS's appeal.** Our "workflow" is the state machine of `decide`, replayed from our journal; each event yields only one transaction followed by a few independent effects. With DBOS, we would use a workflow engine as an outbox, without benefiting from what it does best: long, multi-step workflows written as sequential code.

## Recommendation

**Option A: home-made inbox + outbox on Postgres.**

The measured guarantees are the same, `decide` stays pure in both cases, and option A follows the model of the linked tickets, with the changes listed in the table below. It keeps a single schema (Drizzle), a single journal, and no version trap at deployment. The code to write is small: the prototype fits in 138 lines, plus the shared journal and replay. What remains to be written (dead-letter, lease heartbeat, metrics) is partly written in the linked tickets anyway. DBOS deserves another look if one day an effect becomes a real multi-step workflow (for example the supervision of agent attempts, ORC-220), not for the outbox.

## Decided points

Points 1 to 4 are decided: the answer adopted for each is in the [decision](#decision) table. Point 5 remains open. Below, the points as they were submitted to the dev.

1. **Option A or B.** Recommendation: A.
2. **Outbox lease and backoff (ORC-150)**, which the doc does not set. Proposal: 60 s lease renewed every 20 s by the executor while the effect runs (an agent run lasts hours: a short fixed lease would make it be picked up twice, a long fixed lease would delay the recovery of a dead executor); when the MVP's single server starts, release all leases, so as not to wait 60 s; backoff `1 s × 2^(attempt − 1)` capped at 5 min; dead-letter after 8 attempts (ORC-175). The spike used 5 s without heartbeat, just to measure quickly.
3. **Order of ORC-162 / ORC-150**: make per-effect idempotency arrive with the outbox (recommended, given the "without idempotency" variants), or accept duplicate effects in between.
4. **Revisit DBOS later for the supervision of agent attempts (ORC-220)**, or close the question for the MVP. Recommendation: close it for the MVP, and reopen it only if ORC-220 describes a real multi-step workflow.
5. **The MVP doc** (open): I could not read it. If its "Mécanismes de sûreté" (safety mechanisms) section expects something from DBOS that is not in the tickets, this page has not evaluated it.
