## La question

Le doc MVP (« Les garanties du moteur ») liste 8 invariants de `decide` sur « 8 à 12, liste à compléter », et laisse vide la colonne « comportement en doublon » de la table d'idempotence des 7 effets externes. Deux tickets attendent la réponse :

- **ORC-173** teste chaque invariant par propriétés, sur 10 000 séquences d'événements avec doublons et désordre ;
- **ORC-162** rend chaque effet idempotent et teste chaque ligne de la table.

Il faut donc fixer :

1. la liste complète des invariants, chacun énoncé de façon testable par propriété ;
2. pour chacun des 7 effets, ce qui se passe quand il est exécuté deux fois, et ce que l'outbox fait du doublon.

Les invariants sont écrits sur la **cible d'ORC-133**, pas sur le code actuel : `decide(state, event, wf) → { events, effects, timers, trace }` pure, `reduce(state, event) → state`, résultats des exécuteurs revenus par l'inbox (`effect:<id>`, `attempt:<id>:finished`, `check:…`), fencing et taint dans `decide`.

**Limite de cette proposition** : le doc MVP est un artefact claude.ai que cette session n'a pas pu ouvrir. Les 8 invariants et la table de départ sont repris tels qu'ORC-173 et ORC-162 les recopient. Si le doc dit autre chose sur un point, le doc l'emporte : voir [Points tranchés](#points-tranchés), point 1.

## Critères

Dans l'ordre, ceux du ticket d'abord :

1. **Les tickets liés s'appuient sur la réponse** (critère d'acceptation d'ORC-138) : chaque invariant doit pouvoir devenir une propriété d'ORC-173, chaque ligne de la table un test d'ORC-162, sans nouvelle question.
2. **Testable par propriété** : l'énoncé porte sur une suite d'états et d'événements générée, pas sur un scénario choisi à la main ; il dit ce qui est observé (état, effets émis) après chaque pas.
3. **Couvre les promesses de l'usine** citées par ORC-173 : pas de publication sans vérification, pas de test gelé affaibli, pas de message humain perdu, boucles bornées.
4. **Tient avec « au moins une fois »** (ORC-147, ORC-150) : un événement peut arriver deux fois ou en désordre, un effet peut être exécuté deux fois.
5. **Reste dans la fourchette de 8 à 12** du doc, sans invariant redondant (un invariant qui découle d'un autre n'a pas sa propre propriété).

### Ce que le `decide` actuel fait sur les séquences qui comptent

Un script (reproduit en [annexe](#annexe--le-script-de-sondage)) appelle `decide` de `src/core/engine.ts` avec le workflow de `packs/standard`, sans orchestrateur :

```text
1. run.finished(success) du run A, run actif B -> move:human_review, post_output
2. pr.checks_failed n°1 -> start_run:fix-ci
2. pr.checks_failed n°2 -> start_run:fix-ci
2. pr.checks_failed n°3 -> start_run:fix-ci
2. pr.checks_failed n°4 -> start_run:fix-ci
2. pr.checks_failed n°5 -> start_run:fix-ci
3a. verify.passed (1er) -> patch_ticket, move:human_review, post_output
3b. verify.passed (rejoué, même état) -> patch_ticket, move:human_review, post_output
4. verify.passed du run A, vérif en cours B -> patch_ticket, move:human_review, post_output
5. session.prompted fil de dev, état ai_review -> (rien)
5. session.prompted fil de dev, état ready -> (rien)
5. session.prompted fil de dev, état todo -> (rien)
```

Ce que ça montre :

- **Aucun fencing dans `decide`** (lignes 1 et 4) : un résultat d'un run qui n'est plus actif produit les mêmes décisions qu'un résultat courant. Pour `verify.*`, c'est `handle()` qui filtre avant ; pour `run.finished`, rien ne filtre (seul `activeRunId` n'est remis à zéro que si l'id correspond, `orchestrator.ts:284`).
- **`decide` n'est pas idempotent seul** (3a, 3b) : rejoué, un événement reproduit ses effets. Tout repose sur le dédoublonnage par id en amont. C'est normal pour une fonction pure, mais ça veut dire que l'invariant « doublon sans effet » doit être porté par le couple inbox + `decide`, pas par `decide` seul.
- **La boucle CI rouge n'est pas bornée** (2), comme ORC-173 le signale déjà : la règle `pr.checks_failed` de `packs/standard/workflow.yml` relance `fix-ci` sans compteur. De plus, l'id de ces événements contient l'heure du relevé (`pr:<ticket>:<n>:checks:fail:<at>`, `src/adapters/forge/pr-poller.ts`) : deux relevés du même échec ont deux ids, et le dédoublonnage repose sur la clé `meta` `checks:<projet>:<ticket>`, hors du journal.
- **Un message humain peut ne jamais atteindre l'agent** (5) : une réponse dans le fil de dev d'un ticket en `ai_review`, `ready` ou `todo` non bloqué ne matche aucune règle `session.prompted` ; elle est écrite dans le journal mais jamais ajoutée à `pendingFeedback`. Autre perte possible : `pendingJob` est écrasé par un second `start_run` pendant un run (`orchestrator.ts:495`), et son `inputText` avec.
- **Pas de SHA** nulle part : `verify` tourne sur le worktree (`run.cwd`), et c'est l'agent qui pousse et ouvre la PR (`packs/standard/settings.json`). « Vérifié sur le même SHA » n'a pas encore de sens dans Relais.

## Les invariants proposés

Douze invariants : les 8 du doc (I8 renforcé : atteignable **et** absorbant), plus 4 que la cible d'ORC-133 rend nécessaires (déterminisme, doublon, fencing, taint). Chacun s'énonce comme une propriété sur une **séquence générée** `e₁…eₙ` (avec doublons et désordre) repliée par le pas suivant, qui inclut le dédoublonnage de l'inbox :

```text
step(s, e) = si e.id ∈ s.seen alors (s, ∅)
             sinon let r = decide(s, e, wf) in (fold reduce s[seen ∪ {e.id}] r.events, r)
```

Sans le test `e.id ∈ s.seen`, I10 serait faux d'office : la preuve 3a/3b ci-dessus montre qu'un `decide` rejoué reproduit ses effets. « Après chaque pas » veut dire : pour tout préfixe de la séquence.

Notation : `s` l'état d'un run, `r = decide(s, e, wf)`, `r.effects` les effets émis. Une **publication** est un effet qui expose le travail hors du bac à sable : `Publisher.publish(req)` avec `req.sha = sha` (le port de `main` pousse le SHA vérifié puis ouvre ou met à jour la PR), une porte franchie, un merge. Le check qui la précède est le verdict de `CheckRunner` sur ce SHA, exécuté **avant** le push ; les checks de la CI GitHub, qui n'existent qu'après le push, servent aux portes (I2), pas à I1. Les deux ont des ids distincts : `check:…` pour le verdict de `CheckRunner`, `ci:…` pour un résultat de la CI GitHub (voir ORC-147 plus bas).

| # | Invariant | Énoncé testable (propriété) | État et événement en jeu | Ce qui le garantit aujourd'hui |
|---|---|---|---|---|
| I1 | **Pas de publication sans vérification verte sur le même SHA** | Pour tout pas où `r.effects` contient une publication portant sur `sha` (voir la notation), le journal contient avant lui un `check:…` vert dont le SHA est `sha`, et aucun `push.human` ni push de l'usine n'a changé la tête de branche entre les deux. | verdicts de `CheckRunner` par SHA, tête de branche ; `check:…`, `push.human`, effet de publication | **Partiel** : `run.finished` succès → `run_verify` avant `successCommands` quand le job a des `verify`. Pas de SHA, et l'agent pousse lui-même ; `Publisher` et `CheckRunner` n'existent qu'en faux. |
| I2 | **Pas de porte franchie sans approbation postérieure au dernier push** | Pour tout pas où l'état passe une porte `g`, il existe une approbation de `g` dont l'horodatage de journal (séquence) est postérieur au dernier push (usine ou humain) sur la branche. | `s.gates`, dernier push ; événement d'approbation, `push.human` | **Rien encore.** |
| I3 | **Un test gelé ne sort du gel que par un événement humain** | Pour tout pas où un fichier passe de gelé à non gelé dans `s`, l'événement `e` de ce pas est `/refreeze` (ou équivalent) d'acteur humain. Et aucun effet d'écriture n'a pour cible un fichier gelé. | `s.frozenTests` ; commande humaine `/refreeze` | **Rien encore.** |
| I4 | **Le risque ne baisse jamais pendant un run** | Pour tout pas entre deux états d'un **même run**, `risk(s') ≥ risk(s)` (un nouveau run repart de son propre niveau). | `s.risk` ; tout événement | **Rien encore.** |
| I5 | **Toute boucle a un compteur borné, CI rouge comprise** | Pour toute boucle `L` du préréglage bornée à `N` **relances** : sur toute séquence, le nombre d'effets « démarrer une tentative » attribués à `L` dans un run est `≤ N + 1` (la première plus `N` relances) ; au `N+1`-ième échec, `decide` émet un passage à `blocked` ou `waiting_human`, jamais une nouvelle tentative. C'est la lecture du critère 4 d'ORC-173 ; `verify_attempts: 2` d'aujourd'hui compte les tentatives, pas les relances (`N = 1`), voir point 8. | compteurs par étape (`s.attempts`, `s.rounds`) ; échecs de vérification, `ci:…` rouge, tour de review | **Partiel** : `verify_attempts` compté (`engine.ts`) ; `review_rounds` seulement dans le prompt ; `pr.checks_failed` compté depuis ORC-270 (`ciFixAttempts` contre `limits.ci_fix_attempts`, en relances), sans le compteur partagé avec la review IA (ORC-184, ORC-187). |

À la fin de toute séquence, chaque `h` est soit dans `humanInbox`, soit remis. | `s.humanInbox` ; `session.prompted`, commentaires, commandes | **Partiel** : `append_feedback` seulement quand une règle matche ; perte en `ai_review`/`ready`/`todo` (preuve ligne 5) ; `pendingJob` écrasé. |
| I7 | **Jamais deux tentatives actives non autorisées** | Pour tout pas, pour chaque rôle `ρ`, `|s.activeAttempts[ρ]| ≤ quota(ρ)` (1 pour le dev, l'agent de réponse à part) ; un effet « démarrer une tentative » n'est émis que si la place est libre dans `s`. | `s.activeAttempts` ; tout événement qui démarre une tentative | **Partiel, hors de `decide`** : `scheduler.tryAcquire` par `<ticket>:<file>`, `pendingJob`. |

| I9 | **`decide` est déterministe et ne lit que ses entrées** | Pour tout `(s, e)`, `decide(s, e, wf)` appelé deux fois donne un résultat égal en profondeur, ids d'effets compris (dérivés de `ticket:seq:i`, jamais d'un aléa ni de l'horloge). | tout | **Partiel** : `decide` n'a pas d'effet de bord, mais `handle()` lit Linear (`createTicket`) et les ids de run viennent de `randomUUID` dans l'orchestrateur. Critère 1 d'ORC-133. |
| I10 | **Un doublon n'a aucun effet** | Pour toute séquence `σ` et `σ'` obtenue en dupliquant des événements de `σ` (même id) à des positions quelconques après leur original : l'état final et la suite des effets émis sont les mêmes pour `σ` et `σ'`. | journal ; tout événement rejoué | **Oui pour un doublon exact** : `recordEvent` (`INSERT OR IGNORE`). **Non** pour un même fait sous deux ids (`checks:…:<at>`, `ui:…:<at>`). |
| I11 | **Fencing : un résultat d'une tentative inactive est ignoré** | Pour tout `attempt:<id>:finished`, `check:…`, ou `effect:<id>` d'un effet **lié à une tentative** (conteneur, appel au modèle), dont la tentative n'est pas dans `s.activeAttempts` (ou dont le SHA n'est plus le dernier SHA de la tentative active : avant le push, ce n'est pas la tête distante) : `r.effects = []`, `r.timers = []`, `r.events` ne change que la trace. Le résultat d'un effet non lié à une tentative (commentaire, label) est toujours enregistré. | `s.activeAttempts`, dernier SHA de chaque tentative active ; résultats d'exécuteurs | **Partiel, hors de `decide`** : `verifyingRunId` dans `handle()` pour `verify.*` ; rien pour `run.finished` (preuves lignes 1 et 4). Critère 2 d'ORC-133. |
| I12 | **Taint : un contenu non fiable n'écrit jamais sur un chemin sensible** | Pour tout pas dont l'événement porte une taint non fiable, `r.effects` ne contient aucun effet d'écriture dont la cible est un chemin sensible (workflow, CI, secrets ; les tests gelés sont déjà couverts par I3, quelle que soit la taint), quelle que soit la suite d'événements qui précède. | taint de `e`, liste des chemins sensibles de `wf` ; tout événement | **Rien encore.** Critère 5 d'ORC-133. |

**À côté des 12, une propriété du harnais** (ORC-173 la liste à part) : **la projection est égale au rejeu du journal** — pour toute séquence, l'état tenu en ligne est égal à `fold reduce` sur le journal relu depuis zéro. Ce n'est pas un invariant de `decide` mais de `reduce` + inbox ; c'est elle qui interdit de dédoublonner hors du journal (la clé `meta` `checks:…` d'aujourd'hui la violerait).

**Pourquoi pas plus** : « un état terminal est absorbant » n'a pas sa propre ligne, il est fusionné dans I8 (b) : I7 borne la concurrence et l'atteignabilité seule n'empêche pas un démarrage après `merged`, il fallait donc le dire. « Le budget n'est jamais dépassé » (aucun démarrage de tentative budget épuisé) reste hors liste (point 2 tranché) : il dépend des budgets en tokens qui n'existent pas encore (ORC-150, « Attention »).

## La table d'idempotence

### Les 7 effets

Les 7 lignes sont celles d'ORC-162. Dans `src/core/commands.ts`, elles correspondent à `comment`, `labels`, `start_run` (conteneur + appel au modèle) ; push, PR et check run n'ont pas de commande aujourd'hui (l'agent pousse et ouvre la PR, `run_verify` tourne en local sans check GitHub).

« Exécuté deux fois » couvre les deux cas réels sous l'outbox d'ORC-150 : l'exécuteur a fait l'effet puis est mort avant d'écrire `effect:<id>` (le bail expire, un autre reprend), ou un bail expiré pendant que le premier exécuteur vivait encore. `SELECT … FOR UPDATE SKIP LOCKED` (Postgres, cible d'ORC-150 ; le store est SQLite aujourd'hui) exclut le reste.

| Effet | Clé | Avant d'écrire | Comportement en doublon (2ᵉ exécution) | Ce que l'outbox fait du doublon | Aujourd'hui |
|---|---|---|---|---|---|
| **Commentaire** | marqueur `<!-- factory:effect=<id> -->` dans le corps | lire les commentaires du ticket et chercher le marqueur | le marqueur est trouvé : **aucune écriture** | `effect:<id>` **succès**, avec l'id du commentaire existant et `deduplicated: true` | `tracker.comment()` sans marqueur ; seul le commentaire de budget est dédoublonné (clé `meta`) |
| **Labels** | groupe exclusif (`agent:*`, …) | aucune : on écrit l'**état final** du groupe (ajouter la cible, retirer les autres membres du groupe) | même état final : **effet naturellement idempotent** ; l'écho est filtré par `isEcho` | `effect:<id>` **succès** ; l'outbox exécute les effets labels d'un ticket **dans l'ordre de `seq`**, pour qu'un ancien effet rejoué n'écrase pas un plus récent | `setLabels(add, remove)` relatif, pas de groupe |
| **Push** | `--force-with-lease=<branche>:<sha attendu>` | aucune : git compare lui-même la tête distante | tête = **SHA poussé** → git répond « Everything up-to-date » et sort en 0 avant même de regarder le lease : **naturellement idempotent** ; tête = **SHA attendu** → push ; **autre SHA** → refus `(stale info)`, sortie 1 | 0 : `effect:<id>` **succès** ; refus : `effect:<id>` **conflit** (non rejoué) avec la tête lue (`git ls-remote` après le refus) ; `decide` la traite comme un `push.human` seulement si ce SHA n'est pas un push de l'usine déjà au journal (sinon c'est un ancien effet rejoué après un plus récent : conflit sans suite) | l'agent pousse ; `--force-with-lease` interdit dans `packs/standard/settings.json` |
| **PR** | branche (tête → base) | `findPr` par branche, état **ouvert** | une PR ouverte existe : **aucune création**. Course entre lecture et création : GitHub devrait refuser (422) une 2ᵉ PR ouverte pour le même couple tête + base (**non vérifié**), l'erreur est alors traitée comme « existe déjà » puis relue | `effect:<id>` **succès** avec le numéro de la PR existante | `findPr` existe (`--state all --limit 1`) mais sert au relevé ; l'agent crée la PR |
| **Check run** | `external_id` | lister les check runs du SHA et filtrer sur `external_id` (**non vérifié** : que l'API permette de retrouver un check par `external_id`) | trouvé : **mise à jour** au lieu de création | `effect:<id>` **succès** avec l'id du check | aucun check run |
| **Conteneur** | label `factory.attempt=<id>`, et nom du conteneur = id de tentative | chercher par label (`docker ps -a --filter label=…`) | trouvé en marche : **rattachement**, pas de 2ᵉ conteneur ; trouvé `created` (crash entre création et démarrage) : le démarrer ; trouvé arrêté : pas de redémarrage, l'exécuteur lit sa sortie. Le nom unique devrait faire refuser une création concurrente côté démon Docker (**non vérifié**). Un conteneur déjà supprimé (`--rm`, nettoyage) n'est plus trouvé : c'est la ligne suivante qui évite alors un 2ᵉ appel | `effect:<id>` **succès** avec l'id du conteneur existant | worktree par ticket ; le port `SandboxProvider` de `main` n'a que `create`/`destroy`, et son faux crée un 2ᵉ bac à sable pour le même `runId` : il manque une recherche par id de tentative |
| **Appel au modèle** | id de tentative | lire l'inbox d'abord (`attempt:<id>:finished` déjà là ?), puis se rattacher au conteneur de la tentative (ligne précédente) au lieu de relancer | jamais deux appels pour une même tentative : la 2ᵉ exécution se rattache ; si `attempt:<id>:finished` est déjà dans l'inbox, **rien** | aucun nouveau résultat ; un résultat tardif d'une tentative remplacée est **ignoré par `decide`** (fencing, I11) | `start_run` → `runner.start` ; fencing seulement pour `verify.*` dans `handle()` |

**Preuve pour la ligne Push** (git 2.43.0, dépôt nu local, branche `b` en `A`) : premier push de `B` avec `--force-with-lease=b:A`, puis rejeu à l'identique, puis push d'un troisième commit `C` avec le même lease périmé.

```text
1st push exit 0
Everything up-to-date
replay exit 0
 ! [rejected]        HEAD -> b (stale info)
other-sha exit 1
```

### La règle commune pour l'outbox

**Un doublon détecté est un succès, pas une erreur.** L'exécuteur écrit `effect:<id>` avec la référence de l'objet déjà présent ; comme l'inbox dédoublonne par id, `decide` ne voit qu'un résultat par effet, quel que soit le nombre d'exécutions. Une seule exception : le push dont la branche a bougé vers un **autre** SHA, qui est un **conflit** — il n'est jamais rejoué et revient à `decide`, qui décide (I1, I2 s'appliquent alors au nouveau SHA).

Ce qui en découle pour la clé de chaque effet : elle doit être **stable d'une exécution à l'autre**, donc dérivée de l'id d'effet (`ticket:seq:i`) ou de l'id de tentative, jamais de l'horloge. C'est I9 vu du côté de l'outbox.

**Le cas du bail expiré sous un exécuteur vivant** reste le seul où deux écritures peuvent se croiser (lecture du marqueur puis écriture des deux côtés). La proposition : l'exécuteur vérifie que son bail est toujours le sien juste avant l'écriture et au moment d'écrire `effect:<id>`, et le doublon résiduel est accepté comme rare et visible (même marqueur deux fois, détectable).

### Les commandes de `commands.ts` hors des 7 lignes

`commands.ts` porte d'autres effets externes que la table ne couvre pas. Proposition de rattachement (point 6 ci-dessous) :

| Commande | Rattachement proposé | Comportement en doublon |
|---|---|---|
| `move` (statut Linear) | comme **Labels** : état final, écho filtré | naturellement idempotent ; ordre par `seq` |
| `activity`, `post_output` (activités de session Linear) | comme **Commentaire** : marqueur ou id d'effet dans l'activité | à vérifier : l'API Linear permet-elle de relire les activités d'une session pour y chercher un marqueur ? Sinon, doublon accepté et visible |
| `link_pr` (`addExternalUrl`) | état final : l'URL est présente ou non | à vérifier : Linear dédoublonne-t-il une URL déjà présente ? Sinon, lire avant d'ajouter |
| `stop_run` | naturellement idempotent : arrêter une tentative arrêtée ne fait rien | succès |
| `cleanup` | naturellement idempotent : supprimer un conteneur ou worktree absent n'est pas une erreur | succès |
| `run_verify` | devient `CheckRunner.run`, exécuté **avant** le push (I1), dont le verdict revient en `check:…` ; ce verdict est ensuite publié en **Check run** GitHub sur le SHA poussé (ORC-150) | `CheckRunner.run` : résultat fencé par I11 ; publication : comme Check run |

## Points tranchés

Chaque point ci-dessous a été tranché le 2026-10-22 : l'option retenue est dans le [tableau de la Décision](#décision).

1. **Fidélité au doc MVP.** Cette proposition n'a pas pu lire le doc : les 8 invariants viennent d'ORC-173. Si le doc formule autrement l'un d'eux, quelle version garder ?
2. **12 ou 13 invariants.** « Terminal absorbant » est fusionné dans I8 (b) ; faut-il ajouter « le budget n'est jamais dépassé » ? Recommandation : hors liste pour l'instant, il attend les budgets en tokens.
3. **« Projection = rejeu »** : propriété du harnais à part (recommandé, comme ORC-173), ou 13ᵉ invariant ?
4. **Ce que l'outbox fait d'un doublon** : B1, B2 ou B3 (recommandé, voir [Les options](#les-options)) ?
5. **`external_id` du check run** : l'id de l'effet qui **crée** le check, repris par les mises à jour (recommandé : un check passe par plusieurs effets, `in_progress` puis `completed`), ou l'id de **chaque** effet comme l'écrit ORC-162 (alors chaque mise à jour créerait un check) ?
6. **Effets hors table** (`move`, `activity`, `post_output`, `link_pr`, `stop_run`, `cleanup`, `run_verify`) : les rattacher aux 7 lignes comme proposé, ou ouvrir des lignes à part dans ORC-162 ?
7. **PR fermée trouvée sur la branche** : en ouvrir une nouvelle (recommandé : c'est ce que fait déjà `FakePublisher` sur `main`, et GitHub ne rouvre pas une PR mergée sur un push), rouvrir l'ancienne, ou bloquer le run ?

10. **Nom de l'événement d'annulation (I8 a)** : `run.cancel` est un nom de travail ; à fixer avec les renommages d'ORC-133.

## Annexe : le script de sondage

Lancé depuis la racine du dépôt avec `npx tsx /chemin/vers/probe-decide.mts "$PWD"` (fichier hors du dépôt, d'où le chemin absolu ; extension `.mts` pour l'`await` de premier niveau). Version condensée : les libellés affichés sont plus courts que dans la sortie citée plus haut, les appels à `decide` sont les mêmes.

```ts
const root = process.argv[2]!;
const { loadWorkflow } = await import(`${root}/src/config/load-workflow.ts`);
const { decide } = await import(`${root}/src/core/engine.ts`);
const { newTicketState } = await import(`${root}/src/core/types.ts`);

const workflow = loadWorkflow({ packDir: `${root}/packs/standard` });
const kinds = (cs) => cs.map((c) => c.kind + (c.job ? `:${c.job}` : '') + (c.to ? `:${c.to}` : '')).join(', ') || '(rien)';
const base = { at: 1, projectId: 'p', ticketId: 'ORC-1' };

// 1. run.finished périmé : le run actif est B, un succès du run A arrive.
const t1 = { ...newTicketState('p', 'ORC-1', 't', 'dev', 0), delegated: true, activeRunId: 'run-B' };
const stale = { ...base, id: 'run:run-A:finished', type: 'run.finished',
  payload: { runId: 'run-A', job: 'dev', outcome: 'success', costUsd: 0, turns: 1, lastText: '' } };
console.log('1.', kinds(decide(stale, t1, { workflow })));

// 2. CI rouge 5 fois.
const t2 = { ...newTicketState('p', 'ORC-1', 't', 'human_review', 0), delegated: true };
for (let i = 1; i <= 5; i++) {
  const ev = { ...base, id: `pr:ORC-1:7:checks:fail:${i}`, type: 'pr.checks_failed',
    payload: { number: 7, url: 'u', branch: 'b', failures: ['ci'] } };
  console.log(`2. n°${i}`, kinds(decide(ev, t2, { workflow })));
}

// 3. Même verify.passed deux fois ; 4. verify.passed d'un autre run que celui vérifié.
const vp = { ...base, id: 'verify:run-A', type: 'verify.passed', payload: { runId: 'run-A', job: 'dev' } };
const t3 = { ...newTicketState('p', 'ORC-1', 't', 'dev', 0), delegated: true, verifyingRunId: 'run-A' };
console.log('3a.', kinds(decide(vp, t3, { workflow })), '3b.', kinds(decide(vp, t3, { workflow })));
const t4 = { ...t3, verifyingRunId: 'run-B' };
console.log('4.', kinds(decide(vp, t4, { workflow })));

// 5. Réponse humaine dans le fil de dev, ticket non bloqué.
for (const logical of ['ai_review', 'ready', 'todo']) {
  const t5 = { ...newTicketState('p', 'ORC-1', 't', logical, 0), delegated: true, linearSessionId: 'S-dev' };
  const reply = { ...base, id: 'linear:activity:42', type: 'session.prompted',
    payload: { linearSessionId: 'S-dev', body: 'attention au cas vide', author: 'dev' } };
  console.log(`5. ${logical}`, kinds(decide(reply, t5, { workflow })));
}
```
