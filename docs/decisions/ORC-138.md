## The question

The MVP doc ("Les garanties du moteur", the engine's guarantees) lists 8 invariants of `decide` out of "8 to 12, list to be completed", and leaves empty the "duplicate behavior" column of the idempotency table of the 7 external effects. Two tickets are waiting for the answer:

- **ORC-173** tests each invariant with property-based tests, over 10,000 event sequences with duplicates and disorder;
- **ORC-162** makes each effect idempotent and tests each row of the table.

So we must set:

1. the complete list of invariants, each stated in a way that can be tested as a property;
2. for each of the 7 effects, what happens when it is executed twice, and what the outbox does with the duplicate.

The invariants are written against the **ORC-133 target**, not the current code: a pure `decide(state, event, wf) → { events, effects, timers, trace }`, `reduce(state, event) → state`, executor results coming back through the inbox (`effect:<id>`, `attempt:<id>:finished`, `check:…`), fencing and taint in `decide`.

**Limit of this proposal**: the MVP doc is a claude.ai artifact that this session could not open. The 8 invariants and the starting table are taken as ORC-173 and ORC-162 copy them. If the doc says something else on a point, the doc prevails: see [Decided points](#decided-points), point 1.

## Criteria

In order, the ticket's first:

1. **The linked tickets rely on the answer** (acceptance criterion of ORC-138): each invariant must be able to become a property of ORC-173, each row of the table a test of ORC-162, with no new question.
2. **Testable as a property**: the statement is about a generated sequence of states and events, not a hand-picked scenario; it says what is observed (state, effects emitted) after each step.
3. **Covers the factory's promises** cited by ORC-173: no publication without verification, no frozen test weakened, no human message lost, bounded loops.
4. **Holds with "at least once"** (ORC-147, ORC-150): an event may arrive twice or out of order, an effect may be executed twice.
5. **Stays within the doc's range of 8 to 12**, with no redundant invariant (an invariant that follows from another does not get its own property).

### What the current `decide` does on the sequences that matter

A script (reproduced in the [appendix](#appendix-the-probe-script)) calls `decide` from `src/core/engine.ts` with the `packs/standard` workflow, without an orchestrator (output recorded verbatim, in French):

```text
1. run.finished(success) du run A, run actif B -> move:human_review, post_output
2. pr.checks_failed n°1 -> start_run:fix-ci
2. pr.checks_failed n°2 -> start_run:fix-ci
2. pr.checks_failed n°3 -> start_run:fix-ci
2. pr.checks_failed n°4 -> start_run:fix-ci
2. pr.checks_failed n°5 -> start_run:fix-ci
3a. verify.passed (1er) -> patch_ticket, move:human_review, post_output
3b. verify.passed (rejoué, même état) -> patch_ticket, move:human_review, post_output
4. verify.passed du run A, vérif en cours B -> patch_ticket, move:human_review, post_output
5. session.prompted fil de dev, état ai_review -> (rien)
5. session.prompted fil de dev, état ready -> (rien)
5. session.prompted fil de dev, état todo -> (rien)
```

What this shows:

- **No fencing in `decide`** (lines 1 and 4): a result from a run that is no longer active produces the same decisions as a current result. For `verify.*`, `handle()` filters beforehand; for `run.finished`, nothing filters (only `activeRunId` is reset, and only if the id matches, `orchestrator.ts:284`).
- **`decide` is not idempotent on its own** (3a, 3b): replayed, an event reproduces its effects. Everything relies on deduplication by id upstream. This is normal for a pure function, but it means the "duplicate without effect" invariant must be carried by the inbox + `decide` pair, not by `decide` alone.
- **The red CI loop is not bounded** (2), as ORC-173 already points out: the `pr.checks_failed` rule of `packs/standard/workflow.yml` relaunches `fix-ci` without a counter. Moreover, the id of these events contains the poll time (`pr:<ticket>:<n>:checks:fail:<at>`, `src/adapters/forge/pr-poller.ts`): two polls of the same failure have two ids, and deduplication relies on the `meta` key `checks:<projet>:<ticket>`, outside the journal.
- **A human message may never reach the agent** (5): a reply in the dev thread of a ticket in `ai_review`, `ready` or `todo` that is not blocked matches no `session.prompted` rule; it is written to the journal but never added to `pendingFeedback`. Another possible loss: `pendingJob` is overwritten by a second `start_run` during a run (`orchestrator.ts:495`), and its `inputText` with it.
- **No SHA** anywhere: `verify` runs on the worktree (`run.cwd`), and it is the agent that pushes and opens the PR (`packs/standard/settings.json`). "Verified on the same SHA" has no meaning in Relais yet.

## The proposed invariants

Twelve invariants: the doc's 8 (I8 strengthened: reachable **and** absorbing), plus 4 that the ORC-133 target makes necessary (determinism, duplicate, fencing, taint). Each one is stated as a property over a **generated sequence** `e₁…eₙ` (with duplicates and disorder) folded by the following step, which includes the inbox deduplication:

```text
step(s, e) = if e.id ∈ s.seen then (s, ∅)
             else let r = decide(s, e, wf) in (fold reduce s[seen ∪ {e.id}] r.events, r)
```

Without the `e.id ∈ s.seen` test, I10 would be false outright: evidence 3a/3b above shows that a replayed `decide` reproduces its effects. "After each step" means: for every prefix of the sequence.

Notation: `s` the state of a run, `r = decide(s, e, wf)`, `r.effects` the effects emitted. A **publication** is an effect that exposes the work outside the sandbox: `Publisher.publish(req)` with `req.sha = sha` (the port on `main` pushes the verified SHA then opens or updates the PR), a gate passed, a merge. The check that precedes it is the `CheckRunner` verdict on this SHA, executed **before** the push; GitHub CI checks, which only exist after the push, are used for gates (I2), not for I1. The two have distinct ids: `check:…` for the `CheckRunner` verdict, `ci:…` for a GitHub CI result (see ORC-147 below).

|---|---|---|---|---|

| I3 | **A frozen test only leaves the freeze through a human event** | For every step where a file goes from frozen to unfrozen in `s`, the event `e` of that step is `/refreeze` (or equivalent) from a human actor. | I10 | **A duplicate has no effect** | For every sequence `σ` and `σ'` obtained by duplicating events of `σ` (same id) at arbitrary positions after their original: the final state and the sequence of emitted effects are the same for `σ` and `σ'`. | journal; any replayed event | **Yes for an exact duplicate**: `recordEvent` (`INSERT OR IGNORE`). **No** for the same fact under two ids (`checks:…:<at>`, `ui:…:<at>`). |
| I11 | **Fencing: a result from an inactive attempt is ignored** | For every `attempt:<id>:finished`, `check:…`, or `effect:<id>` of an effect **tied to an attempt** (container, model call), whose attempt is not in `s.activeAttempts` (or whose SHA is no longer the latest SHA of the active attempt: before the push, that is not the remote head): `r.effects = []`, `r.timers = []`, `r.events` only changes the trace. Criterion 2 of ORC-133. |
| I12 | **Taint: untrusted content never writes to a sensitive path** | For every step whose event carries an untrusted taint, `r.effects` contains no write effect whose target is a sensitive path (workflow, CI, secrets; frozen tests are already covered by I3, whatever the taint), whatever sequence of events precedes it. | taint of `e`, list of sensitive paths of `wf`; any event | **Nothing yet.** Criterion 5 of ORC-133. |

**Alongside the 12, a harness property** (ORC-173 lists it separately): **the projection equals the replay of the journal** — for any sequence, the state held online equals `fold reduce` over the journal reread from scratch. This is not an invariant of `decide` but of `reduce` + inbox; it is what forbids deduplicating outside the journal (today's `meta` key `checks:…` would violate it).

**Why not more**: "a terminal state is absorbing" does not get its own row, it is merged into I8 (b): I7 bounds concurrency and reachability alone does not prevent a start after `merged`, so it had to be said. "The budget is never exceeded" (no attempt start with the budget exhausted) stays off the list (point 2 decided): it depends on token budgets that do not exist yet (ORC-150, « Attention »).

## The idempotency table

### The 7 effects

### The common rule for the outbox

**A detected duplicate is a success, not an error.** The executor writes `effect:<id>` with the reference of the object already present; since the inbox deduplicates by id, `decide` only sees one result per effect, whatever the number of executions. A single exception: the push whose branch moved to **another** SHA, which is a **conflict** — it is never replayed and goes back to `decide`, which decides (I1, I2 then apply to the new SHA).

What follows for each effect's key: it must be **stable from one execution to the next**, hence derived from the effect id (`ticket:seq:i`) or the attempt id, never from the clock. This is I9 seen from the outbox side.

**The case of a lease expiring under a live executor** remains the only one where two writes can cross (marker read then write on both sides). The proposal: the executor checks that its lease is still its own just before the write and when writing `effect:<id>`, and the residual duplicate is accepted as rare and visible (same marker twice, detectable).

| C1 — ORC-162's text as is | the push is already idempotent (evidence above); but the current `findPr` (`--state all --limit 1`) can return a **closed** PR from a previous attempt and pass it off as "already exists" |
| **C2 — ORC-162 + open PR only** | closes this gap, at no cost: `--state open` |
| C3 — C2 + `ls-remote` read before each push | useless for the duplicate (git handles it alone); useful only to report the head read after a refusal, which the table already provides for |

## Recommendation

1. **A2: adopt the 12 invariants** I1 to I12 as stated, plus "projection = replay" as a separate harness property; leave "budget never exceeded" off the list for now.
2. **B3: adopt the table** with the common rule "detected duplicate = success with the existing reference, marked `deduplicated`", and the refused push `(stale info)` as the only exception (conflict not replayed).
3. **C2: refine the PR row relative to ORC-162's text**: reuse only an **open** PR. The Push row stays as in ORC-162: a replay of the same SHA exits with 0, no prior read is needed.
4. **Require ordering by `seq` in the outbox** for "final state" effects of the same ticket (labels, status), otherwise an old effect replayed after a newer one goes backwards.

## Decided points

Each point below was decided on 2026-10-22: the option adopted is in the [Decision table](#decision).

1. **Fidelity to the MVP doc.** This proposal could not read the doc: the 8 invariants come from ORC-173. If the doc words one of them differently, which version should be kept?
2. **12 or 13 invariants.** "Terminal is absorbing" is merged into I8 (b); should "the budget is never exceeded" be added? Recommendation: off the list for now, it waits for token budgets.
3. **"Projection = replay"**: a separate harness property (recommended, like ORC-173), or a 13th invariant?
4. **What the outbox does with a duplicate**: B1, B2 or B3 (recommended, see [The options](#the-options))?
5. **`external_id` of the check run**: the id of the effect that **creates** the check, reused by the updates (recommended: a check goes through several effects, `in_progress` then `completed`), or the id of **each** effect as ORC-162 writes it (then each update would create a check)?
6. **Effects outside the table** (`move`, `activity`, `post_output`, `link_pr`, `stop_run`, `cleanup`, `run_verify`): attach them to the 7 rows as proposed, or open separate rows in ORC-162?
7. **Closed PR found on the branch**: open a new one (recommended: this is what `FakePublisher` on `main` already does, and GitHub does not reopen a merged PR on a push), reopen the old one, or block the run?
8. **What a loop's bound `N` counts (I5)**: retries (`N` retries, hence `N + 1` attempts, the reading of criterion 4 of ORC-173 adopted here) or attempts (today's reading of `verify_attempts`, which blocks at the `N`-th failure)? The ORC-187 preset must write its bounds in the same unit.
9. **"Lost" for a human message (I6)**: is an explicit acknowledgment (the message is read but asks for nothing) enough to take it out of `humanInbox`, or must every message be handed to an attempt?
10. **Name of the cancellation event (I8 a)**: `run.cancel` is a working name; to be set with the ORC-133 renamings.

## Appendix: the probe script

Run from the repository root with `npx tsx /chemin/vers/probe-decide.mts "$PWD"` (file outside the repository, hence the absolute path; `.mts` extension for the top-level `await`). Condensed version: the printed labels are shorter than in the output quoted above, the calls to `decide` are the same.

```ts
const root = process.argv[2]!;
const { loadWorkflow } = await import(`${root}/src/config/load-workflow.ts`);
const { decide } = await import(`${root}/src/core/engine.ts`);
const { newTicketState } = await import(`${root}/src/core/types.ts`);

const workflow = loadWorkflow({ packDir: `${root}/packs/standard` });
const kinds = (cs) => cs.map((c) => c.kind + (c.job ? `:${c.job}` : '') + (c.to ? `:${c.to}` : '')).join(', ') || '(rien)';
const base = { at: 1, projectId: 'p', ticketId: 'ORC-1' };

// 1. Stale run.finished: the active run is B, a success from run A arrives.
const t1 = { ...newTicketState('p', 'ORC-1', 't', 'dev', 0), delegated: true, activeRunId: 'run-B' };
const stale = { ...base, id: 'run:run-A:finished', type: 'run.finished',
  payload: { runId: 'run-A', job: 'dev', outcome: 'success', costUsd: 0, turns: 1, lastText: '' } };
console.log('1.', kinds(decide(stale, t1, { workflow })));

// 2. Red CI 5 times.
const t2 = { ...newTicketState('p', 'ORC-1', 't', 'human_review', 0), delegated: true };
for (let i = 1; i <= 5; i++) {
  const ev = { ...base, id: `pr:ORC-1:7:checks:fail:${i}`, type: 'pr.checks_failed',
    payload: { number: 7, url: 'u', branch: 'b', failures: ['ci'] } };
  console.log(`2. n°${i}`, kinds(decide(ev, t2, { workflow })));
}

// 3. Same verify.passed twice; 4. verify.passed from a run other than the one being verified.
const vp = { ...base, id: 'verify:run-A', type: 'verify.passed', payload: { runId: 'run-A', job: 'dev' } };
const t3 = { ...newTicketState('p', 'ORC-1', 't', 'dev', 0), delegated: true, verifyingRunId: 'run-A' };
console.log('3a.', kinds(decide(vp, t3, { workflow })), '3b.', kinds(decide(vp, t3, { workflow })));
const t4 = { ...t3, verifyingRunId: 'run-B' };
console.log('4.', kinds(decide(vp, t4, { workflow })));

// 5. Human reply in the dev thread, ticket not blocked.
for (const logical of ['ai_review', 'ready', 'todo']) {
  const t5 = { ...newTicketState('p', 'ORC-1', 't', logical, 0), delegated: true, linearSessionId: 'S-dev' };
  const reply = { ...base, id: 'linear:activity:42', type: 'session.prompted',
    payload: { linearSessionId: 'S-dev', body: 'attention au cas vide', author: 'dev' } };
  console.log(`5. ${logical}`, kinds(decide(reply, t5, { workflow })));
}
```
