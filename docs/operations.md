# Operations

Running Relais day to day: limits, budget, pause, logs, recovery after a restart, and troubleshooting.

## Limits and what happens when they are reached

| Limit | Where | Default | When it is reached |
|---|---|---|---|
| Concurrent code runs | `concurrency` (`factory.yml`), otherwise `limits.parallel_sessions` (workflow) | 3 | Further runs wait in the `dev` queue (persistent), by ticket priority. |
| Concurrent question runs | `limits.question_sessions` (workflow) | 2 | Same, `questions` queue. |
| Turns per run | `limits.per_run.turns` / `jobs.*.limits.turns`, the step's `maxTurns` and `budgets.max_turns` | 150 | Run interrupted, ticket blocked, kind `budget` (ORC-216). |
| Run duration | `limits.per_run.duration` | `90m` | Run interrupted, result `limit`. |
| Tokens per attempt | `budgets.per_step_tokens` (`factory.yml`) | none (to calibrate) | Run interrupted, ticket blocked, kind `budget` (ORC-216). |
| Tokens per ticket | `budgets.per_ticket_tokens` (`factory.yml`, lowered by the repository's) | none (to calibrate) | An attempt never gets more than what is left; once spent, the next code run is refused, ticket blocked, kind `budget`. `factory validate` refuses a preset whose worst case exceeds it. |
| Verification passes | `limits.verify_attempts` | 4 (preset: 3 retries) | Ticket blocked, failing commands posted in Linear. |
| Same failure, unchanged worktree | preset (`sameFailure`) | 3 in a row | Ticket blocked with the cause « Loop », failing commands posted in Linear. |
| Rounds of the review and CI loop | `limits.ci_fix_attempts` (preset `review_ci`) | 2 per run | Red CI (`fix-ci`), a conflict (`rebase`) and an AI review with a blocking finding (`fix-review`, ORC-184) share it: the next one relaunches nothing, the ticket is blocked, the failing checks or the review's count posted in Linear. Reset by another PR or a human who starts work on the ticket (blocked or not); a green CI only lifts the red-CI block. |
| Rounds of human review feedback | `limits.human_review_rounds` (preset `human_review`) | 3 per run | Each `fix-human` started by feedback in Human Review (ORC-190), apart from the review and CI loop: the 4th feedback relaunches nothing, the ticket is blocked, the feedback kept. Reset by a human relaunch or another PR. |
| Duration of a `verify` / `setup` command | fixed | 15 min | Command counted as failed (`timeout`). |
| Duration of any other subprocess of the daemon (git, `gh`, the container engine) | `DEFAULT_EXEC_TIMEOUT_MS` (`src/adapters/exec.ts`), unless the caller names its own | 30 min | Killed with its whole process group (POSIX), code 124 (ORC-344): the effect that ran it fails and is tried again, its ticket freed. |
| Silence of an attempt | `silentAfterMs` (preset `silentRun`), otherwise `RUN_SILENT_MS` | 30 min | Its lease is no longer renewed: closed and relaunched once its lease runs out (ORC-344), unless the stagnation detector stopped it first. |

After a `limit` result or a failure, a code run **blocks** the ticket and Relais writes in the Linear session to reply in the thread to resume; a question run replies « I could not finish (failure or limit reached). ». Details and settings: [`workflow.md`](workflow.md#limits). Budgets in tokens and turns: [`configuration.md`](configuration.md#budgets).

## Blocked tickets

A ticket is **blocked** after: a failure or a cap, failed verifications, a CI still red or an AI review still finding after the `limits.ci_fix_attempts` rounds of the review and CI loop, a refused pickup check, a question from the agent (`relais-agent ask`), a stop, a lease that expired twice in a row, too many relaunches after an outage, a launch error (worktree setup, `git fetch`, knowledge repository…), or an event whose decision failed (« Event <id> set aside », see [Dead-letter](#dead-letter-and-factory-run-repair-orc-175)). The reason is visible in the UI (Needs you, grouped by cause) and in the blocking comment on the Linear ticket, the only escalation channel ([template](linear.md#the-blocking-comment-orc-196)).

To unblock it: **reply in the ticket** (comment, or the agent's session): the blocked step restarts right away. A ticket blocked by a set-aside event is repaired with `factory run repair <ticket>`.

## Pause

`relais pause` (or the UI button): no run starts any more, requests stay queued; runs in progress finish. `relais resume` resumes. The pause state survives a restart. A pause holds every request accepted after it, from the moment it is recorded: a delegation that follows it at once starts no run, even if it is decided first (ORC-335). Useful before maintenance, an upgrade, or to stop spending without stopping the daemon (webhooks and reconciliation keep going).

To stop a single ticket: `relais stop <ID>`, the Stop button, the `agent:stop` label, or stop in the Linear session.

| What | Where |
|---|---|

| Run transcript | `<RELAIS_HOME>/transcripts/<runId>.jsonl`: Claude Code's `stream-json` output (messages, tool calls, result, cost), **masked** (see below). Outside the database and the log. Also via `GET /api/runs/<runId>/transcript`. |
| A ticket's Claude session | `<RELAIS_HOME>/sessions/<projet>/<ticket>/`: the ticket's Claude Code config folder, mounted as `~/.claude` for the runs that resume its session (with a sandbox, ORC-217). Outside the database and the log; the source of truth stays in the database, the session only provides context. Each run's role and session id are stored on the run (`sessionRole`, `claudeSessionId`). |
| Events, runs, costs, queue | Postgres when `FACTORY_DATABASE_URL` is set (tables `inbox`, `journal`, `tickets`, `attempts`, `outbox`, `timers`…), otherwise `<RELAIS_HOME>/relais.db` (SQLite). The last 100 events: UI or `GET /api/events/recent`. At startup the daemon writes `store: Postgres (Drizzle migrations applied)` or `store : SQLite (<chemin>)`. |
| Run labels | Each run keeps, fixed at creation, what it ran with (`labels`, also in `/api/state`): job, queue, model, Relais version, Relais commit read from `FACTORY_COMMIT` if set, `sha256` fingerprints of the prompt (the run's own, specific to the ticket, and its template, where the ticket fields are replaced by placeholders: identical from one ticket to another for the same job), of the skills, the workflow and the config (`settings`, `hooks/`, `.claude-plugin/`, `agents/`, `commands/`, `.mcp.json`). The config fingerprint covers the run settings without the `<RELAIS_HOME>` path, and the pack's text files are hashed with LF line endings: two instances, Windows or Linux, with the same config and the same pack have the same fingerprints. Symbolic links in the pack are neither followed nor hashed. In Postgres, also in the `attempts` columns. Labels that have no source yet (Relais commit without `FACTORY_COMMIT`, effort, image, risk, register and delivered facts, knowledge index) are `null`, and `labels.pending` (computed on read) gives the tickets that will fill them. The pack fingerprints are computed on every run, as Claude Code rereads the pack: a change counts from the next run. An unreadable pack gives `null` fingerprints (warning `attempt labels: pack not fingerprinted` in the log), without preventing the run. |
| What the team sees | Each ticket's Linear agent session: acknowledgement, live activity, questions, summaries, errors. |

Transcripts are **kept for 30 days**: at startup, then every day, the daemon deletes those last written 30 days ago or more (`transcripts: N deleted after 30 days` in the log). Archive them beforehand if you need them longer. The database is not purged. In the same pass, the daemon deletes run folders (`<RELAIS_HOME>/runs/<runId>/`, the sandboxed run's denial log) modified 30 days ago or more, and the session folder of a closed ticket (`done`, or its PR closed without merge, in the database state) whose folder has not changed for 30 days (`sessions: N deleted…`). A ticket unknown to the database keeps its folder. A ticket canceled in Linear without a PR is not seen as closed: its folder stays, to be deleted by hand.

As soon as it is read, each line of the run's output is masked (`[masked]`), before being written to the transcript, streamed to the UI and relayed into the Linear session; the run's last text (stored with the run and posted in Linear) is masked too. Masked: the values of the daemon's and the run's secret variables (names ending in `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `_PASS`, `_PWD`, `APIKEY`, `_KEY`, `CREDENTIALS` or `DATABASE_URL`, 8 characters or more; `*_ASKPASS`, which names a program, stays readable), the secrets in `secrets.json` (client secret, webhook secret and Linear tokens) and the GitHub webhook secret in `config.yaml`, the credentials (`user:password`) of any environment value that is a URL, as well as the known shapes of GitHub, Anthropic and Linear tokens, `Bearer` tokens and PEM private keys. A secret that has neither form (a password typed into a file in the repository, for example) stays visible.

Examples of reading the database (with `sqlite3`, daemon stopped or read-only):

```bash
sqlite3 ~/.relais/relais.db '.tables'      # tickets, events, runs, timers, queue, echoes, meta
sqlite3 ~/.relais/relais.db "select id, status, cost_usd, datetime(started_at/1000,'unixepoch') from runs order by started_at desc limit 10"
```

The SQLite schema is defined in `src/store/sqlite-store.ts`; the `data` columns contain JSON. The Postgres schema is in `src/store/pg/schema.ts` and its migrations in `drizzle/`. Rejected webhooks (signature, freshness) are **not** recorded in the database: they only leave a log line in smee mode.

## Measures (ORC-235)

The measures from the MVP doc are collected from the first run. The dashboard shows them on its **Measures** page (`#measures`, ORC-223), read from `GET /api/measures` (the 50 most recently updated tickets, read-only), summed over a period on its **Overview** (`#overview`, ORC-299: `overview` of `src/core/overview.ts`, read from `GET /api/overview`, which reads only the tickets updated since the period began), plus the tokens of the Flow (ORC-297). The Overview faces them with the 90-day baseline (ORC-230), the only figures not computed from the factory's facts: `factory baseline` reads them from Linear and GitHub over the 90 days before the factory started and freezes them in the `baselines` table, one row per measure ([`cli.md`](cli.md#factory-baseline-project-orc-230)). ## The small model of messages

A human message that is not a command is classified `instruction` or `question` by `claude-haiku-5-5` at ingestion (ORC-336, [rules](linear.md#human-messages-during-a-run)). It reaches Claude by the runners' credential, with no new setting:

| What the daemon has | Runs on the host | Runs in sandboxes (`FACTORY_CONTAINER_CLI`) |
|---|---|---|
| A Claude account (`claude.active` in `factory.yml`) or `CLAUDE_CODE_OAUTH_TOKEN` | `claude -p` with that token, as a run on the host would | The Messages API if `ANTHROPIC_API_KEY` is set too, otherwise none |
| `ANTHROPIC_API_KEY` alone | The Messages API | The Messages API |
| Neither | `claude -p` with the host's Claude Code login; without one it fails | None |

`claude -p` runs with no tool, no MCP server, no settings, no session kept, out of any repository, the message on stdin. The daemon image holds no `claude` (no agent runs in it, ORC-204), hence no Claude account backend with sandboxes. The Messages API call has `max_tokens` 16, thinking off, low effort: Claude Haiku 5.5 takes `output_config.effort`, and `thinking: {"type": "disabled"}` at `high` effort or below ([effort](https://platform.claude.com/docs/en/build-with-claude/effort)). With no backend, or one that fails, the fallback rule classifies.

`FACTORY_MESSAGE_MODEL` set to `off`, `0`, `false` or `none` (any case) turns the model off, and any other value is logged as a warning: the fallback rule (a `?` outside a URL makes a question, anything else an instruction) classifies alone. The fake runner (`--fake-runner`) never calls it.

**After the answer.** Linear fails a webhook delivery that is not answered with a 200 within 5 s, and retries it after 1 minute, 1 hour and 6 hours ([Linear's webhook docs](https://linear.app/developers/webhooks)). So a webhook that may carry a message is answered as soon as it is kept in the store (a `delivery:<kind>:<key>` meta row: the raw webhook and its arrival time), before it is mapped or classified. The kind is in the row's key because a session reply and the comment Linear writes for it share their delivery key: each is kept, and the inbox keeps their event once by its id. A comment the mapping would drop on its body alone (the factory's own, a session's, one opened by a mention, an empty one) is not kept. Then, per issue (by its stable id, which survives a move to another team), its events are mapped in the ingest's turn in arrival order, classified out of any turn and side by side, and written to the inbox in the turn in arrival order. Then the kept row goes. A webhook of the same issue that comes behind it goes the same way, so as to keep its place. Webhooks of other issues, and the reconciliation that shares the turn, wait for no model. Each step that fails (the mapping, the write, the removal of the kept row) is tried again in the background, from 1 s and doubling up to 5 min, for an hour from the delivery's first arrival as kept (a restart does not start the hour again). Past that hour the row is moved aside (`delivery-aside:<key>`, logged as an `ERROR`): it is no longer tried at each start, and an operator can still read it. A row that cannot be read back is set aside the same way. At start, before the server or the relay takes any webhook, `resume` sets the kept rows on their way in the order received (with the model off too: what an earlier start kept is still written, by the fallback rule), so a new webhook of their issue goes behind them. Resumed rows wait for a classification slot instead of taking the fallback rule. On a stop, the relay closes first. A webhook still received after that is kept for the next start rather than refused, since a relay could not send it again. The retries stop short, and what is not written stays kept for the next start, all before the store closes. A webhook kept already is answered and not written twice; if no delivery of it is under way any more, it is delivered again, timed at its first arrival. An event the inbox already holds asks no model. That lookup only spares a call: when it fails, it is logged once and the event is classified and written all the same. A webhook's issue is taken before its row is even kept, so a later webhook of that issue cannot overtake it while the insert runs. Without the model, every webhook is written before its answer, as before.

**Bound.** At most 4 classifications run at once; past that, a message gets the fallback rule at once, and no process is queued. A call is cut at 3 s through the Messages API, 6 s through `claude -p` (killed with `SIGKILL`; a timer rejects 500 ms later should a grandchild keep its pipe open), and the fallback rule decides. The acknowledgement comes after the write, and Linear marks a session unresponsive when no activity arrives within 10 s. Measured on a developer's machine (Claude Code 2.1.319, low effort): the model itself answers in about 0.9 s (`duration_api_ms`). `claude -p` takes 1.7 to 3.4 s in all, its start included, and about 5 s more without `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, which it is given. `claude -p` never gets `ANTHROPIC_API_KEY`: it uses the Claude account. The time of a message (`at`, and so `signOfLifeMs`) is taken when the webhook arrives, before any wait, so the wait for the model shows in the measure.

**Failures.** Each failure is logged with its reason (`HTTP <status>`, `request failed: <code>`, `spawn failed: <code>`, `exit <code>`, `killed by <signal>`, `timed out after <n> ms`, `output too large`, `unparseable answer`, `4 classifications already running`: short reasons, never the command line or the prompt), once per reason every 10 minutes: a model that never answers shows in the log without flooding it.

## Shutdown, restart and interrupted runs

A clean shutdown no longer stops the runs in progress (ORC-344): the daemon lets go of them and they keep going, as after a `kill -9` ([`deployment.md`](deployment.md#clean-shutdown-and-restart)). They are not children of the daemon but containers, whose `docker exec` client writes its output to a file on the host that outlives it (on the host, without a sandbox, the `claude` process in its own process group, writing to the same file). At the next startup, with no human intervention (ORC-220), Relais:

1. **reattaches** to each attempt whose container is still running (`SandboxProvider.reattach`, by its label) and that the runner can resume (`Runner.attach`), raising its lease token first (see [the lease](#heartbeat-and-lease-of-an-attempt-orc-220)). The attempt continues, keeps its place in the queue and its result comes back as usual, even if it finished during the outage. Its egress proxy listens again on the same socket, which the container still sees: it mounted the socket's folder, not the socket. What the agent wrote during the outage does not reach the Linear thread (the transcript, however, is complete);
2. destroys the containers of the attempts it did not reattach to;
3. writes to the inbox, for each vanished attempt, `run.lost` (id `attempt:<run>:lost`), then closes it under a raised lease token (`running` → `failure`; `interrupted`, left by a daemon from before ORC-344, → `stopped`). Its decision **relaunches the step** with a start of its own: the ticket's session resumed (`--resume`, or `--session-id` under the same id if the attempt was cut before Claude wrote its session), the same inputs as the cut attempt (feedback read included, with its `taint`), the "Resumed after a cut" section at the end of the prompt. Unless nothing should run on the ticket any more (blocked, stopped, no longer delegated, PR merged). A review, which does not have the ticket's session, starts from scratch. A **question** is not relaunched (ORC-277): its decision replies in its thread « Relais restarted during my answer. Ask the question again in this thread. »;
4. writes `verify.lost` (`check:<run>:lost:<instant>`, since a relaunched verification can be cut again) for a cut verification whose effect is no longer pending: its decision relaunches the verification of the same attempt, whose verdict keeps the id `check:<run>`, kept once by the inbox. A finished run whose result was never written (outage between the two) receives that result, under its id, without relaunching anything. A run or a verification whose result is waiting in the inbox is left to that result, and so is one whose result was [set aside](#dead-letter-and-factory-run-repair-orc-175) whose repair is not decided yet (ORC-321): neither the verification nor an end is made up for it, its repair decides;
5. for a run that its ticket names and that was never written (outage during launch), drops the run: the start resumed in step 6 launches it, once (`startHandled`, [Idempotence](idempotency.md));
6. executes the effects decided before the shutdown and not yet done (`pending` outbox rows), then processes, oldest to newest, the events written to the inbox but not yet decided: a webhook accepted (200) just before a crash, a run or verification result written before the shutdown, or an event whose processing failed, along with the following events of the same ticket (see troubleshooting). An effect cut mid-execution (its row is `running`) is taken over by any daemon once its lease has expired (at most 60 s after the crash): it may then be executed a second time ("at least once"): each effect is idempotent, and an effect found already done is not rewritten ([Idempotence of external effects](idempotency.md)). A ticket's `run.lost` waits for these effects, like any event: a start that was just launched goes first, and relaunches nothing;
7. resumes the queue, the timers and reconciliation, which catches up on some of the Linear events missed during the shutdown ([`linear.md`](linear.md#3-webhooks-smee-or-public-url) says which)  : a reply in the thread posted during the shutdown is lost and must be sent again; a label added during the shutdown stays on the ticket with no effect, it has to be removed and added again.

### Bound on relaunches after an outage (ORC-220)

A daemon crash loop does not relaunch an agent every time. Each automatic relaunch (`run.lost`, whether from a restart or an expired lease, and `verify.lost`) is counted per ticket, over a sliding window: **3 relaunches per hour** (`CUT_RELAUNCHES`, `CUT_WINDOW_MS`, next to the lease in `src/store/types.ts`). Beyond that, nothing is relaunched and the ticket goes to Blocked: « Too many relaunches after a cut: 3 in 60 min. »; a cut verification is no longer awaited.

- `decide` decides at the event's time, never by the clock: replay decides the same thing. The instants are in the projection (`cutRelaunches`), absent as long as no relaunch has happened.
- These do not count: a reattachment to a live container, a recorded result sent as is, a resumed start whose launch had started nothing (no agent ran), a cut question (it is not relaunched).
- The normal end of an attempt does not reset the count: a loop that finishes a step from time to time is stopped too. Only a human relaunch (reply in the ticket, status change, new delegation on the blocked ticket) resets it.
- A ticket blocked by the bound stays blocked until that relaunch, even once the window has passed.

### Heartbeat and lease of an attempt (ORC-220)

This lease has its own bound, on top of the one above. Every 30 s (`RUN_BEAT_MS`), the daemon renews for 90 s (`RUN_LEASE_MS`, three beats: one missed beat is not an expiry) the lease of each attempt it supervises (`leaseUntil`, in the database), as long as its container is running (without a container, as long as it tracks it) and the attempt shows progress (ORC-344): something written to its stream within the silence bound of its workflow (`silentAfterMs`, 30 min in `factory/default`; 30 min, `RUN_SILENT_MS`, for a workflow version without one). Alive is not progress: an attempt that writes nothing more has its lease run out with its beats, and is then closed and relaunched as below. An attempt whose process ends does not go through the lease: it returns its result. An expired lease closes the attempt, destroys its container (an engine that does not respond relaunches nothing: the next beat looks again), then writes `run.lost`: **a single relaunch**, on the ticket's session; **a second consecutive expired lease blocks the ticket** (« The lease of the run … expired 2 times: the runner no longer responds. »). The bound (`leaseRelaunches`) resets when an attempt finishes, or when a human relaunches. The closed attempt no longer sends a result, and a late result arriving by another path is ignored (`ignored stale run.finished`, fencing). With the same bound, [stagnation detection](preset.md#attempt-stagnation-orc-136) (ORC-136) stops a silent attempt first and blocks the ticket: the lease is the backstop of a workflow version without the detector, and of a daemon whose pump no longer reads the stream.

**Lease token (ORC-344).** Each attempt carries a fencing token (`leaseToken`, in its record, from 1 at its launch). A daemon that takes it over raises it in the database, compare-and-set, before anything else: a reattachment at startup, an expired lease, a closing in `recover()`. Of two daemons, one wins. Every write of the attempt by its holder (lease renewal, the record of its end, its failure) carries its token, and is refused once the token is another: the daemon that lost it writes nothing more, neither its record nor its result. One whose renewal is refused while the attempt still runs under another daemon lets go of it, without stopping it, destroying its sandbox or removing its workspace. The outbox effects already have their own (the claim token of a row, ORC-150), and `decide` ignores the result of an attempt the ticket no longer holds (ORC-133).

### Deciding an event (ORC-149)

A worker processes the inbox, with one task per ticket: a ticket's events go one after the other, in order of arrival, and tickets progress side by side (a long `workspace.setup`, an `npm ci`, only holds back its own ticket). For each event, a single transaction:

1. takes the ticket lock (`pg_advisory_xact_lock` on Postgres; on SQLite, the transaction and the ticket's task in the single process);
2. checks that the inbox row is the oldest pending one for its ticket and that no effect of the ticket is unfinished, otherwise leaves it for later;
3. reads the ticket's projection and the workflow version it is pinned to, calls `decide`;
4. writes the journal, the decision (`decision_trace`: what is needed to replay it with `factory replay`, ORC-174), the projection, the timers, the effects in the outbox (id `ticket:seq:i`, `seq` being the event's position in the ticket's journal) and marks the inbox row as processed. A timer armed by a decision only fires once that decision's effects have been executed: a failed effect removes it before it fires.

A crash before the `COMMIT` leaves nothing: the event is decided at the next startup. After the `COMMIT`, the effects are executed from the outbox (see the next section).

### Executing effects (ORC-150)

The outbox executor (`src/runtime/outbox.ts`) takes a ticket's effects one by one, in `seq`, `i` order:

1. **Claim.** The ticket's first unfinished row is locked with `FOR UPDATE SKIP LOCKED` on Postgres: an executor never waits for another, two executors never take the same row, and a row held by another is not skipped (the ticket waits, its effects stay in order). The row becomes `running` under a 60 s lease, renewed every 20 s while the effect runs, with a claim token; the try is counted (`attempts`).
2. **Effect done.** In a single transaction, the row becomes `done` and its result enters the inbox under the id `effect:<id>` (type `effect.done`): the worker decides it like any event (it is journaled, and decides nothing more today). A finished run always enters as `attempt:<id>:finished`, verifications as `check:<id>`.
3. **Effect failed, tries remaining.** The row goes back to `pending` with its error, claimable after `1 s × 2^(try − 1)` (1 s, 2 s, 4 s… capped at 5 min, ORC-129). A [transient failure](#transient-and-permanent-errors-orc-343) gets 15 tries, about 33 min, a permanent one 8, about 2 min. The ticket's following effects and following events wait for it; other tickets progress. **A stop jumps the line** (ORC-138): an event whose decision stops the ticket's work (`control.stop`, `session.stopped` on the ticket's session, which reconciliation also sends when the delegation is removed, label `agent:stop`) does not wait for an effect held back by its backoff; in its transaction, the ticket's pending effects become `failed` ("cancelled by <event>", without `effect.failed`), and the stop is executed right away. A `running` effect still holds the stop back until its try ends. The stop also jumps ahead of the results (`effect.done`) of the already-done effects of the held-back decision, which are decided after it. A `dev` start is never launched on a blocked ticket: a retried start, or one taken from the queue, for a ticket blocked in the meantime is dropped (`refused … the ticket is blocked` in the log).
4. **Effect failed on its last try** (the 8th, or the 15th for a transient failure). In a single transaction: the row becomes `dead` with its error, the following effects of the same decision become `failed` (skipped, except `settle`), the timers armed by that decision are removed, and `effect:<id>` (type `effect.failed`) enters the inbox. Its decision blocks the ticket « Erreur : … » and posts the error in the session; if that error cannot be posted either, the ticket is only blocked (no loop when Linear is down). A delivered ticket (`done`, PR merged) or one stopped by a human is not blocked again: its reason « Stopped on request » stays. None of this state is kept in memory: a restart finds it as it was.

An executor killed during an effect leaves its row `running`: any daemon takes it over when the lease expires (at most 60 s) and executes it again. This is "at least once": an effect that had acted before the crash is replayed, but it first looks for what its first execution wrote (comment, activity, run start) or rewrites the same state (labels, status), and writes nothing more; its result then carries `deduplicated` and the daemon log says so (`effect <id> (<type>) already made…`). Per-effect details: [Idempotence of external effects](idempotency.md). A try cut this way counts as a try. Only the result and the row's state are written once: the claim token is rechecked in the transaction that writes `effect:<id>`.

### Transient and permanent errors (ORC-343)

An outage of GitHub, Linear or the database passes by itself: a ticket is not blocked for it, nor a result lost, as long as it lasts less than about 30 minutes. One function tells it from an error that would come back on every try (`isTransient`, `src/runtime/transient.ts`), from what each adapter throws:

| Source | Transient | Permanent (examples) |
|---|---|---|
| GitHub API | 5xx, 408, 429, a 403 for the rate limit | 401, 403 for a permission, 404, 422 |
| Linear API | 5xx, 408, 429, a GraphQL error `RATELIMITED` | an error of the query, an unknown issue, 401 |
| Network (`fetch`, `pg`) | connection refused, reset, timed out, name not resolved now | |
| Postgres | SQLSTATE `08…`, `53…`, `57P01`–`57P03`, `40001`, `40P01`; connection lost, or none obtained in time | a constraint, a syntax error; the pool closed by a shutdown |
| SQLite | database busy or locked | anything else |
| `git fetch`, `gh` | host unreachable, connection cut, a 5xx | a 403, a repository not found |

Anything else is permanent. Where each one goes:

- **An effect** (outbox): retried 15 times when transient, about 33 min, 8 times otherwise, about 2 min (see [above](#executing-effects-orc-150)). Past them, it is dead and blocks the ticket.
- **A launch**: a transient failure before its run is recorded (the forge's `git fetch`, Linear, the database) is a start tried again, not a « Launch error ». A start decided by an effect is retried as the effect; a start from the queue goes back in line after 2 s, 4 s, 8 s… capped at 5 min, 14 times in all (about 33 min), 5 times for a failure of the factory's own state that is not transient. Past them, the ticket is blocked « Launch error: … ». A failure of the launch itself (worktree, setup, the repository's `.factory/config.yml`) blocks it at once, as before.
- **An inbox event** (worker): retried 12 times when transient, about 34 min (2 s, 6 s, 18 s, 54 s, 162 s, then every 5 min), 5 times otherwise, about 80 s. Past them, it is [dead-lettered](#dead-letter-and-factory-run-repair-orc-175) as ORC-320 does: a long outage, or a permanent failure, still ends visible in the ticket, with `factory run repair`.
- **The result of a run or a check**: retried a few times at once; still failing transiently, it is kept and written again at each heartbeat (every 30 s), with no bound while the daemon runs. Its run is recorded at the same time, and its agent's output read then: an output the database could not give is not taken for an output the agent never gave. A daemon stopped meanwhile leaves it to the next start, which takes the run over (`recover()`).

### Dead-letter and `factory run repair` (ORC-175)

An event whose **decision** throws (`decide` or `reduce` throwing, or an event that the upcast refuses: a newer schema version) would throw again on every try: it is not retried. An event whose preparation or transaction fails on all its tries (12 for a [transient failure](#transient-and-permanent-errors-orc-343), 5 otherwise), on a tracked ticket, takes the same path (ORC-320): otherwise it would hold back everything arriving after it, and the ticket would appear unblocked. In a single transaction, under the ticket lock:

1. its inbox row is marked processed (it is no longer reread);
2. the event enters the `dead_letter` table, `open`, with the error and the number of failures;
3. the event `dead-letter:<id>:<n>` (type `dead_letter.added`) enters the inbox.

An event refused because another project holds the ticket ([one team, several repositories](projects-and-workspaces.md#one-team-several-repositories)) follows the same path, but its `dead_letter.added` goes to the project that holds the ticket, blocks nothing and reports the refusal in the ticket's session (ORC-316).

The ticket's following events go through (the ticket is not held behind it); those already in the inbox are decided before the block, which comes in behind them. The decision of `dead_letter.added`, a separate transaction, blocks the ticket « Event <id> set aside (<type>): its decision failed (<error>). », or « <n> attempts without success (<error>) » for a row out of tries, which may come from an outage (ORC-320), and says so in the blocking comment, with the repair command. A ticket that is already blocked keeps its reason (another set-aside event, a dead effect, red CI…): the message is posted, but repairing the event does not lift that block. A delivered ticket or one stopped by a human is not blocked again; an event with no ticket, or for a ticket the factory does not track, is only set aside.

A failure of the preparation (Linear unreachable to read the ticket) or of the transaction itself (database error) is retried first (see [Troubleshooting](#troubleshooting)); it is only set aside on the last try. A row stays in the inbox, retried without a restart, and holds back the following rows of its ticket when nobody could read its block: no ticket, a ticket the factory does not track yet (a first delegation, Linear unreachable), delivered or stopped by a human, or the `dead_letter.added` event itself and its repair. Likewise if the database cannot write the dead-letter: once the database is back, the row is decided on the next try, without a dead-letter. No event is lost. A daemon shutdown sets nothing aside: the row waits for the next startup.

A `replay` prepares the event it applies: set aside before being prepared, it thus gets its roles and its snapshot, and the authorization matrix applies to its replay. A `force` reads only the snapshot: it decides nothing, and goes through when the roles remain unreadable. If this preparation fails on all its tries, the dead-letter is reopened (`failures` + 1); in the cases where a row is not set aside (above), the repair stays in the inbox and is retried until the cause ends.

`factory run repair <ticket>` lists the ticket's set-aside events; `factory run repair <ticket> <action> [<event>]` repairs one (the event must be given when the ticket has several open; an event with no ticket is designated by its id):

| Action | Effect |
|---|---|
| `replay` | The event is decided again, on the unblocked ticket, with its effects: after a fix (deployment, corrected workflow). If it still throws, it is set aside again (`failures` + 1) and the ticket blocked again. |
| `skip` | The event is ignored: it is never decided. Refused for a run or verification result (`run.finished`, `run.lost`, `verify.*`): the ticket would remain "in progress"; use `force`, or `replay` for `verify.lost`, which `force` does not settle. |
| `force` | Its facts are recorded (`reduce`: delegation, status, merged PR…) without its decision: no effect, no timer. |

Each repair is **journaled**: the command writes directly to the database (the daemon does not need to be running) the dead-letter's new status (`replayed`, `skipped`, `forced`) with the user's name, and the event `repair:<id>:<n>` (type `dead_letter.repaired`, which carries the action, the author and the event as the inbox held it). The worker decides it on its next pass like any event: it is written to the journal, lifts the block of that event (not another) and announces it in the Linear session. A repair whose decision throws in turn reopens the event's dead-letter (`failures` + 1), like a `replay` that throws (a `force` of an event the upcast refuses, for example: only `skip` settles it). A ticket blocked by two set-aside events keeps the reason of the first: the second is repaired without unblocking the ticket.

**`queue` queue.** A start waiting for a slot is pulled from the queue under a lease (`FOR UPDATE SKIP LOCKED` on Postgres), renewed during its launch, and only leaves the queue once the run is written (or the start dropped: ticket not delegated, unknown job, put on hold behind a run). With no slot, it goes back to its place in the queue. A daemon killed in between leaves the start in the queue: it is taken over when the lease expires (up to 60 s late). Stopping the ticket also removes a start that is being launched.

**Workflow version.** The workflow hash (sha256 of its canonical JSON) is recorded in `workflow_versions` and in the projection (`workflowHash`, column `tickets.workflow_hash` on Postgres) on a ticket's first event. After a change to `workflow.yml` and a restart, tickets already tracked stay on their version; new ones take the new one.

**Two daemons on the same Postgres database.** A ticket's decisions and effects do not overlap from one daemon to the other (ticket lock, order of arrival, effect leases), and each daemon polls the inbox and the outbox every second. A start from the `queue` queue is pulled by only one daemon at a time (lease). Still single-daemon: `recover()` at startup takes over **all** `running` runs in the database, including those of another live daemon (the lease has no owner: a daemon restarted right after a `kill -9` finds its own lease still valid), and queue slots are counted per daemon. Leases are not released at startup (ORC-129 provides for this on a single server): a second daemon would take over the first one's in-progress effects; an effect cut by a crash therefore waits for its lease to end. The webhooks kept before the inbox (ORC-336) have no lease either: two daemons could both deliver one, and the inbox keeps each event once by its id, so the cost is a second model call, never a second event.
