# Idempotence of external effects

The outbox executor (`src/runtime/outbox.ts`, ORC-150) executes each effect **at least once**: an effect that acted and was then cut off before being settled (crash, lost lease) is executed again by the next claim. Each external effect is therefore idempotent: executed twice, it leaves only **one visible effect**. This page is the ORC-162 table, with the "duplicate behavior" column decided by [ORC-138](decisions/ORC-138.md#the-idempotency-table); each row has its test.

## The common rule

- **The key is the effect id**, `ticket:seq:i` (the id of the outbox row), followed by the installation id: `<ticket:seq:i>@<installation>`, for example `REL-1:1:2@3f9c0a1b2d4e`. It is stable from one execution to the next, never derived from the clock. The installation id (12 hex characters) is drawn once and kept in the store (`meta`, key `instance-id`): another instance on the same Linear workspace (staging, dev workstation), or this one after a database restarted from scratch, has other keys and never mistakes an effect of the other for its own.
- **Only a replay looks**: a row claimed for the first time (`attempts` = 1) cannot have written anything before, it writes directly; a row claimed again (lost lease, crash, retry after a failure) first looks for what the previous execution wrote. The normal path therefore costs no extra call to Linear.
- **A detected duplicate is a success** (ORC-138, option B3): the execution that finds the effect already done writes nothing, and its result `effect:<id>` (`effect.done`) carries `deduplicated: true` and, when the adapter provides it, the reference of the object found (`ref`: id of the comment, of the activity…). `decide` derives nothing from it, but notes it in its trace (`effect <id> deduplicated`), and the daemon writes it to the log: `effect <id> (<type>) already made (<ref>): not written again`.
- **A "final state" effect** (labels, status, link) has nothing to look for: it rewrites the same state, and the adapter writes nothing when the state is already there. The outbox executes a ticket's effects in `seq` order: an old replayed effect does not run after a more recent one.
- **The only exception** is the push whose branch has moved to another SHA: a conflict, never replayed, returned to `decide` (`publish.refused`).

## What Linear allows

- **Comments**: `commentCreate` accepts a client `id` (UUID v4) and `comments(filter:)` filters by `id` and by `body: { contains }`. The adapter writes both keys: the marker the ticket asks for, and an id derived from the effect id (sha256, with the version and variant bits of a UUID v4). The lookup takes one **or** the other: if Linear did not keep the HTML comment in the body, the id is enough.
- **Session activities**: `agentActivityCreate` also accepts a client `id`, but `AgentActivityFilter` does not filter on content (only `id`, `type`, dates, session): an activity's key is therefore its id, not a marker, which would moreover show up in the agent's thread.
- **Not verified live** (the Tracker's live test is read-only): that Linear accepts a client id on these two creations for an app (the public GraphQL schema describes it: "The identifier in UUID v4 format. If none is provided, the backend will generate one."), and what Linear does with `<!-- … -->` in a comment body: keep it hidden, strip it (the id is then enough for the lookup) or display it as text, which would be visible under every factory comment. To check on a test workspace before going to production; if the marker shows, the client id is enough and the marker should be removed.

## What GitHub and Docker allow

- **Check run**: only a GitHub App can create or modify a check run ("OAuth apps and authenticated users are not able to create them"): `ForgeWriter` is only implemented by the GitHub App adapter, not by `gh`. The API does not filter on `external_id` (parameters: `check_name`, `status`, `filter`, `app_id`), but returns it: the lookup is done on the factory side, on the SHA's check runs carrying the requested name, page by page (100 per page).
- **PR**: the `POST /pulls` docs only say "422: Validation failed"; that GitHub refuses a second open PR for the same branch is **not verified live**. `ensurePr` does not rely on it: after a 422, it reads the open PR again, and rejects with the error if there is none.
- **Container** (verified with Docker 28.2.2): a second creation under the same name is refused (`Conflict. The container name "…" is already in use`), and `docker ps -a --filter label=factory.attempt=<id>` finds the container, even if only created.

## Limits

- **Lease lost under a live executor**: two executions can read "absent" then each write (ORC-138). The duplicate remains rare and visible: two comments with the same marker (on Linear, the second creation under the same client id should be refused, not verified). For the model call, nothing on the server side stops it: a slow launch that loses its lease can be duplicated.
- **The `effect:<key>:started` mark** of the model call is local (`meta`, stored with the workflow versions on Postgres), one per `start_run`, never purged. A launch writes it with its attempt's id **before** writing the attempt, hence before the runner starts it (ORC-277), then sets the attempt on the ticket (`run.started`), then writes it; it goes to `1` once the start is handled. On replay: mark at `1`, or the named attempt is written, nothing is relaunched; named attempt never written (crash between the mark and the write), nothing was launched and the start is replayed. An attempt written then cut off is `recover()`'s business (ORC-220): reattached if its container is alive, otherwise `run.lost`, whose decision writes a new `start_run` row, with its own mark, which names the attempt it relaunches (`relaunchOf`): each row launches at most once, and replaying the first relaunches nothing. A **question** is not relaunched, and the « Ask the question again » notice is the human's only message. An attempt named by the ticket and never written: `recover()` drops it (`run.cleared`), and the resumed start launches it. A start queued by the effect carries its own mark, `effect:<key>:started:queued` (the effect's mark is already `1`), which its launch by `drain` writes in the same way: an item taken out, launched then cut off before its removal from the queue, taken out again after its lease, finds its attempt and is not relaunched. A start queued without an effect (the pending start of a `dev` ticket, gone through `settle`) also receives its queue mark. Only that same start launched directly by `settle` has no mark: cut off before its attempt is written, nothing takes it back, and `recover()` writes `run.lost` on the job the ticket holds; its inputs are then those of the default job.
- **Replayed labels**: the engine sets the echo of added labels before writing; a replay that writes nothing sets one for nothing, and a human who changes that same label within the following minute (`ECHO_MS`) is taken for an echo.
- **Feedback read twice**: a cut between writing an attempt and removing its feedback (`feedback.consumed`) leaves that feedback on the ticket: the relaunch reads it in the cut-off attempt, and the next run reads it again. Feedback read twice rather than lost.
- **Two daemons starting together on a fresh database** each draw an installation id; the last write wins in the database, but the first keeps its own in memory until it restarts.
- **The result of a publication** comes back as two events, `pr.opened` under the id the webhook gives it (the first of the two counts) and `publish-done:<key>`. A cut between them leaves the PR known to the ticket, and the replay writes the second.
